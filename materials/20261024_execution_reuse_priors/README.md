# 実行の先行処理・再利用を次候補にする際の先行研究

2026-10-24。P84の固定生成中に確認した一次資料。新しい方式の実装や性能検証ではない。[読取範囲](../../reports/execution_reuse_prior_sources_20261024.json)を記録した。原稿の主張を増やすためではなく、既存の手法を新提案として作り直すことを避けるための確認である。

| 先行研究 | 読んだ範囲での仕組みと限界 | 研究目的との関係 |
|---|---|---|
| [TomasuLLM v1](https://arxiv.org/html/2609.38201v1)、2026-09-22 | 予測した道具処理を隔離環境で先行実行し、実際の次行動、依存状態、観測、変更結果を検証して順に反映する。主モデルの判断を代行して省く方式ではない。§5.4は主モデル約8.3M対8.2M tokenに加え、先行処理に1.6M tokenなどが必要と報告している | 応答待ち時間の短縮と、制御・外れた予測を含む総計算量削減を分ける。状態検証を付けた先行実行だけでは独自性にならない |
| [Speculative Macro Commit v1](https://arxiv.org/html/2609.03236v1)、2026-09-03 | 訓練記録から抽出した処理列、予測済み実行、先頭行動の一致、状態検査で後続の主モデル判断を省く近似方式。AppWorldは70/168から68/168へ完了数が下がり、逐次１GPUと投機３GPUの構成差もある | AppWorldでの処理列再利用と判断回数の省略にも既存例がある。遅延短縮だけを、こちらの「成果品質を保つ全仕事費用削減」の成立へ読み替えない |

上の数値は論文の報告であり、こちらで再現した測定値ではない。TomasuLLMの保証は道具の依存関係を追跡できることなどに依存し、SMCの実行列省略は論文自体が厳密な同一性を保証する方式とは扱っていない。これらと異なる方式を検討するなら、どの判断を何の根拠で省けるか、状態変化をどこまで検出するか、外れた場合の全費用を明示する必要がある。

途中で切れた生成の部分実行、予算付き文法、投機実行について計６問を検索し、最終目標に近い上の２本の該当節を読んだ。検索で見つからないことを新規性の証拠にしない。外部実装・追加モデル・課題実行は行っておらず、新たな計算予算の配分や採用決定はしていない。
