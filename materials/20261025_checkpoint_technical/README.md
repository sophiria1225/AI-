# 現在のハーネスと一度だけの要約処理

2026年10月25日、P118の全８条件が閉じる前に実装を確認して作成した技術説明. 中間の成否や要約本文は参照していない. この資料の例と計算は説明用であり、実験成績ではない. [P111実行時点の説明](../20261025_harness_technical/README.md)を上書きせず、今回の変更点を分けて残す.

ハーネスエンジニアリングを使っている. モデルの外側で、次の入力、Pythonの状態、APIの実行、記録、残予算を管理する. モデルの重みは変更していない. 今回はその基盤へ通常の要約方式を接続し、要約を行わない全保持方式と比較している. これだけで新規手法が成立したという意味ではない.

## 保存状態とモデル入力を分ける

会話の完全な保存記録、Pythonの実際の状態、次にモデルへ送る文章は別のものとして管理する.

| 管理するもの | 役割 | 要約後の扱い |
|---|---|---|
| 会話の保存記録 | 元指示、推論、実行コード、観測を残す | 原文を保持する |
| 持続Python | 取得したデータや変数を後続処理で使う | 状態を保持する |
| モデルへの入力 | 次の判断に見せる文章 | 古い会話だけを要約へ置き換える |

例えばPythonに一覧 `rows` が保存されていれば、次のコードは同じ変数を参照できる. しかし、変数が存在することと、モデルがその存在や意味を覚えていることは別である. 要約へ利用できる変数や未完了作業を残すよう指示するが、漏れなく残ったとは保証しない. また、完全な保存記録があるだけで、今回のモデルに任意の過去履歴を再取得する専用ツールが与えられるわけではない.

実行基盤は[持続Python](../../scripts/persistent_api_python.py)、今回の入力制御は[SingleCheckpointInference](../../scripts/single_checkpoint_inference.py)である. API取得を遅らせる別実装のReadViewは今回使っていない.

## いつ、どこを、どう要約するか

次の実行役入力を実モデルのtokenizerで数え、初めて16,384 token以上となり、完了した会話ターンが３つ以上ある時点を候補にする. １ターンはassistantの出力と、それに対応する全ツール結果の組で、途中で切り離さない. 16,384は65,536の文脈上限の４分の１として事前に固定した値である.

入力の構成は次のように変える.

```text
全保持:
  元のsystem指示 + 元のtask + 古い会話 + 直近２ターン

要約採用後:
  元のsystem指示 + 元のtask + 古い会話の要約 + 直近２ターン
```

さらに後続の会話は原文のまま追加する. 要約後に繰り返し圧縮する方式ではなく、１課題につき一度だけである. この機会に予算不足で見送った場合も、形式不正などで採用できなかった場合も、後で再試行しない.

要約を作るのは同じM3モデルである. 要約役は通常の実行役とは異なる指示を受け、ツールを持たず、次の４項目のJSONだけを返す.

| 項目 | 記録させる内容 |
|---|---|
| `completed` | 観測できた処理結果 |
| `usable_state` | 継続に使う識別子、API情報、持続変数など |
| `remaining` | 未完了の作業と条件 |
| `uncertainties` | 未確認事項や完全性への疑い |

これは固定された４分類の通常要約で、実行結果から自動証明した状態表ではない. `completed`という項目名も、そこに書かれた事実の検証済みを意味しない. モデルへ渡す包装には`ordinary_fallible_summary`と`semantics_verified: false`を明記する.

[SingleCheckpoint.begin](../../scripts/single_checkpoint_history.py)が候補を一度だけ作り、`closed_turns`が会話の組を検査し、`project`が実際に見せる入力を構成する. 保存したprefixの指紋も照合し、違う時点の要約を誤って当てはめない.

## 要約を採用する検査

要約の生成完了理由が`stop`であること、ツール要求がないこと、JSONの項目が正確に４つで重複しないことを検査する. 各項目は最大32本の文字列、各文字列は1〜2,048文字、出力本文全体は最大8,192文字とする. 検査に通らなければ元の履歴を使い、要約の修正生成はしない.

形式に通った後、同じ更新後の予算通知を入れた「元の入力」と「要約後の入力」を実tokenizerで数える. 要約後が厳密に短い場合だけ採用する. この検査が確認するのは形式、対応する履歴、直後の入力長であり、内容の正しさや最終品質ではない.

要約が情報を落とせば、誤った対象を操作したり、完了済みの調査を繰り返したりする可能性がある. APIの正常返却だけではそれを否定できないため、最終成果はモデルへ見せない独立評価で調べる.

## 費用を別枠にしない

実行役と要約役は、同じ呼出し台帳、token残予算、仕事の時計を使う. １条件の上限は合計80呼出し、450,000論理token、1,800仕事秒である. 生成失敗や要約不採用でも、使った費用は残る. 使用量不明は０で補完せず、その条件の継続を止める.

```text
全仕事token費用
  = 全実行役呼出しの(input + output)
  + 全要約役呼出しの(input + output)
```

要約前には、要約と次の実行役の２回分の呼出し枠を確認する. 要約入力、現在の実行役入力、両者の最大出力を残token予算と照合する. 要約後には予算通知の数字が変わるので、実際の次要求は改めて計数して予約する. 事前検査だけで次の仕事の完了や最大出力を保証しない.

[attempt_usage](../../scripts/checkpoint_attempt_usage.py)は両役割の送信開始と使用量返答を対応づける. 送信されたのに使用量が戻らなかった要求も、不明な要求として残す. [全件監査](../../scripts/audit_whole_task_single_checkpoint.py)は８条件全ての入力、費用、独立評価との対応を確認する.

例えば、要約生成に20,000 tokenを使い、その後の入力を毎回5,000 tokenずつ短くできるとする. 後続３回なら省ける入力は15,000 tokenで、差し引き5,000 token増える. 後続５回なら、出力や行動が同じという仮定の下で5,000 token減る. 実際には呼出し回数や出力、再取得が変わるので、この単純計算を実験結果へ置き換えない.

過去の入力を変えるとprefix cacheの再利用も変わる. 論理token、実測cached token、実時間は別々に記録する. 今回の主指標は全仕事の論理input＋outputであり、cacheに載ったtokenを０として差し引く方式ではない.

## 以前の選別方式との関係

P111では要約モデルを使わず、実行記録をホストで判定し、古い推論の表示を切り替えた. 正常な実行やAPI返却の記録を使うが、それが将来に必要な推論の判別に十分かは別問題だった. 全12条件の結果は事前の採用基準へ届かず、未知使用量２件も残った. [P111所見](../../docs/P111_findings.md).

P118は「普通の要約を、制御費用まで含めた同じ基盤で比較する」という次の対照実験である. 現在の４課題は既知の開発課題で、未見12課題は開いていない. 全８条件終了後に成功損失、要約の適用状況、全課題と両側成功課題の総費用を判定する. 要約が有効でも新規性や一般的な品質維持は別途必要になる. [P118固定計画](../../docs/experiments/P118_whole_task_single_checkpoint.md).

## 共通基盤について確認した既存実装の説明

[Docker Agentの公式予算仕様](https://docker.github.io/docker-agent/configuration/budget/)にも、要約呼出しを同じ予算へ計上する仕組みが記載されている. 同資料の上限判定はturn境界で、進行中の１turnぶん超過し得ると説明されており、今回の要求前予約と全く同じ実装とは扱わない.

[Yielded Agentの公式履歴管理](https://yielded.dev/agent/guide/context-management/)は、保存履歴と入力表示の分離、元指示と完結したtoolの組の保持、要約の共通予算計上を説明している. これは当該文書の確認で、コードの再現や品質保証の検証ではない. 共通予算や保存場所の分離だけを独自性へ数えない. [確認範囲と取得記録](../../reports/checkpoint_runtime_documentation_scope_20261025.json).
