# P120: 要約を必須引数として指定する同時出力の準備

P119では任意のcheckpointが２機会とも出力されず、要約採用０件、CSVの成功損失１件だった. 今回は要約を求める１回だけ、run_pythonのrequiredへcheckpointを加え、指示文でも出力を要求する. tool_choiceはautoを保ち、追加呼出しや再生成はしない. 必須指定はモデルの従属性や意味の完全性の保証ではない.

別呼出し要約と、必須欄を指定する同時出力を、既知４課題×２方式の全８条件で各１回比べる. 16,384 native token以上の最初の機会を使い、元指示、直近２回、今回のコードと実際の返却、その後の履歴、Python状態を残す. コードと要約は同じ4,096出力tokenを共有し、追加指示、schema、出力、失敗、再調査を共通予算へ数える.

新規34テストを含む全1,974テストと構文検査が成功した. 合成試験は、必須schemaと指示の対応、一度だけの適用、介入前入力の一致、コード不変、全費用、不明応答の不実行、欠落・不正・打切り、後処理と記録監査を確認した. これらは実モデルの成功や費用削減の測定ではない.

各条件80モデル呼出し、450,000論理token、1,800仕事秒. 写真160 API、他80 API. 全８枠の上限640呼出し、3,600,000 token、800 API、８評価、所有server21,600秒. 同一headの両workflowと両job成功後、12入力の語彙計数を確認し、固定順で一度だけ実行する. 全８件の使用量既知、成功損失なし、全体と両側成功課題の総token減少に加え、同時出力要約の実採用１件以上を必要とする.

これは通常対照の確認であり、必須欄の追加を新規性とはしない. P119の失敗と不発動、P111の不明２件、P118の不明１件を保持する. 原稿と未見12課題は保留し、全件終了後に結果をまとめる.
