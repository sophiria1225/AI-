# 同じ返答で行動と引き継ぎ記録を作る実装

この説明はP119実行中の固定ソースに基づく. 中間成績や私有要約本文は参照していない. 原稿は更新しない.

ハーネスは、LLMへの入力、Pythonの実行状態、APIの受付と返却、保存履歴、残予算を管理するプログラムである. 今回はこの外側の制御を変更し、モデル重みは固定している. 使っている構成は、状態を保つPython実行環境、型付きAPIの実行記録、保存履歴と入力表示の分離、全役割に共通の費用台帳である.

P118では、要約だけを作るために長い履歴をもう一度モデルへ送った. P119の同時出力条件は、通常のPythonコードを返す要求に、任意の引き継ぎ記録も加える. 専用の要約要求を省ける可能性がある一方、追加指示と記録の出力は無料ではない.

```text
1. 次の入力を実tokenizerで数える
2. 16,384 token以上、完結したやり取り３回以上で一度だけ要約を要求
3. 通常の行動応答 = 元のコード + 元の参照ID + 任意のcheckpoint
4. checkpointを実行引数から外し、同じコードと参照IDを一度だけ実行
5. 次の行動が必要なら、古い履歴をcheckpointへ置き換えた入力を数える
6. 形式が正しく、短くなった場合にその表示を採用
```

checkpointは`completed`、`usable_state`、`remaining`、`uncertainties`の４欄である. 対象は古い完結履歴に限り、元指示、直近２回、同じ返答のコードとその実行結果、以後の履歴は残す. 同じ返答のコードをまだ実行していない時点で、その結果を確定事実として要約させない.

形式検査では重複JSONキー、余分な引数、型と長さ、生成の終了理由を確認する. 出力が短くても、要約中の事実や未完了作業が正しいという意味にはならない. 不採用でも使った生成費用は計上する. 保存した原応答と実行へ渡したコードの指紋を照合するが、それも意味の正しさの証明ではない.

両方式は同じ80モデル呼出し、450,000論理token、1,800仕事秒の枠を使う. 最終結果では、成功を落としていないことに加え、全呼出しの入力と出力、要約費用、再調査、失敗を含む合計を比べる. Pythonに残った変数は使い続けられるが、モデルがその変数の意味を覚えているかは別に評価が必要である. ReadViewによる遅延API取得は今回使っていない.

費用差は次の関係で照合する. 実行役の費用は各要求の入力と全出力の合計であり、同時出力の追加指示、schema、要約文も含む.

```text
別呼出し方式の総費用 = 別呼出し方式の実行役費用 + 専用要約費用
同時出力方式の総費用 = 同時出力方式の実行役費用
総費用差 = 実行役費用の増減 − 専用要約費用
```

総費用差が負なら同時出力の方が安いが、成功を落としていないことも必要になる. 使用量不明がある全費用差は数値で確定しない. １回の出力上限4,096 tokenをコードと要約が共有するため、要約で出力枠が埋まり、コードが途切れる場合も比較に含む. キャッシュ済み入力を論理tokenから差し引かず、実時間とキャッシュ再利用量は別に記録する.

近接するMEM1は、内部状態と次の行動を同じ生成過程で作り、古い文脈を更新する. 論文には学習済み方式のほか、通常の指示モデルへ同じ切詰め手順を与えた対照もある. したがって、同時出力や学習不要という特徴だけを新規性にしない. P119はMEM1の再現ではない. [MEM1 v1 §3.1、§4.1、付録A.5](https://arxiv.org/html/2506.15841v1#S3).

P119が確認するのは既知４課題の通常方式間の費用と成功であり、新手法の独自性や一般的品質保証はまだ確立していない. 全８条件が閉じてから結果を追記する.

実装を追う場合の入口は次のとおりである. いずれも実験開始時に固定したソースを使う.
