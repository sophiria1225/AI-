# 通常のAPI呼出しと将来取得の共通予算

2026年10月24日。[読取ビューの部品](../20261024_explicit_read_views/README.md)に必要な、仕事全体で共有するAPI要求数の予約会計を[実装](../../scripts/shared_api_reservations.py)した。既存の公開APIチャネルと型付き実行記録を使うホスト側の接続である。実APIへの遅延読取、Pythonコンテナとの制御通信、モデル実験にはまだ接続していない。

通常の呼出しが使えるのは、上限から実送信数と将来取得の予約数を引いた残りだけ。例えば上限２回で１回分を予約していると、通常の呼出しは１回まで実行できる。残り０でも、予約した完全取得にはその１回を使える。別のPythonプログラムに移っても同じ予算を共有する。未使用予約の解放は実送信数を減らさず、節約効果という集計もしない。

| 実行記録 | 会計と継続 |
|---|---|
| 未公開API、不正要求、期限前の拒否 | 未送信。実費を追加せず、将来取得の予約を残す |
| 正常な応答 | 予約１回分を実送信１回へ移す |
| 確認されたAPI例外 | 実送信１回。副作用の巻戻しを仮定しない |
| 送信後の通信断や割込み | 実送信１回と結果不明を残し、仕事全体の追加送信を停止 |
| nonce生成など送信前の内部失敗 | 実送信０。予約と失敗を残して停止 |
| 完了宣言 | 追加送信を停止。残る予約を成功や節約へ読み替えない |

既存チャネルが行を追加する前に `KeyboardInterrupt` が起きても、輸送側の送信記録から費用を残す。最初の９検査は通過したが、この割込み経路をコードレビューで追加し、10境界検査と全1,327検査を再確認した。最初の検査記録も保存した。手書きの模擬サービスと既存の型付き記録経路を使い、AppWorldの課題データ・API・モデル・評価器は呼んでいない。

この会計部品は純粋な読取や部分値の正しさを認定しない。遅延取得が例外になった場合に「必ず成功する読取」という前提を失効させる制御は、取得器側に必要である。単一スレッドで使い、再入した要求・予約変更を拒否する。回数の予約だけで、時間・生成token・課題品質は保証しない。

次は返却済み情報から作る部分値、状態変更前の完全取得、コンテナ側の参照寿命とホスト側の予約を接続する。通常の即時取得と同じ明示的インターフェースで比較し、全追加費用を含める。候補の実装が進んだことと、新規性・全仕事の改善が示されたことは区別する。P88の途中成否・出力は参照していない。
