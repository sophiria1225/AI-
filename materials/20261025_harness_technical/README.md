# 現在のハーネスと、トークンを減らす候補の技術

2026年10月25日. P111の全件比較を実行している時点の説明. 以下の手順例は説明用であり、実験成績ではない. 原稿ではなく、ユーザーへの技術説明と実装の対応を残す資料.

ハーネスエンジニアリングを使っている. モデルの重みを学習し直すのではなく、モデルへ渡す履歴、生成したコードの実行、APIの入出力、保持状態、予算と停止を外側のプログラムで管理する. 研究上の問いは、その管理方法によって最終品質を保った仕事全体の費用削減が成立するかである.

## 実行の１周

1. 公開task、保存した会話、予算を基に、次のモデル入力を作る.
2. 実際に送る入力のtoken数を計数し、残予算に収まる出力上限を決める.
3. モデルが `run_python` に渡したコードを、課題ごとの隔離された持続Python環境で実行する. 次の手順でも同じPython変数を利用できる.
4. Python内のAPI呼出しをホストの橋渡し処理へ渡す. API名と引数を検証し、実際に送信したか、返却したか、例外や作用不明があるかを型付きの記録に残す.
5. stdout、例外、公開API結果を会話へ追加し、次の入力を作る. どの方式も同じ公開指示、API経路、環境と予算規則を使う.

[実行ループ](../../scripts/run_whole_task_receipt_history_cell.py)と[持続Python](../../scripts/persistent_api_python.py). 生の値をPython変数で扱い、必要な表示をコードで選べることは共通基盤であり、今回の比較で提案方式だけに与えた利点ではない.

## 現在比較している技術：実行記録で過去の推論表示を切り替える

元の会話を保存する場所と、次のモデルに見せる会話を分ける. 削除候補は過去の `reasoning_content` だけで、公開指示、コード、引数、観測結果は残す. 推論原文は保存先に残り、表示を戻す際には同じ原文を使う. 要約用の追加モデル呼出しはない.

各手順について、次の条件をホストが確認する.

- 対応する `run_python` が正常終了し、拒否や途中切れがない.
- 実際の内側API送信が１件以上あり、その全件が正常返却し、作用不明がない.
- 外側のコード実行記録に、内側API記録が重複や欠落なく結び付く. 関数名と全引数の指紋が、会話に残る呼出しと一致する.
- 未取得の読取予約が残っていない. P111の即時API経路では予約そのものを使わないため０である.

ここでの正常返却は実行に関する条件であり、課題の正解や業務上の成功を意味しない. APIが正常に返っても、対象を取り違えたり、必要な処理が不足したりする可能性がある.

表示規則は次のとおり. 直近の推論は常に残す.

| 方式 | さらに古い推論の扱い |
|---|---|
| 全保持 `full` | 全て残す |
| 直近保持 `recent` | 全て非表示にする |
| 実行記録による選別 `execution_gated` | 直近が上の条件を満たす場合、古い手順のうち同じ条件を満たすものだけ非表示にする. 直近が条件を満たさなければ全て再表示する |

例えば、手順１と２が適格なら、次の入力では手順１の推論を非表示にし、手順２の推論を残す. 続く手順３で例外が起きた場合、次の入力では手順１〜３の推論を原文で表示する. その後の手順４が適格になっても、例外のあった手順３の推論は残す. 後の正常終了だけでは、昔の失敗が解決したとは判定しない.

[表示規則](../../scripts/receipt_reasoning_history.py)の `execution_evidence` と `project`、[実行への接続](../../scripts/receipt_history_inference.py)の `record_execution` と `call` に対応する. 判定はその時点までの実行記録だけを使い、未来の最終評価を見ない.

## トークンが減る経路と、減らない場合

モデルを呼ぶたびに過去推論を入力へ含めれば、その分が各回の論理input tokenに加わる. 例えば、500 tokenの古い推論を後続10回で省けば、後続の出力と呼出し回数が変わらないという仮定の下では、入力は約5,000 token減る. 実際には文章の境界による計数差もあるので、実入力で計数する.

一方、情報を省いたせいで再調査や失敗が増えれば、追加の入力と出力が削減分を超える. 再表示した推論も、その回の入力として数える. 比較する費用は全モデル要求の `input + output` の合計であり、短くなった一つの入力だけではない.

過去のprefixを変更すると、モデルサーバーのKV cacheを再利用できる範囲も変わる. 論理token、実測cached token、実時間は別々に記録する. 選別や記録に要したホスト時間も仕事時間に含める. 不明な使用量は０で埋めない.

P110では過去の固定軌跡から444の仮想入力を数えた. 全148境界のうち選別方式が入力を短くしたのは96境界、原文を再表示したのは20境界だった. これは機構の適用範囲であり、新方式の正答率や全仕事の削減実績ではない. [P110の所見](../../docs/P110_findings.md).

## 別に実装した技術：必要になるまでAPI取得を遅らせる

明示的な読取専用 `ReadView` を作り、公開API契約から一致を確認できる項目は既取得値で返す. 未取得項目や全体の取り出しが必要になった時点で完全な取得を行う. `dict` を透過的に置き換える仕組みではなく、専用の `Mapping` インタフェースである.

同じ課題、状態世代、API名と全引数の未取得要求を共有し、最後の参照がなくなれば未使用予約を解放する. 状態を変え得る呼出しの前では、必要な未取得値を確定する. 未確認のAPIを単に読取と決めつけない. 送信済み件数を S、将来取得の予約を R、上限を B として `S + R <= B` を維持する. 予約を取消した件数と、実際のAPI削減件数は同じではない.

[公開契約](../../scripts/field_read_contract.py)、[参照と取得](../../scripts/public_contract_read_views.py)、[要求の共有](../../scripts/coalesced_contract_read_views.py)、[予約予算](../../scripts/shared_api_reservations.py). 通常のキャッシュ、遅延評価、要求共有それ自体を新規性とはしない.

P106では通常の完全応答キャッシュを両方式へ入れると、手書き実行列のAPI数は12対12だった. P107のモデルによる全仕事比較では、両方式ともReadViewと対象の詳細取得を使わず、最終課題も未達だった. 従って、この技術でトークン削減や品質維持を達成したとは言えない. 現在のP111には接続していない. [P106](../../docs/P106_findings.md)／[P107](../../docs/P107_findings.md).

## いま確かめていること

P111は既知４課題を最初から、上の３表示方式で各１回実行する. 全12条件が閉じた後、全保持と直近保持の両方に対して、各課題の成功を失わず、全課題の総論理tokenと、両側成功課題の総論理tokenがともに減るかを調べる. 実行記録が、単純な直近保持より有用な判断材料になるかが焦点である.

この条件を満たしても、１回の既知課題比較だけで一般的な品質維持や新規性は確定しない. 推論圧縮、失敗時の情報提示、履歴の保存と復元には先行研究がある. [先行５方式](../../docs/receipt_history_prior_scope_20261025.md)と[追加照合](../../docs/receipt_history_additional_priors_20261025.md)の範囲を踏まえて判断する. [P111の固定計画](../../docs/experiments/P111_whole_task_receipt_history.md).
