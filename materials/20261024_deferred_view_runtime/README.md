# 読取ビューの制御通信と独立したPython実行器

2026年10月24日。Python側の明示的な読取ビュー、ホスト側の将来取得予約、既存の型付きAPI記録を接続した。[制御通信](../../scripts/deferred_view_protocol.py)と[独立した実行器](../../scripts/persistent_read_view_python.py)を追加し、進行中P88の実行器・コード・条件は変更していない。

利用側は `read_view(app, api, ...)` で読取専用の応答を保持し、通常のAPIは `call_api(...)` で呼ぶ。即時取得と遅延取得に同じインターフェースを与える。ユーザーのPythonソースへ前置きやAST変換を加えず、別の初期化実行で能力を用意する。初期化、制御通信の件数・バイト数、終了処理と全体時間を記録する。制御通信をAPI実送信へ水増しせず、実際のAPI記録は全て残す。

| 場面 | 接続した動作 |
|---|---|
| 既知項目の読取 | Python側の部分値のコピーを返し、完全取得の予約を残す |
| 未取得項目や全体の読取 | ホストへ要求し、予約を使って完全応答を取得する |
| 次のPython実行へ参照を保持 | 同じビュー・応答・ホスト予約を維持する |
| 影響が不明な通常API | 生きたビューを先に完全取得し、旧状態の応答を保持する |
| 最後の参照の回収 | 通信せず解放を待ち行列へ置き、次の要求か実行終了前にまとめて通知する |
| Pythonで例外が発生 | 元の例外を残し、終了通知前に解放要求を処理する |
| 完全取得の前提違反 | 確定した費用を残し、実行器を停止する。確認された違反を不明な副作用と混同しない |

９件のJSON境界検査と７件の実行器検査を含む全1,343検査が通過した。実行器検査は手書きの信頼できるコードをローカルの別Pythonプロセスへ送り、実際の既存通信ループと新しいアダプタを通した。元のプログラム境界、例外後の解放、初期化費用、実API記録、既存bootstrapが不変であることを確認した。Dockerコンテナでの動作やAppWorldの課題結果を測定したものではない。

部分値を認定する関数は、ホストから渡す明示的な仮定である。現在の検査では手書きの模擬サービスの値を使い、実サービスの公開応答から部分値を自動構成したとは主張しない。誤った部分値を信頼すると、照合前に誤った値を返せる反例も残した。通常APIの影響が不明なら全ビューを取得するため、この保守的な規則で削減が消える場合もある。実課題の新規性・品質維持・全費用改善は未検証である。

次の[コンテナ確認処理](../../scripts/probe_deferred_view_container.py)を有限に固定した。即時／遅延の２条件、各初期化１回＋手書き３プログラム、各模擬API上限４回、再試行０。各プログラムには30秒の応答予算を渡し、全体の240秒時点を次の実行前に確認する。継承したコンテナ作成・点検の個別コマンドには30秒・15秒の上限があり、起動を含む全経過時間が必ず30秒以内という保証ではない。全作業・終了時間を報告する。モデル生成・環境API・課題評価は全て０である。

この確認は、固定headのCIとP88の全件終了・所有推論器停止を確認した後に新しい出力先で一度だけ行う。ここでは未実行。部分値を模擬世界から無料で与えるため、確認できても仕事全体の節約や実課題品質へ外挿しない。[準備と検査の記録](../../reports/deferred_view_runtime_preparation_20261024.json)。
