# P105: 参照共有は動いたが、残る差には強い比較が必要

全３方式・手書き21段階を実行し、全７段階の標準出力が一致した. APIは即時13、元の遅延16、参照共有12. 全41 APIがreturned、予約残り０、全コンテナ終了と所有bridgeの不在を確認した. 手書き21段階にクライアント設定３回を加え、Pythonは計24実行. モデル・課題評価・未閲覧群参照０.

[全21段階](all_21_programs.csv)／[全３方式と制御費](all_3_conditions.csv)／[集計](summary.json)／[段階別の解釈と事前説明の訂正](../../docs/P105_findings.md).

元の遅延版の重複取得４回を解消したが、即時方式に対する残る１回差は、通常の`call_api`が取得済みの完全応答を再利用しない段階６による. 段階４–５での取得省略は段階７の再取得で相殺された. 事前仕様の原因説明を結果側で訂正し、元の記録は保持した. 通常呼出しにも同じ完全応答キャッシュを適用する比較を準備する.

全方式の制御要求は29回、送信3,788 byte. 返信は即時9,262、両遅延版7,850 byteだった. 全体9.706秒だが、固定順序で各１回のため速度改善の主張にはしない. 機構を作動させる手書き例であり、自然な課題での出現頻度、LLM使用量削減、新規性は未確立. 原稿は保留を維持する.
