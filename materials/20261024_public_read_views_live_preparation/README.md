# 公開APIと読取ビューの有限な接続確認の準備

実AppWorldサービスに接続する前の準備記録。新しいモデル実験ではなく、既知の書出し課題の初期環境を２つ用いた手書きの動作確認である。実行前に固定するため、ここには実サービスでの結果を記載しない。

同じ即時取得／遅延取得インターフェース、同じ完全応答キャッシュ、同じ６プログラムを与える。公開APIからアカウント情報と一覧を取得する費用も含める。最初の一覧ページの先頭３件を順に使い、不足・重複の場合は追加の探索をせず停止する。

| 順 | 確認する動作 | 予定API数 即時／遅延 | 遅延側の残存予約 |
|---|---|---:|---:|
| 1 | 公開認証情報、ログイン、一覧、対象のliked値、一覧の再取得 | 6／6 | 0 |
| 2 | 辞書に別名を残し、元の変数を削除して既知項目を読む | 1／0 | 1 |
| 3 | 次の実行で未知のgenreと完全値を読み、同じ完全応答を再利用する | 0／1 | 0 |
| 4 | 別対象の既知項目だけ読み、最後の参照を破棄する | 1／0 | 0 |
| 5 | さらに別対象の参照を残す | 1／0 | 1 |
| 6 | 公開APIでlike状態を反転し、保存値と新しい値の差を確認する | 2／3 | 0 |

予定値は実測ではない。各API上限12、全体24、初期化２回、Pythonコンテナ２個、各手書き６プログラムとクライアント初期化１回、各プログラム30秒、能動実行300秒。既存の有限な終了処理を別に計時する。モデル・独立評価・隠れたDB参照は０。全６出力の指紋を両側終了後に比べる。元の値・コード通信・認証情報は非公開に保存する。

公開ソースでSongLikeの変更がSong.like_countを更新することを確認した。既存の６読取API以外に変更の例外を追加しない。liked値を読むAPIも保守的にキャッシュを無効化するため、その後の一覧再取得も両側へ課す。サービス障害まで含む一般的な観測同値性は保証しない。

５境界検査と全1,358検査が通過。手書きの別プロセスでは６段階の値が両方式で一致し、likeの両方向、短い一覧での停止、取得応答不明、作用後の確認済み例外、途中停止を確認した。初回の模擬例外パケットは形式を誤り、不明として拒否された。失敗記録を残し、既存の型付き形式へ直した。実サービス・Docker・モデルの追試ではない。

通常の遅延取得やキャッシュを新規手法とせず、成功しても実課題の品質や全仕事費用の改善へ外挿しない。次の判断材料は、元情報の取得費と強い対照を含めて実サービス上でこの契約が動くかどうかである。
