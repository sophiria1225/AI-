# P120: 写真は成功と7.50%削減が両立、CSVの成功を失い全体の採用基準は未達

2026年10月25日. 既知４課題×２方式の全８条件を終了した. 必須欄による同時出力は、写真とCSVの両方で要約を生成し、履歴へ採用した. 写真は通常の別呼出し要約と同じく成功し、要約作成費用を含む総tokenが139,871から129,374へ10,497、約7.50%減少した. 一方、CSVはtoken予算の予約制約で未達となり、成功は別呼出し4/4に対し同時出力3/4だった. 全体の品質維持と新規性は未確立であり、事前の採用基準は未達のまま保持する.

## 必須欄の要約は実際に使われた

| 課題 | 別呼出し要約 | 必須欄の同時出力 |
|---|---|---|
| 写真 | 実行役14回後に生成し採用 | 15回目の行動応答で生成し、実行後に採用 |
| 精算 | 起動条件に達せず | 起動条件に達せず |
| 返金 | 起動条件に達せず | 起動条件に達せず |
| CSV | 実行役12回後に生成し採用 | 13回目の行動応答で生成し、実行後に採用 |

同時出力で要約を求めた２応答は、いずれも`checkpoint_structurally_valid`で、同一予算通知によるnative入力が短くなり採用された. 写真は17,829から9,806へ8,023 token減、CSVは21,999から11,110へ10,889 token減だった. 今回は要求２回、採用２回であり、P119の任意欄の要求２回、採用０回とは別の観測である. 要約本文の意味の完全性は検証したことにしない.

写真の要約付き応答はinput16,925、output1,219、CSVはinput18,196、output3,602 tokenで、共通出力上限4,096内だった. outputはコード、要約等を合わせた値であり、要約部分だけの生成tokenへ分離していない. 別呼出し方式の要約費用は写真18,455、CSV21,419、計39,874 tokenだった.

精算と返金では両方式とも起動条件に達していない. この２件の成功を要約の性能維持の実例に数えない. 要約が動いた２件のうち、写真は両方式成功、CSVは別呼出しだけ成功である.

## 写真で示せること

写真は成功を保ち、API呼出しも両方式102回のままで、モデル要求が17から16へ減った. 仕事時間は約754.969から708.729秒だった. 単発の観測であり、時間短縮の再現性や一般的な高速化は未確認である.

```text
同時出力 − 別呼出しの全仕事token
  = 実行役費用の増減 − 別呼出し要約の費用
  = 7,958 − 18,455
  = −10,497 token
```

同時出力側には追加指示、schema、要約出力と後続行動の費用があり、専用要約の18,455 tokenがそのまま節約されたわけではない. 次入力の8,023 token減も、仕事全体の10,497 token減とは異なる. 写真については、通常要約に対して成功と総token削減が両立した開発例として残す.

## CSVの短縮と未達を同時に残す

CSVの同時出力は要約を採用していたが、438,073 tokenで`token_reservation_limit`となった. 450,000 tokenを実際に使い切ったという意味ではなく、次の入力と必要な出力予約を共有予算へ収められず停止した. 生成中の使用量不明や、要約欄の欠落による停止ではない. この終端理由だけから、要約が必要情報を失った、あるいは残り予算を増やせば成功するとは断定しない.

別呼出しは440,461 tokenで成功した. 実行役だけなら同時出力438,073対別呼出し419,042で19,031 token多く、別要約21,419の差を含めても最終差は2,388だけである. 仕事時間も同時出力側が約125.401秒長い. 未完了の費用を、同じ成果物を得るための費用と同一視しない.
