# P40の全件分析と停止理由の確認

2026年10月22日、全８条件の終了前に準備。凍結した実行条件は変更しない。

最初に全件のAPI返却・使用量・独立評価の対応を照合する。通知ありでは、モデルへ実際に渡した通知が記録と一致し、API・呼出し・総トークンの残量と使用済み量が実行記録から再計算できることを調べる。全件の初回入力で推論キャッシュを再利用していないことも確認する。

結果は４課題それぞれの成否と費用を対応させる。成功件数の合計だけでは、成功した課題の入替えを見落とす。未完了の低費用を、仕事を完了する費用の削減と数えない。繰返しAPIには正当な確認や状態変更もあり、同一要求を一律に無駄とラベル付けしない。

停止理由がトークン予約上限の場合は、保存した未実行入力を同じ形式で再構成し、実行が終了して推論サーバーが空いてから入力長だけを再計数する。実行器は次の入力と最大4,096出力トークンを予約するため、残トークンが正でも次の呼出しが入るとは限らない。

`出力へ残せる量 = 残トークン − 次の入力長` を算出する。その値が正なら短い出力上限で開始できる可能性はあるが、有効なコードや完了回答が収まるとは分からない。この診断だけで「停止しなければ成功した」とは言わず、既存試行を再開しない。モデル生成・環境操作・最終評価を追加せず、入力計数の回数と時間を別に記録する。

上限を後から緩める案、停止した条件だけを成功するまで再実行する案は採らない。停止方針を変更する場合は、元の全結果を保存した上で別の固定比較とする。この診断や残量通知を、新規性の成立に置き換えない。
