# 順位付き取得の条件と既存方式との差

2026年10月22日夜。取得済み入力の省略に加え、取得そのものを避けられる公開条件を調べた。P54は通常対照の限定実装であり、順位付き検索や早期終了を新技術とはしない。

## 今回の公開API契約

インストール済みAppWorld 0.1.3.post1の公開API実装を読み、３ファイルのSHA-256をP54設定へ固定した。`spotify/apis.py` の `search_songs`（287〜440行）は検索・フィルター・順位・ページを `Song.retrieve_dicts` へ渡す。`model_lib.py` の `retrieve_records`（1860〜1948行）は、空の検索語なら全レコードの順位付けの後にページ分割する。検索語が非空なら検索のページ分割の後に順位付けする。`api_lib.py` の `sort_by_description`（969〜998行）は後者の注意を公開説明にも含める。

このため、`query=""`、フィルターなし、`sort_by="-like_count"` の契約だけで全体順位の停止を使う。対象は同じ公開SongカタログのIDで、`show_song` と検索結果の `song_id`、`like_count`、`title` を使用する。順序・同点・網羅を任意の別APIへ転用しない。

`retrieve_dicts`（1757〜1779行）と既定の `DictBy`（128〜130行）、`show_song`（443〜475行）の辞書化も確認した。検索側の既定のフィルター値は `filter_records`（1730〜1754行）と `filter_by_range_find_all_kwargs`（2036〜2065行）で無視値として除かれ、日付や評価の既定範囲を隠れた選択条件として残さない。実行器は検索語・追加フィルター・逆の順序への変更を実行前に拒否する。

固定した公式リポジトリ `42b5bcf3cd334fee33f0c37c02070a9f5807add5` の `src/appworld/apps/model_lib.py` は404で、同コミットのツリーにもこの３実装はなかった。そのためインストール済みファイルとそのコミットの同一性は主張しない。公開API実装の版とハッシュは実行機の取得元として分けて記録する。タスクDB・正解・公式デモの解法を読む作業ではない。

## 主要費用に効くか

同じ有限集合の最大値だけを返す通常集約を全対照へ用意すると、取得要求数を減らしてもLLMへ渡る結果は同じになる。したがってP54で測れるのはAPI試行・取得byte・制御と準備を含む時間であり、主要指標の全AI token削減ではない。通常の順位走査だけで同じなら、限定した先行取得の追加価値もない。

この点検の後、通常対照でも残る不要な呼出しや共有を特定できた場合に限り、新しい制御規則と主要比較を定義する。単に「条件付き」「契約付き」「適応的」と呼ぶことで、既存の探索・問合せ最適化との差が生まれたとは扱わない。
