# 開発と確認に使うシナリオを先に分ける

2026年10月21日、P17生成中・P18開始待ち。未閲覧の課題を使い切る前に、[選定規則](../configs/letter_scenario_reservation_v01.json)を保存した。公開のtrain課題IDだけで分け、要求文、難度、環境内容、解答、評価項目は読まない。

既閲覧８シナリオとP18の４シナリオを除く18シナリオをID順に並べ、先頭６を追加開発用、残り12を確認用に保留する。同じシナリオの別variantを別群に移さない。確認実験を行う場合のvariantは全て１に固定する。[IDと取得元ハッシュ](../reports/letter_scenario_reservation_20261021.json)。

この保留群は、方式、比較基準、モデル、seed、予算、主指標、失敗の扱い、集計方法を確定してから使用する。予備実験や失敗探しには使わない。結果を見て方式を調整した場合は、その群を再び未調整の確認結果とは呼ばない。主提案が成立しなければ、保留したままにする。

12件という数は残数と今週の実行枠を考えた準備上の区分であり、統計的検出力を保証する必要件数ではない。追加の反復は、独立したシナリオ数を増やさない。公式trainの内部での分離であり、公式testへの性能、アプリが変わった場合の転用、モデルの事前学習への未収録を示すものでもない。

全残数を開発に回す案は、方式を選んだ後に未調整で確認する材料がなくなるため採らない。要求文や難度を見て都合のよい確認群を選ぶ案も採らない。既存４課題の別variantだけを確認群にする案は、シナリオの重複を避けられないため採らない。今回の区分による新しいモデル呼び出しと環境操作は０。
