# P40：残予算通知の比較と、途中停止の記録

2026年10月22日12:56に開始し、13:31に事前規則でバッチ停止。**６条件を評価、１条件は使用量不明を伴って終了、１条件は未実行**となった。４課題の比較は未完遂であり、方式全体の優劣・品質維持・新規性は確立していない。

## 何を確かめたか

ハーネスはAPI・生成・トークン・時間の上限を管理していたが、過去15条件・102入力に明示的な残量通知はなかった。そこで、同じ４既知課題の８応答後から、全履歴・Python状態・アプリ状態をそろえ、残予算を毎回通知するかだけを変えた。通知は既存方式に相当する基準で、新提案ではない。

１条件16生成・120,000入出力token・480秒。APIは共通前半を含め写真整理160回、他は80回。全条件の初回は推論キャッシュの再利用を無効化し、実処理量も確認した。生成側へ独立評価を返さず、確認用12シナリオを開いていない。[事前計画](experiments/P40_budget_notification.md)。

全体は**44生成、既知579,759 token＋不明１回、後続253 API、実験用復元84 API**。不明分を０とは扱わない。完全に対応する３課題では通知なし231,709 token、通知あり301,840 tokenだが、これを予定した４課題の費用差へ代用しない。

## 観測と解釈

- 写真整理は通知ありで成功した。費用は4,966 tokenと42 API増えており、単純な費用削減ではない。
- 分担請求は両条件とも未達。通知ありのAPIは１回少ないが、tokenは13,488増えた。API回数だけを効率化の根拠にしない。
- 返金は両条件で成功したが、通知ありで生成が２回から５回、tokenが51,677増えた。通知は常に費用を下げる仕組みとは言えない。
- 書出の通知ありは、３回のPython処理の後、４回目の生成中に時間上限へ達した。後続の実APIは０件だった。通知なしが未実行なので、この課題で通知の有害性や優越性を比較できない。

いずれも既知課題・各条件１回の観測であり、普遍的な因果説明や非劣性の証明ではない。AIが内部で何を考えたかは自己説明から確定しない。

## 停止規則の追加点検

実行器は次の入力と最大4,096出力tokenを予約していた。停止した入力を保存状態から厳密に再構成し、終了後に入力長だけを３回再計数した。

| 条件 | 残token | 次の入力 | 出力へ残せる量 |
|---|---:|---:|---:|
| 写真整理・通知なし | 19,871 | 17,400 | 2,471 |
| 分担請求・通知なし | 20,078 | 16,200 | 3,878 |
| 分担請求・毎回通知 | 6,590 | 16,123 | 0 |

前２件は短い出力上限なら生成開始の計数条件を満たし得る。ただし、残時間も含めて仕事を完了できるかは未検証。入力計数は約0.113秒、追加生成・環境操作・独立評価は０。予算を延長した再試行は行っていない。[入力計数の証跡](../reports/P40_admission_stopped.json)。

固定の出力予約による停止と、必要な情報の欠落を分ける必要がある。残量に合わせた出力枠の調整も通常の制御候補であり、それだけを新規性にしない。今回の通知効果をこの停止規則と混ぜて説明せず、次の候補を選ぶ際の基準実装の確認事項とする。

## 監査と採否

全44入力の元会話・通知ハッシュ、既知使用量から計算したAPI／生成／token残量、実際の要求のキャッシュ設定を照合した。全７開始条件の初回で再利用なしを確認した。評価済み６件の独立評価、共通前半、予算、後始末を照合し、不明使用量の条件と未実行条件を別の状態として残した。[全予定条件の監査](../reports/P40_termination.json)。

準備済みの全８件用分析器・診断器は、未完遂のバッチを完全な比較として受け付けない。別の終了監査で全予定条件を列挙し、欠測を成功・失敗・費用０へ補完しない。[分析規則](P40_analysis_plan.md)。

通知をそのまま独自方式へ改称する案、成功した写真整理だけで採用する案、書出を予算延長して埋める案は採らない。単純通知で変わる行動と停止規則の影響を確認し、通常の対処でも残る失敗へ絞る。今回の終了監査と資料化を一区切りとし、主張の不足を保ったまま次の実装判断へ進む。
