# 識別子の実行欠落・順序・本文表示を分ける

2026-10-24. smolagentsの公開PR２件について、説明だけでなく変更コードと追加検査を読んだ. 取得した４ファイルは固定headのGit blob SHAと照合済み. いずれも確認時点でopen・未mergeで、配布済み修正や追試成功とは扱わない. 外部コードの実行・インストール・モデル呼出しは行っていない.

| 先行修正 | コード上の変更 | 追加検査で意図していること |
|---|---|---|
| [PR2684](https://github.com/huggingface/smolagents/pull/2684)、head `bd00a936e9f1929950e39a621e47b9b47628cbb8` | 空・重複IDだけに衝突しない代替IDを付け、呼出しを順序付きリストで保存する. 完了順とは別の呼出し位置で結果を対応付ける. | 空・重複・代替IDとの衝突・逆順の一意IDという７入力、および並列完了順が逆転する１例. 検査コードを読んだ範囲で、こちらでは実行していない. |
| [PR2999](https://github.com/huggingface/smolagents/pull/2999)、head `c4109249f8b5d0970c800debff5fd03708bed0c8` | 呼出しIDを変更せず保持し、操作と返答の内部対応を元の位置番号で扱う. メモリーも元のモデル出力順にする. | 一意ID・重複ID・None・単一呼出しの４入力で、全操作の実行と保存順を確認する意図. こちらでは実行していない. |

この２件を、単なる「IDの改名」ではなく実行取りこぼしと順序の既存修正として扱う. 前者は壊れたIDを補うが、後者はプロバイダのID自体を保存するため、同じ実装ではない.

## 本研究との重なり

| 経路・問題 | 現時点の根拠 | 本研究での扱い |
|---|---|---|
| 同じIDを辞書キーにして操作が上書きされる | 上記２PRが修正する既存の問題 | 操作の完全性をIDから分ける一般規則を新規としない. |
| IDでソートするとメモリーの順序が変わる | 上記２PRは呼出し位置の順序を残す | 一意IDであっても順序の問題が残る. 単純に「重複IDだけの先行修正」と狭く記述しない. |
| IDを含む呼出し辞書が通常の履歴本文へ入る | 既に確認した固定版のActionStep.to_messages等 | 実装上の経路確認. 外部モデルでIDを変えても同じ結果になる／ならないとは未測定. |
| 履歴の参照統一後、公開出力が一致しても有効なツール提出とは限らない | P84の保存１文脈とP94の実行、P98の閉じた全24実行 | 本実装で得た実証データ. 上記PRへの性能上の優位や、一般的な評価指標の新規性とはしない. |

２PRの変更はagents.pyと検査ファイルであり、memory.pyの本文表示を変更していない. そのことは本文中IDの完全な不変性を保証するという意味ではない. 「実行漏れを直す既存修正を入れれば、本研究が見た全ての入力表現差も解消する」とはこのソース確認から言えない.

レターで説明するなら、接続用IDの正当性、実行順序、モデルが読む本文、生成物の受理、実API、最終成果の各段階を区別した上で、具体的に測った段階だけを書く. 区別そのものを新方式とせず、現在の中心は既知４課題における実証に置く. 新しい方式の有効性は未確立.
