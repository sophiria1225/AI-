# 修復入力・残作業・再開の具体的な近接方式

2026年10月22日。小さい入力を使う修復と、作用を保った再開を候補にする前に、次の原典を確認した。下表は読解範囲での対応であり、各手法の再現や性能の横並び評価ではない。

| 原典・確認範囲 | 重なる具体的な処理 | 今回への判断 |
|---|---|---|
| [CausalRepair v1](https://arxiv.org/html/2608.10613v1)、§3.1–3.3、§4.2 | 失敗テストの静的依存と実行コードの動的依存を取り、構造を再構成した入力で修復。生成・検証・失敗返信を反復する | 入力を依存関係で絞ること自体は既出。今回の公開API拒否には同じ失敗テストがなく、意味が正しい操作かも別途残る。論文ページにPACMSE/ISSTAとDOI表記があるが、出版社側の独立照合は未実施 |
| [TRACE–FIX v1](https://arxiv.org/html/2610.25776v1)、§2、§3、§4.1–4.3 | 資源の版と未充足要求を照合し、診断・検査・修復・継続の費用を共通枠で扱う。局所解消後も同じ実行役を継続し最終成果を別評価する | 残作業、版付き証拠、修復用予算の予約だけを独自性としない。制御枠は抽象単位であり、総tokenとは別。1500軌跡は計画で、収集済みと扱わない |
| [Resume Contract v1](https://arxiv.org/html/2608.03836v1)、要旨・§II-D・§III-A/B | 前半状態からの継続、作用の重複防止、分岐、保存値の妥当性、消費、復旧決定の性質を区別する | 作用を二重実行しないという一般性質だけは新規性にならない。今回のAST１箇所一致は、これらの性質や安全な再開の証明ではない。形式モデル・実装は未検証 |

TRACE–FIXの[公開リポジトリREADME](https://github.com/toffeecat/tracedp/blob/main/README.md)も確認した。実行手順とデータ前提があり、元軌跡・課題・固定メニューは同梱しないと記載される。READMEの存在を全コード・データ・性能の再現へ拡張しない。正式採録は未確認。[出典記録](../reports/repair_context_sources_20261022.json)。

P48の実記録では、単なる引数削除が３件、観測された名前変更が１件、名前と型の変化が２件、未公開APIの拒否が４件だった。この分類は既存手法の反証でも、新しい手法の効果でもない。次の候補には、これらの違いを実行時にどう扱うか、通常の限定修復より何を保てるか、その費用を同じ入力情報と予算で示す必要がある。
