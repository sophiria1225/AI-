# 研究目的の確認：性能を維持しながら不要な情報処理と実行を減らす

2026年10月22日、ユーザーとの認識を再確認した。ハーネスを「AIに渡す情報、ツール実行、状態管理、検証、停止を制御する外側の仕組み」と捉える点は一致している。確認された主目的は、**AIオーケストレーションに伴う不要な情報取得・共有・呼び出し・実行をハーネスで削減し、タスクの性能を維持すること**である。

これは研究目的の新規変更ではない。[10月21日の技術的中核の再検討](technical_core_review_20261021.md)にも、同じモデルで品質条件を満たしながら仕事全体の入力・出力トークンを減らすと記録されている。朝資料が状態の引き継ぎを研究全体の目的として前面に置いたため、目的と手段の関係が伝わらなかった。資料と今後の判断は本目的へ対応づける。

## 背景・問題・目的をつなぐ

AIへ複数工程の仕事を任せるとき、情報取得、担当間の共有、ツール実行、検証は、正しい成果物を得るために必要になる。一方、同じ情報の繰り返し取得、関係の薄い情報の入力、重複した調査・実行、必要性が低い追加の呼び出しが、総費用を増やす可能性がある。これは調べるべき問題設定であり、すべての現行オーケストレーションが必ず性能と費用を増やすという実証済みの主張ではない。

量を一律に減らすと、必要な根拠や作業状態まで失い、誤りや再取得によって品質と総費用が悪化し得る。そこで、必要な情報・処理を維持し、不要な取得・共有・呼び出し・再実行を選択的に減らす制御を研究する。小さいモデルへの置換や単純な打ち切りを、ハーネスの構成効果と混同しない。

| 制御する場所 | 削減候補 | 性能のために残す必要があるもの |
|---|---|---|
| 情報取得 | 重複した検索・要求に関係しない取得 | 未取得の必要根拠、状態変化後の確認 |
| AIへ渡す情報・担当間通信 | 役割に不要な結果、同じ長い履歴の再入力 | 判断条件、対象・時刻・版、未完了作業 |
| 呼び出し・分担・実行 | 同じ処理の重複、再利用可能な処理の再実行 | 独立に必要な調査、正しい更新・操作 |
| 検証・停止 | 新しい判断につながらない検証や反復 | 必須の要件確認、操作後の整合確認 |

これは対象範囲の整理で、全項目を今月の論文で新規に実装する計画ではない。制御器・記憶整理・検証の追加費用も削減費用へ算入する。処理の回数が減っても、１回が長くなれば総費用は増え得る。

## 評価の中心

概念上は、ハーネス方式をHとして、次を目指す。

\[
\min_H\;\mathbb{E}[C_{\mathrm{total}}(H)]
\quad\text{subject to}\quad
Q(H)\geq Q(H_{\mathrm{ref}})-\delta.
\]

Qは要求を満たす最終タスク成功などの品質、基準方式は同じモデルと基本ツールを使う強い比較相手とする。δは勝手に設定して品質低下を許容する値ではない。品質維持を判定する許容差・評価単位・信頼区間・必要件数を、確認実験の前に定める。少数試行で成功件数が同じ、または差が有意でないというだけでは性能維持を証明しない。未知の全課題への保証でもない。

Cは当面、全AI呼び出しの入力＋出力トークンを主指標とする。取得・通信・制御・要約・検証・修復・失敗試行も含める。API回数、実時間、ピークメモリ、実際の推論負荷は別に報告し、異なる単位を無根拠に足し合わせない。キャッシュ済み入力と実際の計算・課金も区別する。全体実行の比較では前半から計上し、途中状態からの比較では共通前半、実験用の再構成、継続部分を区別する。

## 現在の実験は何を確かめるか

P31/P32は、研究全体のうち「入力を減らすと、再取得・再実行が増えて費用削減が打ち消されないか」を調べる局所的な比較である。会話の量とPython状態の保持を別々に変えている。担当は固定しており、複数担当の重複調査・通信を減らした効果も、関係のない情報を取得前に除外した効果も、まだ測っていない。

P31では保持条件で入力を直近だけへ減らすと、再開直後の入力は約半分になったが、後続総トークンは25.2%増え、成功が2/4から0/4へ減った。[全結果](P31_findings.md)。これは品質を保った削減ではなく、一律の入力削減が不適切だった開発事例である。目標そのものの不可能性を示す結果ではない。

P32は同じ４課題の８応答後からの全16実行を08:16 JSTに終了し、監査結果を公開した。[全件集計](../reports/P32_comparison.json)。時点が異なりseed列も異なるため、P31との単純な成功差を時点だけの効果としない。４課題・各条件１回という限界は残る。結果の意味と次の比較の採否は、全件の記録と費用を照合して決める。

## 新規性をどこへ置くか

「性能を保ってコストを削減する」は目的であり、それだけで新規性ではない。しかし、関連する圧縮・キャッシュ・共有・停止の技術があることは、この目的の研究余地がないという意味でもない。

狙う差分は、既存方式で生じる具体的な不要処理と、その発生条件を特定し、必要な処理を削らずに回避する観測・判断・更新規則を示すこと。その追加処理自身の費用も含めて、品質と総費用を既存方式と比較する。現時点で採用済みの独自方式と、その改善効果は未確立である。「新規性が出ないので履歴研究へ目的変更した」という判断は行っていない。

新規性確認では一般的な発想の重なりだけで全候補を除外せず、具体的な機能、必要な前提、判断時点、比較条件、費用、示せる成果を照合する。既存機能を使うことと、研究上の追加価値がないことを同一視しない。

## 次の実験を増やす前に書くこと

1. 全体費用のどの項目を減らす実験か。
2. その処理を不要と考える実行時の根拠は何か。
3. 必要な取得・実行・検証まで削らない仕組みは何か。
4. 同じモデル・情報アクセスで比較する通常方式は何か。
5. 性能維持と費用削減をどう判定し、何が出たら候補を見送るか。

重複要求や最終回答に使われなかった情報を、事後に自動で「不要」とラベル付けしない。状態変化後の再確認や、候補を棄却するための調査にも価値がある。正常な処理を省いた際の悪影響を含めて確かめる。
