# 記憶提出インターフェースの不整合と、比較基準の修正

2026年10月21日、P16の意味判定・採否判断の後で発見した。これは**本研究の基準実装の不備**であり、新しいLLMの失敗機構や提案技術として扱わない。旧結果・凍結ソース・判定ラベルは変更しない。

## 何が一致していなかったか

`LEDGER_TOOL`でモデルへ渡す`source_ids`のJSON定義は、文字列の配列と重複禁止だけを指定し、空配列を許していた。受取関数`validate_ledger`は出典が１件以上あることを別に要求する。さらに、要求文は入力にあるが、参照可能なIDは操作履歴のspanだけで、要求文そのものの参照IDが登録されていない。

そのため、これから行う完了宣言等に空の出典一覧を付けた場合、ツール定義に適合していても台帳全体が拒否された。モデルが`task`を出典にした場合も、与えた入力の参照なのに未登録として拒否された。任意の不存在IDを許すべきという意味ではなく、与える情報と参照可能なIDの対応が欠けていた。

以上は保存出力の検査結果であり、修正後に同じ内容が生成されること、修正で最終成功率が上がること、台帳生成の時間切れがなくなることを示していない。旧P14の2/4という結果は事実として残すが、一般的な台帳方式の弱さを支持する比較として使わない。

## 修正する範囲と採らない対処

今後の版では、台帳の出典配列に最低１件を明記し、その呼出しで使えるIDを列挙する。入力として与えた要求は専用ID`task`で参照できるようにし、「要求の根拠」と「操作実施の証拠」は同じでないことを記憶役へ明記する。構造の検査と意味の判定は引き続き分ける。

空出典を後から都合のよいspanへ付け替える案は採らない。出典を自動補完すると、もともと根拠がなかった記憶を根拠付きに見せるおそれがある。全てを無条件受理する案も採らない。生成済みの旧出力を新しい定義で再採用して、そのまま旧実験の成功に加算しない。

最初の確認では、P16で固定した記録通りの４入力を再利用し、旧インターフェースと整合する版を新しいseedで比較する。候補の新規性評価ではなく、基準実装の校正である。形式適合、出典の意味、費用を別々に確認し、全タスク実行での改善は、その後の別実験で測る。

本来、モデルへ宣言する定義と受取側の制約を先に一致させるべきだった。今後は同じ制約から両方を構築し、要求参照・空出典・未知ID・定義外状態を検査する。この修正自体をレターの独自機構に置き換えない。
