# 予算通知・制御に関する重複確認

2026年10月22日確認。公開原稿の本文と著者実装を対象とし、以下のarXiv版の正式採録は今回確認していない。性能数値を自分の環境へ移して保証しない。

| 原典と確認箇所 | 既に扱われていること | 今回の判断 |
|---|---|---|
| [Budget-Aware Tool Use Enables Effective Agent Scaling, v2](https://arxiv.org/html/2511.17006v2) §3.1, §4, C.2–C.3, G | 各段階の残予算通知、予算に応じた計画・検証、検索以外への適用。資源配分と高度な文脈管理を限界・展望として区別する。 | 残量通知や、コード・状態付き課題へ移したことを新規性にしない。P40はこの種の単純な対照を既存実行器へ追加する。 |
| [著者実装のBudget Tracker](https://github.com/google-research/budget-aware-agent/blob/main/src/agent_budget_tracker.py) budget_templateとループ末尾 | 使用済み／残りの検索・閲覧回数を会話へ加える実装。 | 原コードをコピーせず、本ハーネスの計数から通知する。費用単位、プロンプト、保持方法が違うため完全再現とは呼ばない。 |
| [BAGEN, v1](https://arxiv.org/html/2606.00198v1) §3, §6, §8 | 完了までの必要予算を区間で見積もる評価、実行可否・早期警告・較正、停止への利用。 | 既知の残量を知らせるP40と、未知の必要量を推定する問題を分ける。推定や失敗時停止も、それだけでは独自ではない。 |
| [Scores Are Not Decisions, v1](https://arxiv.org/html/2607.27083v1) §3–5 | 順位付けされた候補ツールのどこまでを取得するかを費用と利益で選ぶ。取得集合を最初のツール実行前に固定する定式化。 | ツールへのアクセス選択と、実行後の値取得・状態更新を区別する。「必要なものだけ取得」という一般表現を差分にしない。 |
| [Inference-Time Budget Control for LLM Search Agents, v1](https://arxiv.org/html/2605.05701v1) §3–4 | tokenとツール予算の下で取得・分解・回答確定を選び、最終回答を制御する。 | 残予算に応じた取得／停止の切替も広く既出。新しい制御を提案するなら、具体的な未解決の失敗と追加価値が必要。 |

この確認から「既存研究がすべて解決済み」とは言わない。一方、予算通知を追加しただけの結果を新提案へ改称しない。現在の目的は最終品質を保った総費用削減であり、そのための比較対象を強くする。P40を終えても、独自機構と十分な評価が自動的に成立するわけではない。
