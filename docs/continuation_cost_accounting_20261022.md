# 入力短縮が総費用へ届いたかを説明する集計

P33の全12件が終わる前に集計規則を用意する。実行条件は変更しない。追加のモデル生成・API・トークン計測は不要で、終了後の監査済み使用量だけを使う。

一試行の生成回数を n、最初の入力を I、各回の入力を I_j、全出力を O とすると、総トークン T は次の恒等式で表せる。

`T = n I + G + O`、ただし `G = Σ_j (I_j - I)`。

Gは初回からの入力増減の合計であり、入力が後で縮む場合も符号を維持する。内容の意味や不要性を示す量ではない。全履歴 a と候補 b の差を次の４項へ分ける。

| 集計項目 | 計算 |
|---|---|
| 初回の入力長の違い | `(n_a + n_b) / 2 × (I_b - I_a)` |
| 生成回数の違い | `(I_a + I_b) / 2 × (n_b - n_a)` |
| 後続入力の増減の違い | `G_b - G_a` |
| 出力の違い | `O_b - O_a` |

４項の合計は実測の `T_b - T_a` と一致する。積の差の対称な分解であり、新しい指標やアルゴリズムではない。単に初回の短縮率だけを示すより、後の呼出し・入力・出力が総費用をどう構成したか説明できるため採用する。どちらかの方式だけを展開の基準にして交差項を一方へ寄せない。

これらは同じ実行の４つの独立した介入効果ではない。履歴を変えると後続行動も変わるため、「入力をこれだけ減らせば必ずこの値を節約できる」とは言わない。キャッシュ済み入力も含む論理トークンで、実時間や推論計算量とも区別する。

不明使用量が１回でもある組では正確な差・内訳を出さず、未確定とする。その組を除いて４課題合計を成功した削減率のように表示しない。各課題の成否は別の対応表で確認する。

実装は `scripts/decompose_continuation_cost.py`。入力短縮と総費用増が同時に起きる例、費用不明、途中で入力が短くなる例、集計の不一致を制御検査に含める。実結果は全件監査後に `reports/P33_cost_decomposition.json` へ保存する。

同じ定義と比較条件を[方法節の部品](../papers/202610_letter/methods_output_views.tex)へ整理した。現在の投稿本文や提案技術ではなく、結果に依存しない方法の記述である。公式様式の４ページ組版は未完了のまま。

## 先行研究との関係
