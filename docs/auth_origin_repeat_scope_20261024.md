# 認証の由来を使う再観測の比較と、既存方式との境界

2026-10-24。P95の全399要求では同一要求34件、正常返答一致９件、返答変化21件だった。21件の変化は全てloginにあった。これは新しい制御の有効性ではなく、完全な引数一致だけで情報の再取得を調べる場合の観測範囲を確認する動機である。

公開実装を読むと、AppWorldの共通loginは資格情報を検査し、`last_logged_in`へ現在時刻を代入し、有効期限の秒数を乱数から選んで新しいtokenを作る。ただし当該関数内に`user.save()`はなく、この読取だけでDBの永続化を断定しない。fastapi-login側は期限をJWTへ格納する。共通logoutはtokenをblacklistへ加え、認証側はその集合とJWTを検査する。このため、古いtokenへの置換やloginの省略を、返答の一致や読取キャッシュの延長から許可しない。

次の点検は実行を置き換えず、すでに返った読取結果を３方法で分類する。第１は全引数一致、第２は対象４ APIの`access_token`だけを比較キーから除く通常対照、第３は、それ以前に成功した**同一login要求**から返ったtokenを同じ由来の群として比較する方法である。第３でもページ番号、検索条件、他の引数、返答内容を変えない。

由来の群は、同じアカウント・現在の権限・同じ環境状態の証明ではない。後から得たlogin返答を過去の要求へ適用せず、観測していないtokenをJWT本文の推測等で結び付けない。異なるlogin要求が同じtokenを返した場合は由来を曖昧として扱う。未知の作用後は由来による分類を抑制する。これは実行権限を付与する機構ではない。

通常対照の第２が同じ候補を得るなら、由来を追う実装件数を独自の改善としない。比較キーの正規化、出自追跡、繰り返し警告という一般技術は既存である。今回の既知群で追加の観測がなければ、この方向のモデル比較は始めない。通知候補が残っても、誤警告、通常対照、制御費込みの全仕事品質を別に測る必要がある。
