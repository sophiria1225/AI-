# P63：説明の表示と、公開名による呼出しを分けた通常基準

インストール済みAppWorld 0.1.3.post1の公開 `ApiCollection.load` と初期化経路を確認した。許可された公開APIは初期化時から名前で呼ぶための関数が作られ、説明の取得を呼出しの必須条件にはしていない。一方、この研究のPython接続は `NativeCatalog.decode` で説明未公開の名前も拒否していた。これは当研究の接続条件であり、標準APIの本来の制限ではない。

比較用の通常部品 [PublicNameCatalog](../scripts/public_name_catalog.py) を追加した。正確な名前が固定の公開catalogにあれば、説明をまだ表示していなくても従来の引数キー検査へ進む。値の変更、説明取得、再試行は追加しない。非公開・未登録名は拒否し、実際の実行は既存の認証、API・時間上限、完了後停止、作用不明後停止を通る。モデルとPythonに表示する定義は従来と同じ集合で、名前で呼べることと説明を見せたことを区別する。

元のNativeCatalog、以前のPython方式、native関数呼出しのスキーマsnapshotは変更していない。新部品は明示的に選ぶ比較用で、既存実験へ遡及して適用しない。[点検範囲](experiments/P63_public_name_scope.md)。

## 次の判断

この変更は標準的な公開名アクセスを比較用に用意するもので、新提案手法の核ではない。既知２課題で時刻を正しく取得できるか、その後の成否と仕事全体費用がどう変わるかは未測定。次は写真整理と電気代精算だけを対象に、両方式へ正しいインターフェース説明、同じモデル・情報アクセス・予算を与える有限の比較を別途固定する。結果が不利でも全条件を残す。

P55の全表示／省略比較は同じ追加制約の下で行われた局所比較として維持する。ただし、その結果を標準AppWorldや任意のコード実行基準へ一般化しない。P62で不足した公開時刻を、推測や公式成否から埋めることもしない。必要な情報と品質を保ち、仕事全体の費用を減らす研究目的へ向け、通常基準の接続に由来する負担を先に切り分ける。
