# P22待機中の比較基準の点検

2026年10月21日20時台。P22の途中の要求・操作・回答本文は読まず、固定した一般実装と原典を確認した。実行条件の変更、追加モデル呼出し、確認用12シナリオの閲覧は行っていない。

## 予算制約と、予算の提示は別だった

P22で凍結した `run_native_appworld.py` は、全履歴を `Inference.call` へ渡す。予算は `run_context_comparison.py` と送信器で制限するが、システム指示や各応答前の入力に残りAPI数・総トークンを追加しない。モデルが操作を数える可能性はあっても、実行器から正確な残量が通知される構成ではない。

このため、予算停止から直ちに新しい記憶や調整機構の必要性を導かない。今後、予算停止を対象にする場合の最小の対照は、同じ上限のまま残量を明示する方式である。通知自体の入力費用も合算する。数値を通知することと、十分な資源を与えることは別なので、合理的な上限による感度確認も区別する。

[Budget-Aware Tool-Use / BATS](https://arxiv.org/html/2511.17006v1)の3.1節は残予算の逐次提示を、4節は予算に応じた計画・検証を扱う。今回は本文の原理を比較対象として確認した。画像内の全プロンプトの転記、原実装の再現、同じ性能の測定は行っていない。単なる予算表示を新提案やBATS完全再現とは呼ばない。

## 情報の取得・提示・利用を分ける分析にも近接研究がある

[Same Simulation, Different Evidence](https://arxiv.org/html/2610.26836v1)は、科学計算の出力について、生成された値、モデルに届いた値、回答を分けて調べる。保存した計算状態を揃えた継続比較と、出力の読取先への介入を含む。したがって、取得後の失敗を区別したことや、同じ途中状態から表示を変えたことだけを独自の技術とはしない。

対象は決定的なシミュレーターと選択式回答である。今回のアプリ状態更新・全対象への操作と同じ問題を解いた論文と断定もしない。本文2.3節、4〜5節、付録Dの範囲を確認し、結果を再現したわけではない。

[DeRef](https://arxiv.org/html/2610.18497v1)の4節は、候補引数を見ない別のモデルが全履歴から参照値を導出し、引数判定器へ渡す方式である。候補と独立に期待値を作る一般案も既知の対照になる。一方、引数の判定精度と、その判定を実行へ戻した最終タスク成功を同一視しない。

３件とも今回確認した著者公開版の範囲で扱う。正式採録と性能再現は未確認。[URL・取得ハッシュ・確認範囲](../reports/budget_and_evidence_sources_20261021.json)。

## 次の判断へどう使うか

P22を全件完了・監査してから、公開観測で裏付けられる問題を選ぶ。予算停止なら残量の提示、転記・集計なら通常の計算、検査器の根拠不足なら参照の導出を、まず適切な単純対照として検討する。これらを一度に追加して差を説明不能にする案は採らない。

既存の一般原理があることだけで、具体的な更新規則の研究余地まで否定しない。追加の機構を提案するには、どの前提が成り立たず、何を変更すると既存対照より改善するかを一つに絞る。現在はその実測前であり、この点検を新規性の成立や投稿原稿完成として数えない。
