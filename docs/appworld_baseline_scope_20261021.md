# 全履歴基準の範囲と、公式エージェントとの差

2026年10月21日、P22実行中。固定した実験条件を変更せず、終了後の解釈のために公式の実装・設定を照合した。実験データ、デモの中身、正解、評価項目は追加で読んでいない。

## 何を確認したか

公式リポジトリのコミット `42b5bcf3cd334fee33f0c37c02070a9f5807add5` に固定し、基底Agent、Function Calling、ReAct Codeの実装と、設定例１件、READMEを読んだ。READMEにあった２つの旧ソースリンクは404だった。ソース一覧で現行の `experiments/code/simplified/` を確認し、同じ原著者リポジトリのファイルを取得した。他リポジトリへのGit操作や書込みは行っていない。[取得元とハッシュ](../reports/appworld_baseline_scope_sources_20261021.json)。

実験機に導入したAppWorld 0.1.3.post1の環境ソースでは、既定の `max_interactions` と `max_api_calls_per_interaction` は各1,000だった。前者は環境とのインタラクション数、後者は１インタラクション内のAPI数である。本研究の接続は環境側のインタラクションを500までとし、その外側で１課題全体80 APIという独自の予算を課す。これをAppWorld公式の難しさや標準予算とは呼ばない。最新リポジトリと導入版を同一の版と扱わない。

## 結果をどう解釈するか

P18の写真移動でAPI上限に達したことは、今回の予算下の失敗である。ハーネスの上限で未送信になった要求を、モデルが対象を忘れた証拠にしない。特定の「１対象１読取＋１移動」の手順では42対象に84 APIが必要でも、別の手順を含む真の最小回数を証明したことにはならない。

全履歴基準は、本研究内で記憶削減方式と比べるための対照である。「現在可能な最強の単一エージェント」「通常のコード実行でも解けない」とは解釈しない。P20/P21も、取得済み情報からの書出だけの診断であり、環境APIを含むCodeAct型の全体実行ではない。

追加のハーネス機構を提案する場合、少なくとも、失敗が小さいAPI上限だけで起きていないか、通常の計算・再取得でも解決できないかを切り分ける必要がある。P22を途中変更せず全６件を終え、上限による未完了と、上限未到達での誤完了を分けてから、必要な感度比較を別計画にする。上限を増やした成功を新規方式の効果に数えない。

## 取得済み観測の計算と、公式のコード実行を区別する

同日、導入済み0.1.3.post1の `environment.execute` と `SafetyGuard` を追加確認した。公式の実行関数はコードセルを動かし、出力を返す。今回の任意の `compute_data` は公開済み観測の計算だけを行い、生成コードから環境APIを呼ぶ機能は持たない。後者を追加しただけで、公式コード型の制御ループ・探索能力まで再現したとしない。

導入済みソースには構文検査と一部関数の無効化があるが、この読取を隔離の実測や完全な安全監査とは扱わない。追加の生成コード・課題実行は０。読んだ関数とソースハッシュを出典記録へ追加した。P22後に探索・操作ループの問題が残った場合は、通常計算だけで十分な対照かを改めて判断する。

## デモと確認用課題の扱い

公式設定に記載されたデモの参照IDには、今回の開発群と保留した確認群のIDが含まれていた。参照IDを見ただけで要求文を読んだことにはしないが、そのデモ本文を取り込めば保留群の分離を損なう可能性がある。そのため、今回取得したのは設定と一般実装だけで、デモJSON・プロンプトテンプレート内の例・公式の回答軌跡は読まず、エージェントへ渡していない。確認用12件の要求未閲覧は維持する。

予測器やデモの追加は、元基準とは情報条件を変える。公式構成をそのまま採用するだけで公平な比較になるとは決めず、情報・モデル・ツール・予算の差を記録する。現行のP22の追加モデル呼出しや課題選定を、この照合に応じて変更していない。
