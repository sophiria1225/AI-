# 同じ状態の未取得参照で取得予約を共有する別版

2026年10月25日. 元の遅延読取実装には、同じ対象を同じ状態で２回読むと、それぞれが取得予約を持つ経路があった. 一方、即時方式は１回目に得た完全応答を２回目に再利用できる. 取得予定が重複しているために、遅延側だけが予算不足になり得る.

手書きのAPI模型で、一覧取得後に同じ曲への２つの参照を作る条件を検査した. 上限２回では、元の遅延版は一覧に１回、未取得値に予約１回を使い、２つ目の参照を拒否する. 即時方式は一覧と完全取得の２回で両参照を作れる. 余裕のある上限でも、両参照を完全に読むと元の遅延版は一覧＋詳細２回、即時方式は一覧＋詳細１回になる. これは実課題や新たなAppWorld実行の結果ではなく、実装の経路を再現する単体検査である.

[別版のhostとadapter](../scripts/coalesced_contract_read_views.py)は、課題scope、状態epoch、公開API名と全引数が一致し、同じ部分応答契約が成立する未取得参照だけを束ねる. 元ファイル、既存の結果、P101/P102/P104の固定ソースは変更しない. 進行中の実験にも導入しない.

## ライフサイクル

参照名は個別に発行するが、host内の未取得値と予約を共有する. 片方だけが解放されても予約は残る. 最後の参照が解放された場合だけ取り消す. どの参照からでも未知項目を読むと１回だけ取得し、全ての参照へ同じ時点の値を用意する. クライアントへ返す値はコピーし、読み出した入れ子の値を変更しても別参照を書き換えない既存の挙動を保つ.

通常のAPI呼出しが同じ状態の完全応答を既に得た場合、その実送信費用は残したうえで、満たされた予約を解除する. 次の操作を予算判定する前に解除し、既に取得できた値のために操作を断らない. 予約付き取得の途中で、その予約を二度消費・取消しすることは避ける.

共有予算は引き続き `S + D <= B`. ここでDは参照名の個数でなく、未取得の異なる取得義務の個数になる. 別名を作った数を節約API数としない. 共有対象を探すhost内処理、制御要求、コピー等の費用は、将来の実測では実行時間・通信量に含める必要がある.

状態変更の前に生きた取得義務を満たす規則、登録された公開APIの検証、課題・状態の分離は維持する. 異なる対象やepochは共有しない. 不正な制御要求を受けただけでは予約を消さない. 契約違反や制御返答紛失時の停止と再試行なしも維持する. 失われた返答に対応する参照は、使用されなかったと推測して取り消さない.

## 検査と採否

[15検査](../tests/test_coalesced_contract_read_views.py)は、上の予算反例、複数参照の完全取得、片方・最後の解放、更新前の旧値保持、別対象・別課題、公開API権限、制御要求の不正、既存の完全応答キャッシュ、後続操作前の予約解除、契約違反、返答紛失、プログラム境界、持続実行adapterへの接続を扱う. APIは手書きの模型であり、生成コード・実サービス・課題DB・評価器を使わない. adapterの検査は手書きコードを検査専用subprocessへ実行するもので、追加のモデル生成や元の保存コード実行ではない.

初回は別対象のfixture観測に認証引数を付け忘れ、部分応答契約が成立せず１検査が失敗した. 失敗ログを保持し、fixtureを公開契約に合わせた. 実装の対象を広げて検査を通したわけではない.

この変更は通常の重複取得の共有と予約管理の改善であり、新規性の主張には使わない. 異なる多数の対象の予約、実課題での取得回避の少なさ、API件数とLLM tokenの違いは解決していない. P104は元版の保存６段階を固定しており、本変更の効果測定には転用しない. この別版を実課題へ入れるには、適用箇所と強い通常対照、全費用・品質の有限な比較を別に固定する必要がある.
