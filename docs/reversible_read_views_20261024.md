# 変更内容を確認できる場合の、古い読取値の遅延復元

これはR120の実行器の追加試作である。新規手法や課題品質の実証ではない。P89・P90で現在の曲一覧契約の適用候補が０だった結果はそのまま保持する。この追加機構だけでは、必要な部分情報が事前にない問題は解決しない。

## 変更前の完全取得を遅らせる条件

元の方式は、生きた参照を後でも正しく読めるように、状態変更の直前に全応答を取得していた。今回の試作は、対象の特定の非負整数項目だけが１増減し、それ以外の読取値が変化せず、変更後も元の読取が成功するという契約を、呼出し側が明示した場合に限定する。成功応答も契約の期待値と一致しなければならない。

参照を作った後の確定した変更を参照ごとに保持する。後で完全値を読むと、現時点の応答を取得し、変更を逆順で戻して元時点の値を返す。最後の参照がその前に消えた場合は、完全取得とその予約を取り消す。原APIの状態を実際に巻き戻す操作は行わない。

例えば元時点の件数を未取得のまま、確認できる変更で１増やし、後から旧参照の件数を読むなら、現時点の件数から１を引く。変更後に新しく取得した参照は現時点の値を返す。新旧の値を同じキャッシュ項目として保存しない。

`S + D <= B` の共有API予算は維持する。変更操作は通常枠を使い、古い完全値の取得予約を流用しない。履歴は１参照につき既定32変更、設定可能範囲1〜128。上限に届いたら次の変更前に完全取得する。未対応操作も元の保守的な取得に戻る。確認済み例外・不明応答・契約に一致しない応答では実際の費用と残る予約を保持して停止し、自動再試行しない。

既定の作用判定器は全て不許可である。公開実装の一部を読んだことやHTTPメソッド名から、この契約が自動で成立するとは扱わない。固定されたSpotifyの `SongLike._post_change` は単純な加算でなく件数の再集計を保存する。旧件数が関連レコード数と整合しているという前提も要る。成功メッセージだけで整数差分を認定しない。現時点では実AppWorldの変更APIにこの例外を有効化していない。外部の同時更新、読取失敗、APIの隠れた変更作用に対する一般保証もない。

## 比較でそろえた通常の再利用

現時点の完全応答がすでにあれば、保守的取得と復元方式の両方で再利用する。予約は実送信として計上せずに解除する。これにより、同じ対象を指す複数の遅延参照があるだけで、弱い比較側に余分なAPIを使わせることを避ける。

完全応答のキャッシュには取得した現在値だけを入れる。復元した旧値は、その旧参照にだけ保存する。追加したのは [別の実行器](../scripts/reversible_read_views.py) で、P89・P90や実サービス確認に使った元の実装は変更していない。

## 検査結果と限界

新規18検査を含む全1,394検査が成功した。４操作×長さ４の全256列を、独立した即時スナップショットの期待値と照合した。保守的取得と復元方式で参照値・最後の世界状態が一致し、この有限集合では復元方式のAPI数は保守的取得以下だった。最後に生きた参照を完全な辞書へ変換して比較したため、未読部分を捨てて一致としたものではない。

別名、異なる時点の複数参照、増減の両方向、履歴上限、同一完全応答の再利用、共有予算拒否、既知例外、不明応答、制御返答の紛失、復元値の型不一致も検査した。すべて手書きの世界であり、256列は独立課題数や現実の発生頻度ではない。実AppWorld API・モデル・評価器・既存の保存コードの実行は０。実課題の成功・token・時間削減は測っていない。

誤った作用契約を与える反例も残した。旧件数17を内部の再集計で5に更新した処理を「１増加」と誤認すると、後から返す旧値は4となり、既知部分との一致確認だけでは検出できない。全256列の一致は、正しい作用契約の前提を外した保証ではない。

## 先行研究との境界

変更履歴から過去を再構成する原理は既出である。[Koloniariら、On Graph Deltas for Historical Queries、§2.1–2.2](https://arxiv.org/pdf/1302.5549)は完全な変更履歴と逆操作による過去の復元、途中のスナップショット、復元費用を扱う。今回読んだ範囲は要旨・導入・§2.1–2.2であり、実装や実験を再現したわけではない。

更新時の維持を遅らせ、参照に必要な時点で整合させる原理も既出である。[Zhouら、Lazy Maintenance of Materialized Views、要旨・§1–2.1](https://www.vldb.org/conf/2007/papers/research/p231-zhou.pdf)は版管理を利用した遅延維持を扱う。今回の旧時点のAPI値と同じ対象ではないが、遅延・版・必要な情報の保持だけを独自性とはしない。

今の追加実装は、これらの原理を明示的な参照・型付き応答・共有予約へ接続する条件付きの実行機構である。新規性の主張には、通常の版管理・完全キャッシュ・既存の項目読取でも残る問題と、実課題での全費用への効果がさらに必要になる。P88の失敗やP90の適用範囲を、この合成検査で補ったとは扱わない。
