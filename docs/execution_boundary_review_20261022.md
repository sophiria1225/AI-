# 実行単位・コード処理の追加原典確認

2026年10月22日。P27の全件終了前に、候補の一般構想と先行研究の重なりを確認した。P27の途中本文を見て方式を変更していない。原典の取得記録と、実際に読んだ範囲は[出典一覧](../reports/execution_boundary_sources_20261022.json)に分けて残す。

| 原典 | 今回確認できた範囲 | この研究への含意 |
|---|---|---|
| [ReCode v4](https://arxiv.org/html/2510.23564v4) | 2節、3.1〜3.2など。計画を未実装関数として表し、実行中に再帰的に具体化する | 「コードにして処理粒度を動的に変える」だけを新規性にはできない。P27は再帰的な計画展開を実装していない |
| [Latency-Aware Orchestration v1](https://arxiv.org/html/2609.03335v1) | 1〜2節、3.1〜3.3など。論理的な依存と結果を維持し、同じモデルの連続呼出しの物理的実行・配置をまとめる | 当初案の「未完了作業の判断・更新責任の移管」と同一とは限らない。ただしモデルをまとめて実行する費用最適化も既存の対象 |
| [Autonomous Topology Mutation v1](https://arxiv.org/abs/2607.20488) | 3.3〜3.4、4節、限界も追加確認。負荷で分割し、５課題のshadow実行後に切り替える | 動的な担当生成や状態移管の追加だけでは差にならない。主評価は模擬ツール、実ツールは５例と著者が限定。実装再現や全条件の等価性は未確認 |
| [Where Does Exactly-Once Live? v1](https://arxiv.org/html/2609.29095v1) | 導入、3〜5節、6.1〜6.3。応答消失等を模擬し、再読とツール契約の保護範囲を比較する | 再試行を止める、実行済み操作を記録する、契約に応じて処理するだけを独自性にしない |

ここでの採否は「使ってはいけない技術」という意味ではない。通常の比較相手に備えるべき機能と、独自に追加する規則を混ぜないための判断である。正式掲載先の確認と再現実験は、この表では完了していない。

P27終了後は、全４件の成否と費用に加え、Pythonを実行できなかった呼出し、プログラム内の例外、APIを送信した後の例外、出力上限を区別する。一つの例外が起きても、その前の操作が取り消されたとは判断しない。例外の本文やプログラムは公開せず、種類と回数だけを集計する。この解析器自体は診断用の通常実装であり、独自の制御方式ではない。

次の方式を選ぶ際は、実際の残存失敗に対応することを条件にする。途中結果から課題を追加・削除する案、上記機能に新しい名称だけを付ける案、実装不備をCodeAct全体の限界とする案は採らない。
