# P104: １ APIの取得回避は、大きな入力削減には直結しなかった

終了済みの手書き６段階を用い、即時/遅延×２表示×６段階後の全24入力を一度計数した. ４描画処理が全て終了し、decode、モデル生成、新規API、保存コード実行、課題評価は０. 全体4.500秒、標本化した最大RSSは157,859,840 byteだった.

通常の管理情報を含む入力では、遅延−即時の差が順に `0, -20, 0, -20, -40, -18` tokenだった. 第３段階は長さが同じでも入力列自体は異なる. API回数、受領参照、登録順のIDを除く計測用表示では、全６段階の本文、prompt、token列が一致し、差は全て０だった. 本文に由来する削減はこの構成ではなかった.

元の実APIは即時11対遅延10で、標準出力は全６段階で一致した. 今回の結果は、API本文がもともとPython側に保持され、印字されない値はLLMへ流れない入力経路に対応する. APIを省略した分の返却本文が、そのままLLM入力から消えるという解釈は採らない. 差があったのは、今回除去した管理情報の範囲である.

これは現在の会話形式、共通説明、手書き提出から作った事後の比較用入力で、過去に送信されたLLM要求の復元や実エージェントの生成履歴ではない. 各時点の予算通知も再構成していない. 第６段階後は終端の表示確認で、実際の次の呼出しではない. 全24入力を合計して実課題の使用量としたり、計測用表示を品質保持済みの削減方式としたりしない.

取得費、プロトコルの入力規模、LLM使用量を分けること自体も先行範囲に含まれる. ProMCPは通信段階別の計数と、ツール返却を文脈に含めるクライアントの選択を扱っている. 今回は原著の該当節と制限を確認した範囲で、外部コードや実験は再現していない. [原著](https://aclanthology.org/2026.findings-acl.1967/)／[読取範囲](../reports/P104_protocol_footprint_prior_scope_20261025.json).

この結果からの判断は、現行の遅延取得を大きなLLMトークン削減手法として打ち出す根拠がない、ということ. API取得の回避と、入力や後続生成を減らす制御は分けて評価する. 同じ未取得参照を共有する実装の接続確認を準備しているが、それも新規性や実課題改善の証明ではない. 原稿の逐次改訂は保留する.
