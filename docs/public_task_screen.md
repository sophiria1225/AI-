# 次の開発課題を選ぶための公開情報調査

2026年10月20日。P3の2開発課題は比較基盤の観察に使う。特に15380の局所修正を、大規模で相互依存する仕事の実証には使わない。そこで、次の課題の適性を公開問題文から調べる。これは本実験の課題確定でも、新しいモデル実験でもない。

## 問題文を読む前に固定する範囲

SWE-bench Verifiedの固定版`c104f840cc67f8b6eec6f759ebc8b2693d585d4a`から、既存の公開7列だけを使う。入力ファイルと閲覧台帳のSHAを[計画](../configs/public_task_screen_v01.json)へ固定する。正解パッチ、独立評価の追加テスト、既存モデルの成績は読み込まない。

調査枠を6リポジトリ×2課題に制限する。対象はmatplotlib、xarray、pytest、scikit-learn、Sphinx、SymPy。既に実行したDjango以外へ観察範囲を広げ、異なるソフトウェア群を含めるためである。これはソフトウェア以外への転用評価ではない。

Astropyでは過去に一部の正解を研究者が閲覧しているため、初回枠に含めない。Flask、Seaborn、Requests、Pylintなどは、調査量を限定するため今回は後順位にする。これらの適性や品質が劣ると判断したわけではない。

各リポジトリ内では固定seed、データ版、課題IDからSHA-256を計算し、その順の先頭2件を選ぶ。既知の開発・正解閲覧課題は除外する。問題文の長さ、正解パッチのファイル数、モデルの成功率で候補を順位付けしない。読む候補のID・基点コミット・問題文SHAを先に保存してから内容を確認する。

## 読んだ後の分類

以下の項目を課題ごとに記録する。本文だけで不明な項目を「依存あり」と補わない。

- 公開要求が結びつけている機能・条件・成果物。
- 複数の判断を整合させる必要があると考える具体的な記述。
- 局所的な修正で済む可能性と、まだ確認できないこと。
- 問題文に具体的な修正案や完成した解決策が含まれるか。
- 公開の基点コードで次に確認すべき箇所。
- 継続調査、局所対照、保留のどれにするかと、その理由。

「複数の単語やファイルが登場する」「問題文が長い」ことだけで作業間依存と判定しない。問題文に依存候補があっても、実コードの確認前には主実験へ採用しない。完成修正の例がある課題は、今回の依存探索では後順位にする。再現コードの掲載だけを、完成した解決策と同一視しない。

全12候補の採否と理由を残す。適切な候補が見つからなければ、その結果を保持して追加調査の範囲を別計画にする。モデルで解けた課題だけへ差し替えたり、少数の調査を全500件の代表性の証拠にしたりしない。
