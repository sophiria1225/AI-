# 未知引数の修復で、元の値と変更範囲を固定する部品

P48では、実際の後続要求に名前変更だけのもの、型や同名値も変わるもの、未取得の契約が必要なものが混在した。そこで、小さい修復入力を試す前に、何を変更できるかを実装で明示する。[部品](../scripts/request_repair_binding.py)は純粋な候補組立てだけを行い、モデル生成・API送信・Python再開にはまだ接続しない。

入力は、送信していないと確定した未知引数拒否、元の要求、その時点で公開済みの原契約。元の引数値はホストに保持し、修復用の入力には未知の引数名と型、既存の引数名、移動先候補の公開仕様を渡す。要求の意味や値を隠しただけで正しい対応が決まるとは仮定せず、判断不能なら辞退を返す。

提案できる変更は、未知引数名から未使用の公開引数名への１対１対応だけ。既存の公開引数名と値は保持し、値変換・API変更・新しい値の生成を許さない。引数を削除できるのは原契約の引数集合が空の場合だけとする。宛先は限定したスカラー型・enumの範囲で照合し、未対応の制約は拒否する。通常の最終検証を省略する機能ではない。

元の値と宛先制約から二部グラフを作り、全未知引数を重複なく割り当てられるかも点検する。これは通常の最大マッチングであり、候補が存在しても意味的に正しい対応とは限らない。存在しない場合に局所修復の生成を省く制御へ使える候補だが、現時点では生成や実行へ接続していない。

要求または原契約が変わった場合、すでに送信した場合、作用が不明な場合は候補を組み立てない。１つの部品インスタンスで提案を受けるのは１回だけ。これは同じプロセス内の候補組立ての性質で、永続化・分散実行・外部作用のexactly-once保証ではない。

## 比較する意味と限界

[SchemaShield-Lite](https://arxiv.org/html/2610.23342v1)は、課題・元の要求・公開契約・検査エラーから、選んだAPIに制限して要求全体を修復する。原典§3–5と固定実装の修復プロンプト・検査・対象選択を確認した。単に別入力で修復することや、API名を固定することは独自性にしない。

今回の部品では元の値と既存の公開引数をホスト側で保持する。その分、意味の判断や型変換を要する修復には対応しない。名前を対応させても目的に合うかは未検証で、型の一致を意味保存と呼ばない。既存の最小修正や拘束付き編集との関係、修復できる範囲の縮小、通常継続へ戻る費用も比較する必要がある。

次に必要なのは合成例で境界を検査し、全保存拒否で適用・辞退範囲を点検すること。後続の正しい要求から作った対応表を、実行時に使える方式として評価しない。モデル実験を行う場合は別に入力・予算・通常の限定修復との対照・合流後の最終品質を固定する。この部品の完成だけで、独自性や品質を維持した総費用削減は確立しない。
