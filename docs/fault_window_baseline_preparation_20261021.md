# 再取得した観測を優先保持する単純対照の準備

2026年10月21日。P18の実行中に、既に終了したP12の観察から準備した。**独自方式の採用や、新しい性能実験の結果ではない。** P18の途中の本文・操作列や、保留12シナリオは入力にしていない。

P12課題３には、削除された観測と同じ内容を取り直した９組がある。通常の保持だけでこの往復が解消する可能性が残るため、費用のかかる記憶生成や新機構を先に足すより、同じ履歴予算で比べられる対照を用意する。[P12の全結果](P12_findings.md)。

既存の[Pichay 3.4〜3.5節](https://arxiv.org/html/2603.09023v1#S3.S4)に、削除後の再要求を検出して同じ内容を保持し、変更された内容の保持を解除する原理がある。本実装は、その原理をAPI観測・既存会話・4,096トークンの履歴枠へ合わせた単純な対照で、原論文の完全再現ではない。公開原稿として扱い、採録済みとは表示しない。[原典確認記録](../reports/baseline_scope_sources_20261021.json)。

## 適用する規則

1. 実際に送信した公開APIの名前とJSON引数が同じで、前の結果がその生成入力から外れ、再取得結果が完全一致した場合に、最新の観測IDを保持候補へ入れる。同一生成内の重複、未送信要求、作用不明をこの判定へ混ぜない。
2. 同じ要求の結果が変わったら、その要求の優先保持を解除する。結果が変わらなかったことから、再確認が不要だった、将来も有効だ、と推論しない。APIの実行は省略せず、古い結果を新しいAPI応答として返さない。
3. P12と同じ全履歴アーカイブを使い、全履歴が枠内なら入力を変えない。超過時は最新の応答と対応する全結果を残し、次に保持候補を直近の要求順に収め、残枠へ直近履歴を入れる。要求と結果を切り離さない。
4. 保持候補のために予算を増やさない。収まらない候補は外し、そのIDを記録する。最新の一応答だけで枠を超える場合は、P12と同じ例外として超過を記録する。固定タスク・API仕様・実入力全体の費用は別に計上する。

検出器と選択器は[実装](../scripts/native_fault_window.py)へ分離した。API引数や観測値、その値を照合するためのハッシュは出力しない。公開する診断は観測ID・公開API名・件数だけ。最終評価・正解一覧・将来の操作は使わない。

## 検証できたことと、まだ分からないこと

14個の制御検査で、要求・結果の対の保持、同じ予算内の候補競合、予算超過の明示、同一応答の重複除外、変化した観測の解除、秘密値を含めない出力、未知作用の拒否を確認した。全体336検査も合格。これらは実装検査であり、エージェントの品質改善ではない。

終了済みP12全４件の記録へ検出だけを適用した。件数は順に0、0、9、0で、課題３の最後に残る候補は時刻取得とアカウント情報取得の２種類だった。元記録は変更していない。これは現在の観測との整合確認で、保持すると成功することや、９回の要求を省けることを示さない。[検出結果と出典ハッシュ](../reports/fault_window_P12_detection_20261021.json)。

まだ実行器へ接続せず、モデル生成・API実行・トークナイザー要求の追加は０。P18を全件分析した後、次の実験の優先順位を決める。保持する単位が大きすぎて枠へ入らない場合、検出できても保持できない。語義の近い要求、引数の異なる同一対象、別操作による状態の失効まで検出できる方式ではない。

## 今は採らない代案

- 再取得した内容を全て無制限に保持する：履歴枠が増えた効果と分離できない。
- 同じAPIなら再実行を省く：状態が変わり得るため、観測保持との比較ではなく実行方式の変更になる。
- 認証APIだけを手で特別扱いする：P12の一課題に合わせた対応になる。まず公開API共通の規則で確かめる。
- これを新規アルゴリズムとして主論文にする：保持原理は既出。対照で十分なら、その点を正直に記録する。

変数・ループを使うコード型も通常の対照候補である。[CodeAct](https://arxiv.org/html/2402.01030v4#S2.S3)の2.1〜2.4節では、コードの制御・データフローを使う行動を扱う。今回の関数呼出し型へループを加えるだけでは独自性にならない。コード型を実装する場合は実際の全API要求を数え、隔離された実行器で比較する。今回、その接続は実装していない。

## 追加確認：丸ごとの履歴削除と観測だけの省略を区別

同日、[The Complexity Trap v3](https://arxiv.org/html/2508.21433v3#S3.SS1)の3.1、5.1〜5.3、6節を確認した。観測だけを省略し、行動と説明を残す方式や、その後に要約を組み合わせる方式を扱う。P12と今回準備した対照は古い応答・結果を一組として選ぶため、この方式の再現ではない。操作の引数に既に残った情報が後の作業に役立つ可能性もある。原論文は保持窓の設定が実行基盤に依存することも示しており、短いP12での失敗から観測省略一般を否定しない。

したがって優先保持が直近保持を上回ったとしても、その差だけで強い単純対照を超えたとはしない。観測だけの省略も比較候補に含め、実際に必要な対照をP18全件後に選ぶ。原論文のモデル・SWE-benchの性能をAppWorldへ移した数値は使わない。CodeActの正式書誌は[ICML 2024のPMLR記録](https://proceedings.mlr.press/v235/wang24h.html)で確認した。[読解範囲と保存ハッシュ](../reports/observation_masking_source_review_20261021.json)。
