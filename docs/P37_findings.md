# P37：明示した２項目の読取部品を検証した

2026年10月22日。必要項目を明示する読取部品を実装し、全12保存記録を使う補助プロトコルで動作を確認した。**99件の曲詳細要求のうち11件を過去のライブラリ取得で満たし、３方式とも保存返却との項目不一致０。** 元のAIプログラムは再実行していないため、これはタスクの品質維持や実際のAPI・トークン削減を示す結果ではない。[事前仕様](experiments/P37_field_contract.md)／[全件結果](../reports/P37_field_contract.json)。

## 何を実装したか

`read_fields(api, arguments, fields)` は原APIとは別の、必要項目を指定する部品。すべての項目を満たすときだけ再利用する。新しい原情報を取得した場合も、返す項目は全方式で同じにする。原APIの返却全体を黙って一部へ変えない。

今回確認した意味の対応は、公開AppWorld実装におけるSongの通常表現とライブラリの短縮表現に限る。固定した実装版、同じ実行・閲覧範囲、既知の状態版が必要。私的な `added_at`、別対象のID、衝突、不足、古い状態、未知の操作は再利用の根拠にしない。原情報はモデルの説明や現在の返却から推測していない。

## 同じ条件で何を比べたか

保存された呼出し列の `show_song` だけに、固定の `title, artists` を要求する。比較は毎回取得、同一要求キャッシュ、同一要求＋別APIの契約による再利用の３方式。必要項目はすべて同じ。通常キャッシュは全返却を保持し、項目集合が変わっても再利用できる。

| 元の記録 | 補助要求数 | 毎回取得 | 同一要求キャッシュの取得 | 別API契約を追加した取得 | 再利用 | 項目不一致 |
|---|---:|---:|---:|---:|---:|---:|
| 書出・全履歴 | 62 | 62 | 62 | 51 | 11 | 0 |
| 書出・一覧追加 | 37 | 37 | 37 | 37 | 0 | 0 |
| 書出・出力省略と、他３課題×３条件 | 0 | 0 | 0 | 0 | 0 | 0 |
| 合計（全12条件） | 99 | 99 | 99 | 88 | 11 | 0 |

ここで「取得」は記録を読むコールバックの回数。実サービスへの送信は０。要求のない10条件を落として全課題へ有効だとは主張しない。キャッシュに当たった後で保存返却と照合し、当たったキャッシュへ未来の返却を補充しない。値・認証情報・原プログラムは公開結果に含めていない。

APIが返す全項目を印字する元コードへ、この２項目の結果を代入すると意味が変わる。このため、元の62詳細取得を51回にできた、元のCSVが完成した、元の仕事が安くなった、という結論は出せない。

## 採否と次に進む理由

同一要求のキャッシュでは拾えない11件の具体的な余地があり、部品は実行器への接続確認へ進める。一方、これを新しい一般的手法として本実験や未閲覧群へ進めることは、まだ決めない。適用範囲が１つのAPI対に限られ、モデルが必要項目を指定する費用や利用率も未測定である。

次は同じ説明・同じ必要項目読取機能を持つ対照を作り、API発見、権限、実行上限、完了、エラー、費用記録を変えずに接続できるか確認する。自動で原コードを書き換える案は、全体印字や後続参照の意味が変わるため採らない。モデルが何を必要とするかを、保存記録の未来から教える案も採らない。

部分キャッシュ、問い合わせ再利用、状態を考慮したツールキャッシュは既存研究にある。[原典と比較範囲](data_reuse_overlap_20261022.md)。P37の契約や部品を作ったこと自体は新規性ではない。研究の主目的は引き続き、ハーネスの制御で不要な取得・共有・実行を削減し、最終品質を保つことである。
