# 観測済みアルバム・プレイリストを使う部分読取契約

P90の全４曲詳細要求には、既存の曲一覧・曲詳細からの事前情報がなかった。この結果を変更せず、別の公開取得元から同じ項目を利用できる範囲を実装した。通常の項目再利用・結合の拡張であり、新規性や実課題の削減を示したものではない。

固定されたSpotify公開実装の `show_album`・`show_playlist` は各モデルの人向け応答を返す。アルバム応答の各曲は `Song.id` と `Song.title` を含むため、同じ状態版の曲詳細の `song_id` と `title` に対応する。曲のアーティストの順序は推測しない。アルバム内の `artist_ids` は保存されたID列であり、曲詳細が使う `Song.artists` と同じ順序だとは扱わない。

プレイリスト応答の各曲は `Song.artists` をたどってID列を作っている。曲詳細も同じ関係をたどってID・名前を作る。この順序付きID列と、同じ状態版ですでに取得したアルバム・曲一覧・曲詳細に含まれるIDと名前を対応づける。全IDの名前が一意に既知の場合だけ `artists` 項目を用意し、部分的なアーティスト列を完成品として返さない。題名だけを持つ場合は、その題名と曲IDだけが既知であり、他の項目は元の完全取得を必要とする。

対象ID、返答ID、認証引数、型、応答構造を確認する。同じ状態版で矛盾する項目・名前・順序を観測した場合は再利用を認めない。既存の６読取API以外は従来どおり無効化し、世界・状態版・公開実装の境界を越えて結合しない。新しい読取例外や変更操作の例外は追加していない。

追加索引は曲・アーティストそれぞれ最大512対象、値64 KiB、同じ項目の相異なる値は２個まで保持して矛盾を判定する。元の完全応答キャッシュも両方式で共通に使う。部分値は遅延参照のための条件付き根拠であり、元APIの純粋性・成功・外部変更の不存在という前提を自動検証するものではない。登録されていないAPIの権限を与えることもない。

公開コードの読取範囲はSpotify `apis.py` の曲詳細443–481、アルバム728–770、プレイリスト1051–1096、`models.py` のSong 141–202、Album・Playlist 203–325。元のP37と同じ２ファイルのハッシュを照合する。全アプリの作用や一般的なSQL順序を証明したとはしない。

P91ではP88全８条件の32固定ファイルを１回だけ点検し、全４対象要求の直前に利用可能な項目を分類する。成功した曲詳細の後の値は事後照合だけに使い、先の根拠に繰り上げない。元のP89分類を併記する。対象要求を実際に含む `run_python` の応答記録をたどり、固定長・ノード数内で構文を点検する。構文箇所と実行回数を同一視せず、根を別の関数へ渡す構文も「全項目が実際に必要だった」とは断定しない。将来コード・持続名前空間・動的な参照寿命・削減回数は未検証である。
