# 修復範囲を選ぶ案の追加照合

2026年10月22日、P47実行中に[ControlScope v1](https://arxiv.org/html/2609.34313v1)の§3–6、付録A.1–A.5・B.1–B.2・C.1–C.2を確認した。同じ公開状態から、継続、次のAPIのデータ引数編集、未完了コードの置換を比較する。通常の後続計画は全条件に残す。利用可能な修復、実際の選択、修復後の実行継続を分けており、再開や修復粒度の変更だけを新規性とはできない。

原稿は、API呼出しが減ってもレビューのモデル費用が増える場合、成功件数が同じでも課題が入れ替わる場合を記録する。AppWorld V1のコード置換にはAPI枠の更新が含まれることを明記し、V2の局所比較では残量を共有する。この二つを同じ費用条件として扱わない。正式採録と公開実装の再現は未確認。[版・取得・読解範囲](../reports/revision_scope_source_review_20261022.json)。

本研究への判断は次のとおり。これらは原論文の結論の転載ではなく、次の実装を選ぶための条件である。

- P47は拒否時の返信と表示を比較し、実行途中のコード置換や局所修復をまだ導入していない。原方式の完全再現ではない。
- エラー前の操作を保持して再開するだけの案は、通常の持続実行と修復範囲の制御から区別できない。新しい名前を付けて主方式にしない。
- 次に修復を扱うなら、閉じた記録で既実施操作の再実行や局所修復の不足を確かめ、同じAPI・同じ残予算・通常の後続計画がある対照と比較する。
- 局所修復に使う情報の選択費用と、後から全体計画へ戻る費用まで含める。後続の生成費用を全額削減可能と仮定しない。

P47の固定条件と生成は、この読解で変更していない。まだ修復器の実装や新しいモデル実験を採用したという記録ではない。10月23日の中心主張には、原典と異なる具体的な規則または十分に裏付けた条件を示す必要がある。
