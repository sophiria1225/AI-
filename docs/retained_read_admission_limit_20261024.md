# 参照を残すだけの遅延読取では受理できる件数は増えない

## 対象と前提

実装した明示的な読取ビューでは、完全取得を後回しにする参照１個につき、将来の完全取得１回分を予約する。実際のAPI消費を `S`、未取得参照の予約を `D`、上限を `B` とすると `S + D <= B` を保つ。予約は実費ではないが、通常APIへ再使用できる余力でもない。

以下は、各読取が別対象で完全応答キャッシュに当たらず、各参照が生きたままで、１参照の完全取得に１要求かかる場合の説明である。成功した読取だけを扱い、例外・不明作用・状態変更・追加の通常API・まとめ取得・予約共有は含めない。任意の課題やPythonへの定理ではない。

## 受理件数の恒等式

開始時の消費を `S0` とし、開始時に未取得予約はないとする。新たに受理した参照が `n` 個のとき、即時取得と遅延取得の両方で `S + D = S0 + n` が成立する。

- 即時取得は `S` を１増やす。
- 遅延取得は `D` を１増やす。
- 後から完全取得すると `D` が１減り、`S` が１増えるため、合計は変わらない。

したがって、参照を保持するだけでは両方式とも最大 `B - S0` 個までしか受理できない。遅延側の実要求数が少なく見えても、同じだけ未消化の予約が残っていれば、次の読取を受け入れる余力は増えていない。終了時にホストを閉じて予約を解放することも、課題が成功したことや生存参照が不要だったことを意味しない。

これは予約不変条件からの直接の帰結であり、新しいアルゴリズム・新規性・実課題の品質保証とは位置づけない。既存の[資源付き遅延計算](deferred_read_resource_prior_boundary_20261024.md)の検討を引き継ぐ。
