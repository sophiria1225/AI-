[Large Result Offloading](https://zircote.com/LRO/paper/)は更新中の著者公開文書で、正式採録は未確認。大きな返却を外部ファイルへ保存し、参照と抽出手段を渡す構成を確認した。評価では全体ファイルとページ取得の条件が異なる。記載上のページ幅・ターン上限だけでは実際の取得可能範囲を確定できず、リンク先の実装は今回404だった。掲載スコアや原因説明を本研究の実測へ流用しない。参照渡しやファイルへの退避を新機構と呼ぶ案も採らない。

[Tool Primitives / HEART](https://arxiv.org/html/2609.01736v1)は2026年9月1日の著者原稿。今回は要旨・導入のみ確認した。自然言語でツールを包み、計画・引数対応・検査を分ける構成を述べている。方式節・実装・性能は未確認であり、重複を判定する精読を済ませた文献とは扱わない。

## 本実装の対照に残る差

準備済みの`compute_data`は、モデル応答前に取得した公開観測をIDで選び、普通のPythonへ直接渡す。入力をモデルに再転記させない点は確認済み。一方、計算結果はモデルへ戻るため、その値を次のAPI引数へ使う際には、なお生成による転記が必要になる。コード自身がAPIを呼ぶ方式や、コードの返却値を引数へ直接束縛する方式とは同等ではない。

この制約がある対照で失敗しても、「コード実行では解決できない」と一般化しない。必要なら取得済みの同じデータを使い、計算結果から実際の書込みまでの経路も比較する。そこへ変数参照を追加する機能自体は既存のプログラム実行であり、独自技術とはしない。

また、全件を先に外部ファイルへ用意した方式と、APIで一件ずつ取得する方式を比べる場合、前者の取得・保存・再読費用も数える。未取得データを無料で追加しない。どちらも同じ公開APIと開始状態から進める全体実行と、取得済み情報を固定する局所比較は分ける。

- 取得済みデータの処理・転記で失敗が残れば、通常計算と書込み経路を先に対照にする。新しい検証器が必要という結論を先に置かない。
- API・時間上限による未完了なら、観測した手順の費用と、他の公開ツールで短縮可能かを分ける。特定手順の回数を全方式の下限と呼ばない。
- 全件改善した場合、その事実を認め、同じ失敗を前提とした専用ゲートは導入しない。

この分岐は次の判断基準であり、新しい実験の自動起動予約ではない。P25の全結果と公開観測を確認して、主張に必要な一つの比較を固定する。新しい機構または知見が成立していなければ、10月23日の時点でもその不足を明示する。通常機能の名前を変えて、月末原稿の新規性へ読み替えない。
