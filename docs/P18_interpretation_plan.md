# P18の結果を読んでから原因を決めるための準備

2026年10月21日17時台、P18の全４件が終わる前に作成。実行条件は変更しない。これは新しい性能実験の計画ではなく、凍結した比較基準から主張できる範囲と、次に検討する対照の整理である。

## 現在の基準が持つ能力

P11/P18は、公開APIの発見、複数の独立した関数呼出し、履歴の保持、原観測の再読を備える。各API要求を数え、同じ応答内の複数操作も１回とは数えない。一方、モデルがPythonのループや変数を直接作る機能は渡していない。ブリッジがJSON引数から作るAPI呼出しと、自由なコード生成を区別する。

AppWorldの[固定版README](https://github.com/StonyBrookNLP/appworld/blob/42b5bcf3cd334fee33f0c37c02070a9f5807add5/README.md)は関数呼出し型とコード型の両方を扱う。後者では状態付きPythonの変数や制御構造を利用できる。現在の全履歴基準は関数呼出し型の比較条件であり、全ての実行形態の中で最強と検証済みではない。[P8の接続選定](experiments/P8_native_baseline.md)、[P10の会話校正](experiments/P10_native_history.md)。

単純な繰り返しや集合計算の失敗が残った場合、既存のコード実行方式で解ける可能性を先に検討する。コードを使える側だけAPI回数を無料にする比較は行わない。逆に、コード型を導入して解決しただけなら、新しいハーネス原理とは呼ばない。

## 全件の確認順序

| 確認 | 用いる記録 | 言い過ぎないこと |
|---|---|---|
| 最終成否と停止条件 | 終了後の独立評価、summary、usage | 完了宣言は最終成功と同じではない |
| 実行器の整合 | 原要求、応答、送信記録、保存境界の監査 | 接続不具合をモデル能力や記憶の必要性と混同しない |
| 予算 | 80 API・80生成・45万トークン・30分の使用量、予算予約、使用量不明 | 上限停止だけで課題が予算内に不可能だったとはしない |
| 情報取得・保持 | 公開操作、原観測の長さ、再要求、実際に渡した履歴 | 同じ要求でも時刻・状態が変われば必要な再確認かもしれない |
| 対象と実行 | 要求・API説明・実際の返却だけから確認できる範囲 | 一覧の行数は一意な対象数や完全な対象範囲とは限らない |
| 次の対照 | 下表の単純方式と近接する既存方式 | 自作接続の修正や既知手段の導入を新規性に数えない |

全４件を残し、成功例も同じ順序で確認する。失敗原因は追加の介入なしに確定しない。最終評価の合否は分析に使うが、隠し評価の対象一覧・解答を次の実行や判断器へ渡さない。予算内不可能を主張するなら、公開仕様と観測から必要操作数の下限を別途立証する。今はその証明はない。

[予算集計器](../scripts/analyze_native_budget.py)は全件の終了を確認してから、API・生成の回数、既知／不明トークン、キャッシュ再利用・再処理、サーバー処理時間を分ける。独立評価ファイルは終了確認のため存在だけを調べ、内容は読まない。７つの制御検査を含む全322検査と既存P11４件の再計数で確認した。[準備の検査記録](../reports/P18_analysis_preparation_controls_20261021.json)。これはP18の結果ではなく、生成・環境操作の追加は０。

## 次に検討する最小の対照

| 観測された場合の候補 | 先に比べる対照 | 独自機構へ進めない場合 |
|---|---|---|
| 消した内容の反復取得 | 同じ履歴予算での再読済み情報の保持、原文への参照、セッション情報保持 | 単純な保持だけで足りる |
| 認証情報や対象IDの転記ミス | 同じ公開情報を使う変数・コード実行 | 転記をなくす通常実装だけで足りる |
| ページ列挙の早期停止 | API説明に従う列挙、未確認範囲の明示 | 通常のページ取得・状態表示だけで足りる |
| API数・時間の超過 | 調査・再要求・対象操作・検査の内訳、公開仕様にある一括API | 主因が機構ではなく対象数と上限、または明らかな無駄だった |
| 全履歴で正常完了 | 同じ情報・予算を使った保持費用の比較 | 品質を保つ費用減がなく、追加機構の必要性もない |

再読した内容を保持する原理も既出である。[Pichay](https://arxiv.org/html/2603.09023v1#S3.S5)は、削除後に同じ内容が再要求された場合の固定保持と、内容変更時の解除を記述する。今回は3.2〜3.6節、6.4〜6.5節を確認した。ファイル中心の検出を、そのまま状態付きAPIの再要求や過去の観測の復元と同一にしない。論文中の応答品質確認を、実環境の最終状態の一致へ読み替えない。正式採録と性能再現は未確認。

[ACM](https://arxiv.org/abs/2607.23809v1)も、外部へ退避した内容を必要に応じて問い合わせる方式を扱う。今回は要旨だけの確認で、詳細機構を網羅した比較ではない。外部記憶・再読そのものを新提案にはしない。[今回の原典保存・確認範囲](../reports/baseline_scope_sources_20261021.json)。

この準備だけで新規性を確定せず、結果が出たら「観測事実」「原因候補」「反証する比較」を分けて記録する。残り12シナリオの要求文はまだ開かず、主方式と評価条件を固定してから用いる。
