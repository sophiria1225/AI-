## 何を区別したか

API返却の辞書・リストを元の型のまま保持し、生成コードの添字・get・反復を観測する。フィールド単位の読み取りと、丸ごとの印字・JSON変換、任意関数への引渡しを分けた。値の代理型を使う案は、型判定・ライブラリ挙動を変える可能性があるため採らなかった。

| 後続での集計 | 件数 |
|---|---:|
| 正常API返却 | 445 |
| 返却中のスカラー項目 | 4,766 |
| 添字等で読み取りを観測 | 348 |
| 印字・JSON変換等へ渡された項目 | 2,066 |
| 内部を追わない関数等へ渡された項目 | 84 |
| 上記のいずれかを観測した項目の和集合 | 2,365 |
| 根がスカラーで、対応を完全に追わない返却 | 7 |

項目は文字列・数値等の終端を数える。１項目が長文でも短い数字でも１件。各行には重複があり、単純加算しない。項目数やJSON量はトークン数でも、削減可能量でもない。APIスキーマや別に渡された原記録のコピー、動的実行、外部ライブラリ等を完全には追わない。今回の軌跡で計測の上限超過・観測した変更・内省はなかったが、任意のPythonで成立する保証はない。

## 「参照されなかった情報を捨てる」案を採らない理由

書出・全履歴は62件のAPI返却に834項目が含まれたが、その後のフィールド読み取りは観測されなかった。保存されたコードを確認すると、全曲の詳細を先に集め、後で印字する順序だった。先行する取得でAPI上限に達し、後の利用へ進めていない。したがって、未参照の多さを不要な取得量とするのは誤りになる。

写真整理・全履歴では、343項目のうち直接の読取84、印字等への引渡し133だった。返金・全履歴は３項目が全て印字等へ渡った。異なる利用形態があり、一定割合を一律に落とす根拠にはならない。

現在の接続は、APIの全文をモデルへ渡すのではなく、コードが印字した結果と参照IDを渡す。**未参照フィールドをAPI返却から除いても、そのまま入力トークンが減るとは限らない。** 取得と入力の制御を別に評価する必要がある。

## 次に確認する具体的な候補

単に情報を捨てる方向ではなく、**要求された情報が別の取得結果や作業状態に既に含まれる場合に、再取得を避けられるか**を確認する。候補は、同じAPI名・引数のキャッシュより細かい、対象IDと必要項目の対応による再利用。ただし既存のデータベース最適化・キャッシュとの重なりがあり、この発想だけを独自性にはしない。

最初は記録上の一致範囲を調べる。対象の取り違え、古い値、必要項目の不足、印字やライブラリによる全体参照、取得自体の副作用を区別する。過去の同じ値が見つかっただけで次のAPIを省略しない。記録した実際の返却を使って答え合わせする分析は、実行時に正しい返却を先に知る方式とは分ける。
