# P105: 未取得参照を共有する実装の接続確認

元の遅延版では、同じ対象への参照を二つ作ると二つの将来取得を予約する. 通常の完全応答キャッシュを持つ即時方式より取得が増えうることを模型で確認した. 別版は実行範囲、状態版、API、全引数、部分応答の契約が一致した参照の予約を共有する. この通常の重複取得共有を新規手法とは扱わない.

P105は、修正版を実AppWorldの型付きAPI境界と持続Pythonへ接続する小さな確認である. 既知CSV課題の同じ初期公開状態から３環境を作るが、CSV課題自体は解かず、評価器を呼ばない. プログラムは機構を作動させるために手書きしたものなので、自然な課題での出現頻度や品質維持を示さない.

## 変更するものと揃えるもの

通常の完全応答キャッシュを持つ即時版、元の遅延版、参照共有を加えた遅延版を、この順序で１回ずつ実行する. 全方式に同じ７プログラム、公開API、初期化seed 42、１方式20 APIの予算を用いる. 元の遅延版も残し、修正前の問題が消えたかを確認する. どの方式も先に実際に返された公開応答だけを再利用する. 契約を未検証のAPIや項目へ拡張しない.

| 段階 | 確認する動作 |
|---|---|
| 1 | 認証と先頭３曲の取得、既存のlike状態確認、一覧の再取得. 元の接続確認と同じ６ APIを全方式に課す |
| 2 | 同じ曲への二つの参照を別々に作り、既知項目だけ読む |
| 3 | 両参照から未知項目と全辞書を読み、同じ値を返すことを確認する |
| 4 | 別の曲の二参照から片方だけを解放し、残る参照を読む |
| 5 | 最後の参照を解放し、未使用取得の予約を取り消す |
| 6 | 同じ対象の通常API呼出しで完全応答を取得し、二参照の解決に再利用する |
| 7 | 一覧再取得、二参照の作成、like/unlikeの状態変更、変更前の値の保持と変更後の値の再取得を確認する |

対象IDは実際の先頭３曲から得る. 課題DBや正解から選ばず、３曲が得られない場合は代わりの曲を探さず停止する. likeとunlikeのどちらを使うかは同じ手書き条件式で決まり、初期状態を後から変更しない. 各方式の標準出力hashは全７段階を比較する. 実API、予約残高、通常キャッシュ利用、参照共有、取得済み応答による予約解除、制御要求と通信量を区別して記録する.

元の公開API契約と実装から期待値を事前に固定する. API数は即時13、元の遅延16、修正版12. 修正版の即時方式との差１回は、既知項目だけを読んで最後の参照を捨てるように作った段階４–５に由来する. 元の遅延版との差４回を、強い通常方式に対する４回の改善と読み替えない. 実測が期待値と異なれば結果を保持して停止し、期待値やプログラムを変えて同じ試行をやり直さない.
