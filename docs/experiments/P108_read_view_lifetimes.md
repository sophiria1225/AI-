# P108: 保存制御列から取得予約の終わり方を確かめる

P107の全２条件が動いている間に準備する. 途中の成否、生成コード、API返答は準備へ使わない. 全条件の閉鎖、元の照合、所有サーバー停止を確認し、固定headのpushとpull_request両workflowおよび両accounting-and-syntax job成功後に一度だけ点検する.

## 対象と操作

対象はP107の既知CSV１課題の即時方式と共有遅延方式の両方で、成功した側や参照を多く使った側へ絞らない. 元のAPI返答、Python制御wire、予算イベント、仕様転送の返答指紋を全件使う. 元の生成Pythonは実行せず、固定したハーネスのホスト処理だけへ元の制御要求と保存返答を順に与える. 現実のAPI、モデル、課題環境、評価器は呼ばない. APIの作用をもう一度起こしたり、未取得の完全値を作ったりしない.

比較するのは実際に使われた方式の当時の返答である. 別方式の反実仮想を作らない. プログラムごとの公開API仕様、実送信行、型付き返答の状態、制御返答の全バイト指紋、共有予算のイベントと最終値が一致することを必須とする. 壁時計の再現値を当時の時間に置き換えない. 元の時刻制限で送信前に拒否した行は、その保存事実を入力として扱う.

## 予約の分類

未取得参照へ結び付いた予約だけを追い、通常APIを送る瞬間の一時予約とは分ける. 終端は、明示的な完全取得、保守的な状態変更前の取得、最後の参照の解放、別の通常呼出しが完全値を供給したことによる解除、停止時の未解消の５つとする. 送信時の正常返却、既知例外、不明を保持する. 複数参照で共有した予約は１群として数える.

部分項目へのアクセスはPython内だけで完了するためwireに残らない. この点検からそのアクセス回数や将来の不要性を推定しない. 参照の解放による予約取消しも、別方式と全仕事を比べたAPI削減数やtoken削減数ではない. P107で課題が未達なら、この一致を課題成功へ読み替えない. 新規手法の主張も行わない.

## 有限性と保存

全２条件、各最大256プログラム、5,000制御要求、2,048ファイル、256 MiB、各ファイル16 MiB、点検180秒. 元の全ファイルを処理前に指紋で結合し、処理後にも不変性を確認する. 失敗、不一致、未実行は残して再試行しない. 元の実験は変更しない. 追加モデル生成、環境API、生成コード実行、評価、未見課題閲覧はすべて０. 原稿は更新しない.

13の手書き検査では、２方式の正確な返答、通常キャッシュ、参照の共有と解放、状態変更前の取得、別の完全応答による解除、例外と返答紛失、モデル側の欠測と明示停止、仕様の即時転送、指紋改変の拒否を扱う. 最初の検査でwireのprogram_index除去の再現漏れを修正した. テスト専用catalogの重複も修正した. これらは実結果を見る前の検査であり、実験の再実行ではない.
