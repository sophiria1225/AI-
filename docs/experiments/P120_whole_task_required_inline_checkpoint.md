# P120: 要約を必須引数として指定する同時出力の通常対照

2026年10月25日. P119の全８条件、所有server、監査、資料、全４対を閉鎖した後の新しい比較. 原稿と未見12課題は保留する. この文書は実行前の規則で、性能結果ではない.

P119は別呼出し要約4/4、任意の同時出力3/4成功だった. 後者は２回とも任意のcheckpoint引数を出さず、履歴の要約置換は０件だった. CSVの成功を失っており、全tokenの減少を品質維持の削減とはしない. [全件所見](../P119_findings.md).

## 問いと変更範囲

任意欄を設けただけでは実際の要約が起きなかったため、同じ行動応答内の要約を必須引数として指定した通常対照を調べる. 比較相手は変更していないP118の別呼出し要約実装で、両側とも既知４課題を最初から各１回実行する. P119の結果を上書きしない.

`single_checkpoint`は従来の別呼出し要約、P120内の`inline_checkpoint`は必須欄を指定する同時出力である. P119と同じpolicy文字列でも、その実装、計画、run_id、原記録は別々に固定する.

変更は要約を求める１回の`run_python` schemaと追加指示である. schemaのrequiredへ`checkpoint`を加え、指示を「含めてもよい」から「含める」へ変える. この回以外のtool schemaは変えず、tool_choiceは全回autoのままとする. 特定のtoolや追加呼出しを強制しない. schemaで指定したことは、モデルが必ず従うという保証ではない.

新しいラッパーは固定済みP119の制御、予算管理、metadataの分離、実行、形式検査、履歴の投影を再利用する. コードと参照IDを変えず、元の応答と対応づけて一度だけ実行する. この変更を新規な意味判定器や新規性の確立とはしない.

## 一度だけの要約と失敗時の扱い

元の全履歴と通常の予算通知を含むnative入力が16,384 token以上で、閉じたやり取りが３回以上ある最初の機会を１回だけ使う. 元のsystemと課題、直近２回、今回のコードと実際の結果、その後の全履歴を残す. 要約対象はそれより古い完結履歴だけであり、今回のコードの未実行結果を予測させない. 保存履歴と永続Python状態は削除しない.

要約は`completed`、`usable_state`、`remaining`、`uncertainties`の４欄で、各欄は最大32文字列、１文字列は1〜2,048文字、compact JSON全体8,192文字以内. 今回のコードと要約は実行役の温度1.0、4,096出力tokenを共有する. 別呼出し要約は温度0.7、上限4,096出力tokenの従来経路を使う. 追加指示とschema、全出力、形式失敗、後続行動の変化を共有費用へ数える.

同時出力はちょうど１つのrun_python、終了理由tool_calls、基礎引数と要約形式が有効な場合に限り要約候補を作る. 重複JSONキー、余分な引数、非有限値を修復しない. 要約が欠ける、形式が不正、打切り、複数tool、別tool、無toolのときも、要約だけのための再生成や別呼出しへの切替はしない. 基礎引数が有効なコードは通常どおり扱い、要約を採用しない場合は古い履歴を残す.

今回の実行が閉じた後、次の行動が必要なら、同一の残予算通知を付けた通常表示と要約表示を実tokenizerで数え、後者が厳密に短い場合だけ採用する. 対応を確認できたmetadataは両表示から除き、原記録には残す. 最終応答で仕事が終わった場合は不要な次入力を計数せず、採用未判定として残す. 形式と長さの検査は意味の完全性や元依頼の充足を証明しない.

## 実行前の確認と全件の判定

合成試験と構文検査を通し、同一headのpushとpull_request両workflow・両accounting-and-syntax job成功後、専用固定木で一度だけ実行する. 初回８要求の課題内一致、別呼出し要約１入力、合成の必須欄付き要求と採否候補２入力を、計12入力の語彙計数で確認する. 事前確認ではモデル生成、実API、独立評価をしない.

全８条件を生成開始前に固定し、中間成否を見て順序や条件を変えない. 使用量不明は０で補完せず、その応答を実行しない. API効果と後処理が確認できた場合だけ、serverのidleを待って１回評価し、次の固定条件へ進む. API効果不明、初期状態やcacheの不一致、実行環境、後処理、評価の故障では全体を停止して失敗を残す. ユーザー停止を優先する.

全８枠と所有serverが閉じてから、全要求と全役の費用、必須schemaと指示、要約の要求・生成・採用・不採用、原履歴、実行コードと参照IDを照合する. 成否、欠測、未実行、未評価を全て残す. 評価の正解や追加テストはモデルへ返さない.

採用基準は全８件評価済みかつ使用量既知、監査不一致０、課題ごとの成功損失なし、両側成功１課題以上、全４課題と両側成功課題の両方で同時出力の総tokenが少ないこと. さらに今回の制御が実際に使われた条件を１件以上必要とし、同時出力要約の採用が０件なら採用しない. 要約を要求した回数だけで発動成功と数えない.

cache済みinputも論理tokenへ含め、実時間とcache利用量を別に残す. 指示、schema、要約の時点、出力配分、後続行動の違いを含む方式全体の比較であり、差を要約要求の入力除去だけの因果効果へ帰属させない. ４つの既知課題に各１回という限界を保持し、一般的な品質保証や新規性を主張しない. P111の不明２件、P118の不明１件、P119の不発動と成功損失を保持する.
