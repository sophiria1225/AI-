# P109: 実際の取得経路と入力履歴の内訳

P107/P108の全２条件が閉鎖した後の診断である. 両側が各21生成、427,234論理token、53 APIで未達だったことと、対象のshow_songが呼ばれずread_viewも使われなかったことは既知である. この結果を隠した事前登録や独立確認とは扱わない.

## 全件の範囲

P107の即時版と参照共有版を全件点検する. 各生成の保存request/response、全events/spans/usage、bootstrapを除く全実行入力を対象とする. P107監査とP108の保存入力台帳からSHA256を引き継ぎ、読取前後で照合する. １条件だけ、成功したプログラムだけ、特定の生成だけを抽出しない. エラー、未処理の枠、元の未達を残す.

1. 全API要求について、同じ名前と全引数の成功返答が既に存在したかを数える. 過去の返答との一致と、既存６ APIの保守的な状態境界を越えないことを別に記録する. この点検でキャッシュ許可を追加しない.
2. 実際に14回ずつ呼ばれたshow_artistについて、以前のshow_song_libraryのartists内、または以前のshow_artistからIDと名前を観測していたかを確認する. 同じIDの矛盾、途中の保守的な境界、後の返答との一致も残す. これは指定した公開返答位置だけの履歴であり、あらゆる取得済み情報を網羅する証明ではない. 名前が既知でもArtist全体の代替にはならない. show_artistを読取専用の免除へ追加しない.
3. 保存Pythonを構文解析し、call_apiの返却の受け方と、単一名へ代入した後の同じ綴りの名前の項目参照、全体参照、変更、上書きを記録する. ループや関数内の参照を明示する. 別名、例外経路、持続名前空間、将来の生成の需要は証明しない. 構文箇所を実API回数や節約tokenに換算しない.
4. 各モデル入力をsystem/user本文、assistant本文、過去のreasoning_content、提出関数名と引数、tool本文に分け、重ならない文字列フィールドのUnicode文字数を数える. API仕様のJSON文字数は別項目にする. 実測input/output/cached tokenは元の値を併記する. 文字数をtokenへ換算しない. 累積入力の文字数の合計は繰り返し提示を含む露出量であり、固有の生成量や削減実績ではない. 私有推論の内容は解釈・公開しない.

## 予算と実行

[固定設定](../../configs/P109_used_paths_v01.json). 全２条件、180解析秒、条件ごと最大80生成・256プログラム・1,024入力ファイル・256 MiB、ファイル16 MiB. 元の生成コード、モデル、環境API、評価器、tokenizer、DB内容、未見12課題の追加実行／読取は０. 新しいタスク実行や状態復元をしない.

同じ完全headのpushとpull_requestのworkflow、および両accounting-and-syntax job成功後に１回実行する. 結果と失敗を上書きせず、自動再試行しない. 保存履歴を読みながら条件や判定器を調整しない. 不適合はそのまま残し、変更が必要なら別の準備と版にする.

## 次へ進める条件

この診断自体を新提案手法や品質を保った削減として報告しない. 実際に利用できる以前の情報、現在の明示的な需要、状態・型・例外の契約が結び付いた場合だけ、通常の完全キャッシュや明示的項目取得を対照にした次の有限計画を作る. API数だけを削っても入力履歴は減らない場合がある. 入力の増加源が分かっても、その削除が成功率を保つとはみなさない. 原稿は保留し、全件がそろってからProjectとmaterialsを更新する.
