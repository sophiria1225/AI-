# P34：省く出力と、実行状態の値を対応づけられるか

2026年10月22日、P33の進行中に独立して行う準備検査。P33の途中成績や生成内容は読まず、既知のP29全４課題・固定８応答後だけを使う。モデル生成、アプリへのAPI送信、評価器呼出しは０。12保留シナリオも使わない。

狙いは、古い出力を一律に省く代わりに、「同じ内容の値を今の実行状態から取り出せる」という根拠を省略判断へ使えるかを確認すること。単なる変数名一覧では、どの過去出力がどの値に対応するかは確定しない。ただし原記録には元の出力が全て残るので、値が一致しない出力も失われたわけではない。

まず、最後の１ターンより古いPython出力の全件を分類する。成功し、切り詰められていない、全体がJSONまたはPythonのリテラルである出力についてだけ型を保った内容のハッシュを作る。ラベル付き文章の一部分を都合よく抜き出したり、LLMへ要約・対応推測を頼んだりしない。

記録済み返却だけでPythonの前半を再生し、返却・要求列・例外が元と一致することを確認する。その後、別の名前空間で読み取り処理を実行し、現在の組込み型の値・子要素との一致を検査する。利用者の名前空間へ変数を加えず、値を書き換えず、独自クラスのメソッドは呼ばない。変数128個・要素20,000・深さ24・各値64KiB・一致経路８件で上限を設け、上限や未対応型を記録する。APIスキーマの状態も対象にし、毎回上書きされる一時入力`observations`は除く。

公開するのは一致数、対象の文字量、検査時間、上限到達、再生照合、原記録のファイルハッシュ。変数名・参照経路・値・内容ハッシュは公開しない。文字量をそのまま削減トークンに換算しない。

一致は、その時点の値の等しさを表す。元データの由来、現在の外部環境への正しさ、将来の関連性、出力の文章表現まで保証しない。一致しなかった場合も、型や上限で調べ切れなかった可能性がある。後で変数が変わるため、参照先を使う直前に値を再確認する関数も用意する。これ自体は検査であり、運用中の入力を省く制御器としてはまだ採用しない。

結果が少数の短い出力に限られるなら、集計だけを残し追加のモデル実験へ自動で進まない。長い出力へ十分適用できる場合は、P33の全結果を見た後、同じ入力量の通常選択や、一覧だけの条件との差を検討する。新規性と品質維持は別に確かめる。

## 近接研究と今回確かめる範囲

[Scrollの著者原稿v1](https://arxiv.org/html/2608.21690v1)の2.2〜2.4節では、変数の型・形・由来、外部の履歴、参照先、復元費用を考慮した省略と索引を扱う。したがって、状態を残して参照先を付ける機能だけでは差にならない。今回確認するのは、既存の出力と現在の値をハーネス側で照合できる範囲・費用である。公開実装の照合と性能再現は未了で、この検査に独自性があると確定しない。v2のHTMLは404で取得できず、v1を読んだことを最新版の全確認とは扱わない。

## 全４件の確認結果と判断

09:40頃に終了。32プログラム・55記録要求の再生が一致した。実API送信・モデル生成・評価器呼出しは０。全体1.85秒、値の照合部分の合計0.061秒。全500検査合格。P33とは別の隔離容器を用い、終了後は全て削除済み。時間はP33の推論が並行する開発機上の参考値で、専有環境の速度測定ではない。[全件集計](../../reports/P34_output_residency.json)。

一致した省略候補は600文字で、P33省略対象の出力84,626文字の約0.7%だった。これは文字量であり、削減トークン率ではない。確認できる範囲が狭いため、この全体リテラル照合だけを新しい省略方式としてモデル比較へ進めない。文と値が混ざった出力、計算で作った表示、型の異なる表現などを今回の照合は扱えない。未一致の内容が実行状態に存在しないと結論しない。

「Pythonを保持したのだから出力の大部分を現在の変数から直接再現できる」という前提を、ここから支持することはできなかった。参照先を付ける制御へ進むなら、表示と値の対応を取得時に記録するなど別の観測が必要になる。ただし取得時の値・由来の管理はScroll等と重なるため、その実装を追加するだけで新規性とはしない。今回は狭い検査とその限界を記録し、P33の全結果を待つ。
