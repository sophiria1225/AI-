# Pro V2の共通ハーネス接続と初回観察

対象は、公開要求と基点コードで選んだAnsibleのYAML処理1課題。主課題の正式採用、自動再編の実装、確認評価ではない。環境の正負対照は別のR13で扱い、成立前にモデルを呼ばない。

10月20日：R13の正負対照が成立し、実コンテナの公開実行経路も確認できた。実装は[PR #21](https://github.com/sophiria1225/AI-/pull/21)、作業は[Issue #20](https://github.com/sophiria1225/AI-/issues/20)で管理する。以下の「未実施」は準備時点の記録で、最新の条件は末尾に記す。

## 共通化の範囲

既存実行器に固定されていた作業ディレクトリ、Pythonパス、環境変数を明示設定にする。トークン台帳、打ち切り、ツールの終了値記録、成果物差分、版に結びつく完了判断は共通部品を使う。Djangoの既定値は維持し、Ansibleでは`/app`と当該イメージのPythonを使う。別分野だからという理由で無料の制御呼び出しや新しい費用計算を加えない。

この接続変更は研究上の新規性ではない。過去のP3ソースと実験条件は原記録に保存済みで、固定計画を書き換えて再実行はしない。新しい試行には新しいソースのSHAを記録する。

## 検証と残作業

明示環境がconda設定を継承しないこと、非ゼロ終了が記録されること、成果物・公開検査が指定した作業場所を使うことを5対照で確認し、既存を含む86テストが合格した。最初の全体実行はworktreeに固定版vendorの参照がなくimportエラー2件だった。無視して合格とせず、既存の固定版へのGit対象外の参照を設定して再実行した。[記録](../../reports/pro_runtime_controls.json)。

実際のAnsibleコンテナ上では、Pythonと可視ツール、成果物への新規ファイル取り込み、失敗・タイムアウト、公開検査の入口を確認する。そのための検査は公開要求と基点コードだけから選ぶ。評価用の追加テストや参照修正を見て選ばない。

公式のproblem statement、requirements、interfaceはすべて渡す。明示された依存を削除して、後から分かった依存のように扱わない。モデル・総予算・時間・公開検査・停止規則は、実機校正と評価器の正負対照が成立してから別の計画へ固定する。現在は予算やモデル実行回数を凍結していない。

## この順序を選んだ理由

課題ごとに別のエージェントを一から書くと、方式差と実装差が重なるため採用しない。固定2担当や自動集約を先に追加する案も、単一方式の新環境での挙動と評価の妥当性をまだ確認していないため後順位とする。R13の基盤エラーをモデルの課題失敗として数えることもしない。

## 実コンテナでの確認

`PRO_RUNTIME_01`は6.54秒で終了した。作業場所・Python、終了13の失敗、新規ファイルの差分保存、元の差分0への復元を、モデルと同じツール経路で確認した。公開基点のYAMLとfilterの既存131テストも合格し、テスト実行後の成果物は変化していない。モデル呼び出し0。[校正記録](../../reports/pro_live_runtime_calibration.json)。

検査対象は公開要求と固定基点のツリーから選び、5つの公開ファイルのGit blob/SHAを照合した。追加依存のインストールは不要だった。非公開テストを参考に検査を選ぶ案や、仕様の依存関係を削った入力を渡す案は採用しない。元の状態でも通る131テストは既存動作の確認であり、新要求の充足判定ではない。モデル自身が公開要求に対応する再現・追加検査を行う余地を残す。

ホスト側は97テストが合格した。追加対照では、公開入力への非公開列混入、入力改変、凍結後の成果物変更、使用量不明、実行コード変更を拒否した。候補評価用のコンテナに参照修正が入らないことも確認した。今回の実コンテナ校正では意図的なタイムアウトを追加しておらず、以前の共通ツールでのタイムアウト確認と区別する。

## 初回単一試行の条件

1課題・単一方式・1回を`P4_PRO_01`として実行する。MiniMax M3 IQ4_XS、KV q8_0、64K入力枠、1応答上限8,192、生成設定はP3と同じ。全リポジトリとproblem statement・requirements・interfaceの3項目を保持する。外部ネットワークなし・ホストマウントなし・1 CPU・4GiBの作業コンテナを用いる。

上限は60呼び出し、全入力＋出力600,000トークン、3,600秒。P3の4件がすべて30回・300,000の枠内で予算停止したため、より広い要求を観察する最初の開発試行では上限を広げる。無制限に増やす案は費用を制御できず、旧枠を唯一の妥当な予算とみなす案も根拠がないため採用しない。この変更は最適な予算の実証ではなく、課題適性を調べる開発判断である。P3と課題・予算・実行環境が違うので、両者の差を分担やモデルの効果とは呼ばない。

既存の費用台帳、残量通知、完了規則、成果物保存を共通利用する。全呼び出しと失敗を数え、最終成果物を凍結して一度だけ独立評価する。途中候補を評価結果から選び直さず、不合格を理由に同条件を成功まで反復しない。モデル用コードと評価側コードのSHA、入力、校正記録、予算は実行前に固定する。評価側にだけ非公開入力を配置し、結果を今回の生成過程へ戻さない。

最初に知りたいのは、要求に沿った複数箇所の作業と検査が実際に進むか、どの条件で探索・実装・検証が止まるかである。単一試行だけで品質維持、費用削減、作業移管の必要性は主張しない。次の固定分担比較は、この観察と残った費用を確認して別計画にする。
