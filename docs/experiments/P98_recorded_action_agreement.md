# P98：閉じたP82全24条件の表示と実操作の対応

2026-10-24。P94の１文脈だけの局所的な照合を踏まえ、既に終了したP82の全24条件を二次解析する。新しい方式、生成実験、未知課題による確認ではない。P97の途中結果は使用しない。

## 固定する対象と問い

P82の既知４課題、３通常条件、２反復の全24実行、426生成試行、1,156実API要求、使用量既知4,602,713 tokenと不明４生成を残す。調査済みの群を選んだ事後解析であり、未観測データへの事前登録とは呼ばない。比較の正負によって対象や閾値を追加しない。

問いは「同じ公開出力でも提出・実行を完了できていない例」「異なるコード構文でも同じ非空のAPI要求列を実行した例」が、この閉じた全群のどこにあるかである。既存のP82経路比較には公開出力のhashがあるが、全生成の構文とAPI実要求の対応を今回追加する。先行研究との差や新しい一般的な指標を証明する解析ではない。

各課題の６実行から全15組を作り、計60組を保持する。同一条件の反復だけ、同じ反復内だけに限定せず、条件と反復が異なる組も区別して残す。60組を独立な課題・標本とは数えない。各組は生成の序数で対応付け、片側が先に終了した後の枠も保持する。意味的に同じ段階への整列や、都合のよい最初の一致点の探索は行わない。

## 区別して数える値

公開出力は本文、関数名、引数文字列、終了理由を比較し、通信上のcall IDだけを除く。既存P82の全公開出力hashと一致することを要求する。コード構文は既存P93処理を使い、ASTの位置情報だけを外す。変数名、定数、文の順序、span参照は保持する。構文不成立、引数不正、提出なし、不明出力を同じ空の構文として数えない。

実API要求列は、実際に送信された要求だけをtyped receiptと対応させる。名前と全引数を保ち、JSON objectのキー順と外側の整形だけを統一する。認証値、商品ID等を除かない。返答とAPI例外、新規公開schemaの列は別のhashとして比較する。全Python内API記録が、その呼出しを含む外側の実行記録へ一度だけ結び付くことを要求する。送信失敗やAPI例外の費用も元監査から除かない。

両方が非空のAPI列である場合の一致と、一方だけ空、両方空、不明を分ける。両方空は同じ有効操作を実行した証拠にしない。一方、APIなしのPython計算やarchive参照が不要だとも扱わない。「提出を完了」は、提出した全ツールについて実行済みの記録がある意味で、Pythonの通常例外を含み、正解や課題成功を意味しない。形式拒否、未実行、実行結果不明は別に残す。

全対応枠に加え、生成直前までのAPI要求・返答・例外・公開schemaの全列が同じだった枠を記述的に集計する。初回の空prefixも含む。過去に作用不明がある場合はprefix比較を不能にする。この一致はPython変数、ファイル、DB、cache、残予算やモデル入力全体の一致を保証しない。片側が先に終わった枠はこの集計から落ちるため、全対応枠の結果も併記する。
