# P74：次の生成へ残るAPI返却と、現在のコード内の参照を分ける

P70はAPI返却の根を直ちに項目へ絞る構文を全12既知記録で点検し、候補０だった。名前へ保存された根144箇所を「将来も不要」とは扱っていない。今回はこの残りを、現在のコードだけで判定できる範囲へ分解する読取点検である。P70の不採用を覆して同じ自動射影を実行系へ接続する実験ではない。

対象はP70と同じ全12条件、181コード出現・117固有ファイル。P35の原入力ハッシュとP70の固定manifestを引き継ぐ。前半の重複96出現、継続81出現、状態一覧の制御４出現を全て残す。後の生成コードを前の需要判定へ使わず、保存コード・モデル・環境API・評価器・DB内容・保留群を実行／閲覧しない。

## 判定する構文と、判定しない意味

単一名へ直接束縛するAPI呼出しごとに、同じコード内の名前の読取を分類する。literal添字、literal get、動的項目、根全体の使用、項目変更、別名・コンテナへの引渡しを区別する。直後に同じ文の並びで明示的な上書き／削除があるか、ループ・分岐・関数の中か、動的名前空間アクセスがあるかを記録する。公開結果はAPI名・位置・許可済み項目名・集計・ハッシュに限り、値やコード全文を載せない。

「現在のコードでは項目だけを読む」と「次の生成へ根を残さなくてよい」を分ける。単なる最後の参照は根の破棄を意味しない。ループの途中で上書きされる変数も、最後の反復では次の生成へ残り得る。上書き／削除前に例外が起きた場合の名前空間、別名、動的型・関数・外部変更は構文点検だけでは同値性を証明できない。

同じ文の並びで上書き／削除までliteral添字しか見えない箇所を、正常経路の限定的な構文候補として数える。getの既定値、動的な参照、根全体の引渡し、条件分岐、関数・ループ内の根はこの候補に昇格させない。該当が０でも全件を残す。API要求回数、実際の利用量、不要情報、節約token、成功率へ換算しない。

## 次の方式を判断するための仮説

仮の設計は、未生成の将来コードを予測せず、生成境界で外へ残る値の完全性を保つこと。現在の項目需要だけで処理できた値も、次の生成・不明な呼出し・状態変更・例外へ移る前に、必要な完全値と取得時点の整合性を確保する必要がある。古い時点の値を後で新しいAPI返却で埋めることは同値とは限らない。今回その実行器は作らず、先に現在の実コードに対象構造があるかを調べる。

[LazyAgent §8.1](https://arxiv.org/html/2609.23058v1#S8.SS1)は通常の不要項目除去を対照に置き、既知の消費辺と現在の目標による需要を区別する。したがって正常経路で死ぬ値の項目選択を独自性とはしない。[Incremental Consistency Execution §3.1–3.4](https://arxiv.org/html/2609.24090v1#S3)も項目依存・再利用・変更時の伝播と作用前の版照合を扱う。将来コードが未定という差だけで新規性を成立させず、通常の依存・脱出解析を含む強い対照との差が必要である。

120秒、１ファイル４MiB、コード20,000字、AST5,000ノード。元181出現の範囲変更・再試行・追加モデル実験はしない。構文解析不能は未対応として残し、出典・計画・時間の不一致なら部分結果と未処理一覧を保存して停止する。固定版の合成反例検査とpush/PR両CIの成功後、別作業木で１回だけ点検する。候補が出ても同値性・費用効果・新手法とは扱わず、次の判断を記録する。
