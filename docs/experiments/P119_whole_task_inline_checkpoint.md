# P119: 通常の別呼出し要約と同じ応答に含める要約の全仕事比較

2026年10月25日. P118の全８条件と所有server、監査、対比較を閉じた後の開発比較. 原稿は保留し、未見12課題は開かない. この資料は実行前の規則であり、性能結果ではない.

P118では通常要約4/4、全保持3/4成功だったが、両側成功３課題の全費用は要約条件で4,243 token増えた. 写真では実行役の費用が14,212 token減り、専用要約18,455 tokenを加えると4,243 token増となった. CSVの要約成功も保持する. 専用要約２件の入力37,350 tokenは今回の節約実績ではない. [全件所見](../P118_findings.md).

## 問いと比較対象

同じモデルへの通常の行動要求に、古い完結履歴の要約も含めることで、専用の要約要求を省きながら、通常要約の成功を維持して全仕事の費用を下げられるかを調べる. 同じ応答に載せること、形式検査、履歴を要約することを新規性とはしない. 自然言語の意味を証明する新しい判定器は含めない.

`single_checkpoint` はP118の通常要約実装をそのまま使う. `inline_checkpoint` は通常の `run_python` の任意引数 `checkpoint` に要約を載せる. 全保持を再実行する比較ではない. 通常要約を弱い方式へ差し替えず、新しい同時期の４課題×２方式を各１回実行する.

両方式は初回要求、課題、world、モデル、通常のAPIとPython経路、予算、通常のtool schemaを共有する. 要約時には必要な指示、schema、時点、出力配分が異なる. この差を消すために通常要約側へ不要な要約出力を強制する対照は置かない. したがって、全費用差は方式全体の比較であり、専用入力の除去だけの因果効果とはしない.

## 固定する制御

両方式とも、元の全履歴に通常の予算通知を加えたnative入力が16,384 token以上で、閉じたやり取りが３回以上ある最初の機会を１回だけ使う. 元のsystem指示と課題、直近２回、以後の全やり取りを残す. 保存履歴と永続Python状態は削除しない.

通常要約側はP118と同じ別呼出し、温度0.7、最大4,096出力token、空toolsで、`completed`、`usable_state`、`remaining`、`uncertainties`を生成する. 次の行動要求と要約の共有予算の事前確認もP118と同じ. 形式不正、打切り、非短縮、予算不足では元の履歴を残し、再試行しない.

同時出力側は、対象となる古い履歴の直後に境界を示し、通常の行動要求に１回限りの指示と任意の `checkpoint` schemaを追加する. 通常の実行役と同じ温度1.0、同じ4,096出力token内でコードと要約を返す. 要約がコードの出力枠を使い、コードが切れたり行動が変わったりする可能性も結果へ含める.

同時出力の要約は古い完結履歴だけを対象とし、今回のコードの実行結果を予測させない. 今回のコードと結果は原文で残す. 受理するのは、返答がちょうど１つの `run_python` で、終了理由が `tool_calls`、基礎引数と要約形式が有効な場合だけ. 各欄は最大32個の文字列、１文字列は1〜2,048文字、compact JSON全体は8,192文字以内. 重複キー、余分な引数、非有限JSON値を修復しない.

コード本文と順序付き参照IDを一切変えず、引き継ぎ情報だけを取り除いた引数を既存の実行器へ１回渡す. 原応答はそのまま保存し、原引数、渡した引数、コード、参照ID、要約の指紋を対応づける. この対応は実行の成功や要約の正しさの証明ではない.

基礎引数が有効な場合、要約が不正または打切りでもコードは通常どおり扱う. 不正JSONや基礎引数不備では既存の形式エラー経路へ進む. 任意要約の欠落、複数tool、`read_span`、無tool返答でも機会は消費し、要約のために追加呼出しや再試行を行わない.

当該やり取りが保存された後、次の行動が必要な場合だけ、通常表示と要約表示を同じ現在予算でnative計数する. 要約表示が厳密に短い場合だけ採用する. 両表示とも、対応が確認できた同時出力metadataを現在のtool引数の表示から取り除く. これは重複表示を避ける追加の表示規則であり、不正要約や非短縮でも適用する. 原記録は保持する. 最終応答で仕事が終わった場合、不要な次入力計数はせず「次要求がなく採用未判定」と記録する.

## 実行と点検

同じ完全headのpushとpull_request両workflowおよび両accounting-and-syntax job成功後、専用固定木で一度だけ実行する. 初回８要求の課題内一致、通常の要約用経路１入力、合成の同時出力要求と採否候補２入力を、計12入力の語彙計数で確認する. 事前確認ではモデル生成、実API、独立評価を行わない.

新しいモデル生成を開始する前に全８条件を固定する. 中間成否を見て条件、順序、閾値、seed、予算を変えない. 不明なモデル使用量は０で補完せず、その返答を実行しない. API効果と後処理が確認できる場合だけ同じserverのidleを待ち、１回評価して次の固定条件へ進む. API効果不明、初期状態不一致、cache不一致、実行環境や後処理や評価の故障では全体を停止し、失敗を残す. ユーザー停止を優先する.

全８枠と所有serverが閉じた後、全要求の実payload、native計数対象、原応答、実行へ渡したコードと参照、保存履歴、要約の採否、全役の費用を照合する. 不明、失敗、未実行、未評価も残す. 評価の正解や追加テストはモデルへ返さない.

採用基準は全８件が評価済みかつ使用量既知、点検不一致０、課題ごとの成功損失なし、両側成功が１件以上、全４課題と両側成功課題の両方で同時出力方式の全tokenが少ないこと. 成功損失を安い失敗で相殺しない. host制御、計数、実行、再取得を仕事時間へ含め、cache済み入力、出力、呼出し数、API、準備、後処理、評価、load、server滞在を分けて記録する. token差を時間や料金の差へ換算しない.

この比較が成功しても４つの既知課題での開発結果であり、一般的品質保証や新規性の確立ではない. P111の不明２件、P118の不明１件、両実験の採用基準未達を保持する. [検討範囲](../inline_checkpoint_candidate_scope_20261025.md)で未定だった通常対照を具体化した段階であり、実行情報による意味検査の新手法を実装したとはしない.
