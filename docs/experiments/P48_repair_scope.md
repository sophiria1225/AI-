# P48：修復を小さい入力へ切り分けられる範囲を点検する

2026年10月22日。P47の終了・全件監査後に選ぶ事後診断。拒否の詳細返信を追加しても、選択表示は写真の成功を失い、全４課題比較も完遂しなかった。次に「エラー後は小さい入力だけで修復できる」と仮定する前に、拒否が単純な引数削除、名前変更、値の変換、API発見のどれに関わるかを実記録で区別する。

## 対象と有限の範囲

固定した[P47監査](../../reports/P47_comparison.json)の全12予定条件を残す。実行済み10条件の全保存プログラムを読み、未実行２条件は未実行のまま記録する。全形式拒否を対象とし、後続が成功したものだけへ限定しない。120秒以内、追加生成・実API・計数・コード再実行・評価器・保留12シナリオ閲覧はすべて０。[固定設定](../../configs/P48_repair_scope_v01.json)。

## 測る内容

1. 拒否の送信有無・作用不明・公開済み契約の有無と、元の引数名・型。引数値、認証、原コード、要求文は出力しない。
2. 保存PythonのASTに同じAPIを直接指定する呼出し箇所が何か所あるか。ループ・分岐・関数・例外処理内か、動的な呼出しがあるかを数える。静的な１箇所を、実際のループ反復や復帰点の同定と取り違えない。
3. 後続に同じAPIの実送信があれば、引数名の追加・削除、同名値の保持・変化、同一型・同一値の移動候補を数える。これは後から観測した修復の形であり、実行時に利用できる修復案・正解・意味的同等性ではない。次の送信がなければ欠測として残す。
4. 既公開の引数なしAPIへ余分な引数を付けたものを独立に数える。通常の引数正規化の候補であり、新規な推論方式としない。型・名前だけでは意味の一致を保証しない。

元の入力・プログラム・イベント・監査のハッシュを照合し、全件の対応が壊れた場合は停止する。文字数や次の生成費用を、実測の削減量や削減可能な上限へ変換しない。新しいモデル実験はこの診断から自動開始しない。

## 次の候補へ必要な差分

全履歴を使う通常の継続、エラー＋契約だけの修復、既存の修復範囲制御を対照候補にする。局所入力に必要な意味情報があること、作用を二重に実行しないこと、修復・合流・失敗を含めた費用と最終品質を、別々の条件として示す。診断器の完成をレターの技術的新規性とはしない。
