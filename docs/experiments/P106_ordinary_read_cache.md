# P106: 通常の完全応答キャッシュを両方式に与える比較

P105では同じ手書き７段階が全方式で同じ出力を返し、APIは即時13、元の遅延16、参照共有12だった. しかし、即時方式との差１回は、段階６の通常`call_api(show_song)`が取得済みの完全応答を再利用しないことによる. 途中の取得省略は後段で戻っていた. この原因を明示してから、通常呼出しにも完全応答キャッシュを与える対照を追加する.

## 固定する２方式

`eager_cached`と`coalesced_cached`の順で、同じ既知課題の新しい環境を１回ずつ作る. P105の７プログラムを一文字も変更せず、同じ初期公開情報、seed 42、API上限20を両側へ与える. 遅延版だけに通常キャッシュを追加することはしない.

新しい共通部品は、検証済みの`show_song`について、同一実行範囲・状態版・全引数の完全応答が既にある場合だけ、その深いコピーを返す. 現在のAPI権限と引数を照合し、部分値、未検証のAPI、曖昧な複数応答は完全応答の代わりにしない. 状態変更時の取得と失効、未知作用時の停止は既存方式を保つ. 実APIを送信しないキャッシュhitは０回として記録し、残りAPI予算が０でも他の予約を消費せず返す. 他の部分参照が残っていても、その予約を勝手に取り消さない.

| 方式 | ７段階の期待API数 | 合計 | 通常呼出しの完全応答再利用 |
|---|---|---:|---:|
| eager_cached | 6, 1, 0, 1, 0, 1, 3 | 12 | 1 |
| coalesced_cached | 6, 0, 1, 0, 0, 1, 4 | 12 | 0 |

これは実行前の期待値であり、実環境の結果ではない. 段階ごとの取得時点は違うが、同じ完全応答キャッシュを与えた場合に最後のAPI数が揃うかを確認する. 全７段階の標準出力を両側とP105の保存hashへ照合する. プログラムや対象を変えて差を探さない. 期待値、返却、会計が異なれば、その結果を残して停止する.

## 範囲と費用

２環境、手書き14段階、設定２回で最大16 Python実行. 各方式20 API、総40 API、全能動処理300秒、１プログラム30秒、bridge30秒. 既存の有限な後片付けを含めて記録し、所有していないプロセスやコンテナへ触れない. 再試行０、停止印は `.runtime/P106.stop`.

P102、P104、P105の閉鎖記録とP105の保存記録照合を前提に、固定ソース、プログラム、公開実装、既知課題説明を最終計画へ結びつける. 同一完全headのpush/PR両workflowと両accounting-and-syntax job成功を確認してから一度実行する. API数、予約残高、キャッシュ利用、制御通信、設定、終了費を全件残す. 保存記録の照合と全14段階・全２方式の集計処理も事前に用意する.

モデル生成、保存されたモデルコードの実行、課題評価、未閲覧12シナリオ参照は０. 通常キャッシュは比較を強めるための既存技術で、新規方式として扱わない. 両側が12回なら、P105に残った１回差を遅延取得の独自な優位性の根拠にしない. 別の課題で遅延取得が役立つ可能性まで否定する実験ではなく、自然な課題での出現頻度、最終品質、LLMトークン削減を測るものでもない. 原稿の逐次改訂は保留する.
