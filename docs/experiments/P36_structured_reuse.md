# P36：別の既取得情報による要求代替の成立範囲

P35全件確認後、2026年10月22日に定める開発用の記録分析。対象は同じP33全12条件。モデルやAPIを再実行せず、未閲覧課題は使わない。値を先に知る実装を運用方式として評価しない。

## 問い

通常の同一API名・引数のキャッシュでは拾えない、別の読取結果に含まれる同じ対象・項目があるか。ある場合も、単なる一致なのか、意味・版・要求を照合して実行時に再利用できるのかを分ける。

## 固定する探索規則

1. 既知の公開API文書でGETの要求に限り、正常返却を候補にする。GET表記だけで副作用・鮮度を保証しない。
2. 同じアプリと、同じ認証引数の範囲でのみ照合する。認証値はメモリ内の比較だけに使い、値やその単独ハッシュを公開しない。
3. 対象を指す引数候補は `_id` で終わるもの、または `file_path`。正常返却が辞書で、その引数と同名・同型・同値の項目がちょうど１つある場合だけ調べる。名前・文字列類似やパスの別名は正規化しない。
4. 過去の読取結果の辞書・リストから、同じ識別子候補を持つ辞書を探索する。外部キーも混じり得るため、これは対象の同一性を証明する規則ではない。衝突を除外せず記録する。
5. 複数の過去候補で値が違う項目は衝突とし、後の正解返却を見て正しい候補を選び直さない。API名・引数が完全一致する通常キャッシュも同時に測る。
6. 実際に送信された非GET・未知の操作があれば、全アプリの候補を無効化する。未送信要求で状態が変わったとは扱わない。GETの失敗・不明応答を再利用候補にはしない。

各要求の候補は、その時点より前の返却だけから構成する。その後、保存済みの実際の返却と項目ごとの一致・差異・不足を照合する。現在の返却を候補へ追加するのは照合の後とする。

## 得るものと、まだ得られないもの

全12件について、読取要求数、通常キャッシュの一致、識別子候補一致、共通項目の一致・衝突・不足、別APIを由来とする一致を記録する。要求ID・項目の値・認証情報・原コードは公開しない。走査上限も記録する。

実際の返却を使った事後の一致率は、対象同一性・鮮度・必要項目の推定が完全な場合の余地を調べる分析であり、節約可能なAPI数・トークン数ではない。コードが必要とする項目が実行前に分からなければ、この分析だけで省略できない。全文を印字する場合、部分一致だけでは代替できない。

次へ進める条件は、一致があるだけではなく、対象・必要項目・版・副作用を実行前の情報だけで判定できる具体的規則を定義できること。部分キャッシュや問い合わせ最適化の一般原理は既存であり、新規性は別に確認する。
