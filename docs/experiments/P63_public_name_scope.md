# P63：公開名で呼べる通常Python基準の部品と適用範囲

P62で時刻APIが未公開として拒否されていたことから、標準AppWorldと独自接続の呼出し条件を点検した。インストール済み0.1.3.post1の公開 `ApiCollection.load` は、許可されたアプリの公開API名を初期化時に束縛する。呼出し前の説明取得はその関数の前提条件ではない。一方、当研究の `NativeCatalog.decode` は説明が露出済みかどうかでも拒否している。

`PublicNameCatalog` を別の通常比較用部品として追加する。Python RPCが既に知る正確な公開名を指定した場合、固定された公開catalogの名前・引数キー検査を使う。非公開・未登録・タイプミスの名前は受理しない。値の生成や変更、説明の自動取得、再試行はしない。文書取得後の公開スキーマ更新、環境側の引数・認証、既存のAPI・時間上限、完了後停止、作用不明後停止をそのまま使う。

元のNativeCatalogと過去の方式は変更しない。明示されたnative関数呼出し用のスキーマsnapshotも迂回しない。Python内で表示する `api_schemas` やモデルに見せる定義は、明示的な文書取得に従う従来どおりの集合である。「呼べる名前」と「説明を見せた名前」を分ける通常の接続で、独自アルゴリズムではない。

最初の点検は保存済みP29全４実行とP55全12条件に限る。公開アクションと当時のスキーマ更新を順番に読み、従来拒否された要求のうち名前と引数キーの検査を通るものを数える。P55の前半はP29からの再利用を含み、16独立課題や実API実行件数とは数えない。途中の実行結果が変わった場合の後続経路は推定しない。

上限120秒、6,000イベント訪問。モデル生成、環境API、記録したプログラムの実行、評価、保留群閲覧は０。元の出典・公開スキーマハッシュの不一致、作用不明、既に通っていた要求の変化は停止する。個々の引数値、資格情報、原プログラムは公開結果に出さない。

この点検で呼べる要求が増えても、API成功、完了、品質、総費用削減は未測定である。実際の比較には、元と新しいインターフェースの説明を正しくそろえた新計画、有限予算、同一headのCI確認が別途必要。保留12シナリオは使わない。過去P55の局所比較を取り消すのではなく、その接続条件と一般化の範囲を明確にする。
