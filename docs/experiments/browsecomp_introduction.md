# BrowseComp-Plus導入：質問を見る前の選定と評価分離

既存AppWorldの短い開発課題だけで研究の必要性を決めないため、固定された全コーパスの検索・調査へ評価候補を広げる。最初の12問は環境確認と失敗の観察に使う開発用で、主実験の件数・方式・成功率を決めたことにはしない。

## 先に固定する選定規則

公式配布のtest 830問から、**query_idだけ**を読み、固定文字列とIDのSHA-256順で先頭12件を選ぶ。[選定方針](../../configs/browsecomp_development_selection_v01.json)をID列の取得前にコミットする。本文・回答・正解文書で候補を入れ替えず、順番やファイル分割にも依存しない。重複ID、件数違い、配布版違い、ID以外の入力列があれば停止する。

12件は性能差の結論を出す件数として選んだのではなく、設定確認と複数の失敗を観察する導入規模である。1件だけの手作業選別、全830件の初回一括実行、正解文書だけを渡す簡略化は採らない。残り818件は未使用候補として保持するが、関連質問や事前学習への混入を検査していないため「独立な盲検テスト」とはまだ呼ばない。

## 元データから実行側へ渡すもの

選定後に、選んだ12件のIDと質問だけを実行入力として作る。回答、gold_docs、evidence_docs、negative_docsのラベルや課題との対応は評価用領域へ分ける。エージェントへ任意のシェルや評価ファイル閲覧手段を与えず、全コーパスの検索と文書取得に限定したツールを提供する。

検索対象は100,195文書の全体を維持する。公式のBM25索引は導入の先候補であり、強い検索器より優れると判断したものではない。検索失敗と、取得済み情報の保持・統合失敗を分けるため、検索要求、順位、文書ID、原文位置、保持・再読、全入力＋出力を記録する。正解文書のIDで検索結果を補正しない。

追加の公開コード確認では、[固定版のBM25検索器](https://github.com/texttron/BrowseComp-Plus/blob/046949032b0328319cc9a02663a759ec601d9402/searcher/searchers/bm25_searcher.py)が索引内の保存原文を検索結果と文書取得に使っている。まず質問側とBM25索引（合計約4.95GBの配布物）で導入し、全100,195文書の件数と原文取得が確認できれば、別形式のコーパスParquetの重複取得は開始条件にしない。索引の欠損・原文取得不足があればそこで停止して、コーパスを追加取得する。これは保存の重複を避ける通常の実装選択であり、文書数や検索対象を減らす選択ではない。

公式の復号処理は回答と関連文書も一緒に出力するため、その出力を実行側へそのまま渡す案は採らない。選定器の入力はIDのみ、実行入力はIDと質問のみを許す投影で分離する。未知の追加列をそのまま転送する実装にしない。

## 評価と資源の未確定点

回答評価には公式判定方式を確認して接続する。Qwen3-32Bの量子化や推論基盤を変える場合は、公式実行と完全同一とせず判定の一致を別に確認する。文字列一致だけを公式スコアに置き換えない。正解データは実行終了後の別プロセスでのみ使い、結果を同じ課題の実行へ戻さない。

Java 21・索引の実機動作、実作業容量、読み出し時間、質問内容の難しさはまだ未測定。大容量データの取得・展開と重い依存導入は、実行中のP13時間測定へ重ねない。配布版・容量の確認は[導入前調査](../browsecomp_preflight_20261021.md)を参照する。

取得器は固定版のファイルサイズとLFS SHA-256またはGit blob SHA-1を照合し、部分失敗を残す。既存ファイルの無条件上書きや途中ファイルの削除はしない。実行前にP13終了を要求し、単体検査ではサイズ・ハッシュ・パス変更を拒否することを確認する。実ダウンロードの成功や索引実行の確認は、この検査とは別に記録する。

この文書の時点で、質問ID列の取得・選定実行・本文の閲覧・データ復号・検索索引の実行・モデル生成はまだ行っていない。実施時に、実際の件数・版・ハッシュ・閲覧範囲を追加記録する。
