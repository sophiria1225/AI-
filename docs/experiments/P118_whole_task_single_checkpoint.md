# P118: 一度だけの通常要約を共有費用で比べる

P111〜P117を閉じた後の、既知４課題×２方式×各１回の通常対照比較. 新提案の確立、PAIRの再現、初期台帳P14の再試行ではない. P14では更新生成の負担が大きく、P111/P114では単純な推論省略が採用基準へ届かなかった. 現在の持続Python経路で、未完了事項を短い記録へ残す通常方式を同じ費用枠に接続する. 過去の全結果と未知使用量を維持する.

## 比較する表示

`full`は原履歴を全て提示する. `single_checkpoint`は、実行役へ渡す入力をnative tokenizerで数え、初めて16,384 token以上かつ完了した会話ターンが３つ以上となった機会に、１回だけ要約を検討する. 閾値は64K文脈の４分の１として固定し、結果を見て変更しない. `full`側も同じ機会まで入力を計数するが、要約しない.

原system指示とtask、直近２つの完結したassistantと観測の組はそのまま保持する. 古い部分だけを、completed、usable_state、remaining、uncertaintiesの４項目からなる通常の生成要約へ置き換える. 要約役には元指示、古い履歴、直近の文脈を記録として渡す. 実際のPython状態と完全保存履歴は保持する. 要約役のtool schemaは空で、返した操作要求を実行しない.

要約は同じM3、推論予算−1、出力最大4,096、温度0.7で１回だけ生成する. 完了理由stop、重複しない正確な４項目、文字列の配列、全体8,192文字以下を検査する. 正常終了や形式適合は内容の正しさを保証しない. 打切り、空、不正形式、操作要求を含む出力なら元履歴を使い、追加の修正生成をしない. 同じ更新後の予算通知を含めたnative入力計数で、要約後が短くならなければ採用しない. この比較は直後の入力差であり、将来の費用効果の証明ではない.

要約と次の実行役に別々の予算を与えない. 生成前に、要約入力＋その最大出力＋現在の実行役入力＋最大出力が残予算に収まるかを確認する. 通知の数字は要約後に変わるため、これは現入力での事前判定であり、次要求の最大出力を保証しない. 実際の次要求は改めて計数・予約する. 呼出し枠が２回分なければ要約しない. 要約機会を見送った場合も再検討しない. 使用量不明なら推測で費用を埋めず、その条件の継続を止める.

## 共通経路、順序、有限予算

P99/P111の公開API schema feedback、型付きAPI、例外提示、隔離した持続Python、auto tool choiceを共通に使う. ReadViewや新しいAPIキャッシュは接続しない. 原文推論も保存し、全保持側では毎回提示する. 要約側も要約前は全保持で、要約後は残した２ターンと以降の原文推論を提示する.

| 既知課題 | 固定順序 |
|---|---|
| 写真 | full → single_checkpoint |
| 精算 | single_checkpoint → full |
| 返金 | full → single_checkpoint |
| CSV | single_checkpoint → full |

同じモデル重み・llama.cpp・65,536 context、世界seed42、実行役seed57＋その役の要求番号、温度1.0を使う. 要約役のseedも役内で57から始め、要約呼出しで実行役のseed番号をずらさない. 初回要求は同一でcache_prompt=false、実測cache_n=0を確認する. 以後は通常のprefix再利用を許し、要約による再処理も実測へ含める. 同じseedで同じ生成が保証されるとはしない.

各条件は、要約を含め80モデル呼出し、450,000論理input＋output token、1,800仕事秒. 写真160 API、他80 API. setup120秒、cleanup180秒、idle60秒、独立評価180秒. 全体予約は８条件、640呼出し、3,600,000 token、800 API、８評価. 要約呼出しはこの内数で最大４回. 所有serverは最大21,600秒で、終了時に停止する. 予約量を実消費とはしない.

同じ完全headのpush・pull_request両workflowと両accounting-and-syntax job成功後に固定実行木で開始する. 開始前に全８初回要求の同一性と計数、空toolの要約経路１入力の計数を確認する. この事前確認は生成０. 元の固定計画・既存結果の指紋も確認する. ユーザー停止または`.runtime/P118.stop`で停止する.

API作用不明、初期化不一致、cleanup失敗、runtime不一致、評価失敗はbatch停止. 使用量不明は未知のまま残し、その応答を実行しない. 次条件への移行は既存の終了状態判定とidle確認に従う. 未実行・未評価を含む８枠を残す. 全条件と所有serverが閉じてから成否比較を読む. 成功例選別、閾値やseedの探索、欠測を埋める再試行はしない.

## 評価と限界

要約の生成・不採用・失敗、実行役の全入力・出力、再取得、回復、ホスト処理を仕事費用へ含める. cached token、時間、論理token、料金は区別する. 主品質は後から独立評価する最終task success. 評価結果を実行役や要約へ戻さない.

通常対照として有望とするには、全８件の評価と使用量が既知、監査不一致０、課題ごとの成功損失０、両側成功が少なくとも１件、全４課題と両側成功課題の双方で総論理tokenが減る必要がある. 安い未達だけの減少を採用しない. これを満たしても新規手法や一般的な品質維持とはしない. P111の不採用を取り消さない.

現在の４課題と過去結果を知った上で設計した開発比較であり、未知課題への確認ではない. 初期P14とは課題・実行経路・更新規則が違い、数値差を要約頻度だけへ帰属させない. [PAIRとの範囲比較](../counterfactual_adaptation_prior_scope_20261025.md)も保持する. 原稿と未見12課題は保留する.
