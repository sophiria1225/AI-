# P13：同じ接続でFOCUSに基づく保持方式を比較する

P11の全履歴、P12の直近履歴に続き、将来計画と救済によって履歴を選ぶ既存方式を同じ4開発課題で比較する。目的は、安価な直近保持を超える価値が追加の生成費用を含めても残るかを調べること。独自手法の提案ではない。

## 固定する実行条件

4課題・順序・元環境、MiniMax M3 IQ4_XS、64K、KV q8_0、標準会話、公開APIの発見と実行、原文再読はP11/P12と同じ。各80モデル呼び出し・80 API要求・450,000総入力＋出力・1,800秒・1生成4,096。保持役の全呼び出しもこの総枠を消費する。課題を成否で選び直さない。

実行役は温度1.0、保持草案は既存設定0.7。呼び出しの種は役割ごとの実行回数に基づくため、保持呼び出しを追加しても実行役の種の順序は変えない。ただし呼び出しID、数値演算、コンテキスト等により完全な軌跡再現は保証しない。1試行だけで品質同等性を結論づけない。

## 保持の手順

1. 前回の保持集合に新しい実行結果を加える。捨てた原文はローカルのアーカイブに保持し、実行役はread_spanで再読できる。
2. P12と同じく、system・元taskを除いた会話のJSONをモデルのトークナイザーで数える。4,096以下なら保持生成を呼ばない。
3. 超えた場合、元task、現在見えているspan、実行役へ公開済みのAPI仕様を保持役へ渡す。API仕様はデータとして渡し、保持役が呼べる機能はsubmit_selectionだけ。記憶を作るために環境操作を実行しない。
4. 各草案は今後の計画、判断に必要なspan ID、計画で参照しなくても失うと危険なspanを返す。最大3草案・保持閾値0.3なので、1草案以上が参照したspanと救済されたspanの和集合を選ぶ。
5. 残りの草案がどうなっても全spanを保持することが確定したら、そこで草案を終了する。先行草案の不備はこの証明に使わない。途中出力が不正なら元の履歴を保つ。通常の早期終了であり新規性ではない。
6. 選んだ操作を含む元の応答全体と、その全結果を残す。複数操作の一部だけを選んでも、対応を保つための同じ応答の他操作も残り、その追加分を記録する。
7. 保持更新は実行役の次の呼び出しの前に最大1回。目標サイズへ収まるまで再生成するループは作らない。全保持や4K超過も結果として記録する。

更新後にトークンが足りず次の操作へ進めない場合も、使った保持費用を戻さない。失敗・打ち切り・使用量不明を除外しない。

## 原方式との関係と補完

[FOCUS原稿](https://arxiv.org/html/2609.37590v1)の将来参照・防御的救済、3草案・0.3の規則を基にする。確認した範囲は[原典照合記録](../technical_core_review_20261021.md)へ保存済み。原モデル・元のコード実行エージェント・原論文のスコアを再現した実験ではない。

標準API会話への適合点は、構造化した提出機能、同じ応答の操作・結果をまとめて残す規則、現時点で公開済みのAPI仕様の明示、原文再読、全保持確定時の早期終了。原稿例の本文だけを渡す案では、実行役がtools欄から得ている仕様を保持役が知らずに将来計画を作ることになるため、今回は同じ公開情報も渡す。仕様の追加入力は無料にしない。

この適合によって保持が保守的になったり、入力費用が増えたりする可能性がある。完全再現を装わず、保持規則だけの原理、実装上の補完、実行結果を分けて報告する。旧P6の失敗をそのまま比較値として流用しない。

## 実行前に見つかった不具合

保存した保持IDのリストを次の更新も参照しており、新しい観測の追加が過去の判断記録まで変えていた。原入力から記録を再計算する検査で検出し、リストを独立して保存するよう修正した。回帰検査、保持生成の費用・非実行性、保存点の0→1→3呼び出しという対応を確認する。P13の実モデル生成前に検出した不具合で、既に実行中のP12は別の固定ソースを使っている。

## 何を成果として読むか

全履歴・直近履歴と、最終成功、総費用、保持生成の比率、実際に取り除いた履歴、再読、余計な操作、時間を比較する。草案が詳しいだけ、削除量が多いだけ、単純対照より高価なだけでは有効性を主張しない。通常対策で十分なら追加機構の必要性は弱いという結果を残す。

実行後は保存済みの草案・計数結果から保持判断と実入力を再計算する。意味的な正しさまで機械的に保証したとは扱わない。大規模・長期作業への主評価、別モデル、反復を含む確認は別途必要である。
