# P94：照合済みの公開履歴を再構成した状態で保存次出力を実行する

## 問いと限界

P93で確認した構文差が、新しく再構成した状態で実際の要求列・実行結果の差になるかを調べる。全18出力を同じ定義の初期世界と公開履歴から比較し、元のモデル生成、全仕事成否、採用基準は変更しない。新しい制御方式の性能実験ではない。

元のP80/P81第２反復の14生成目直前には、12個のPythonプログラムと28実API送信が残っている。13生成目は引数形式エラーで実行されていない。２記録の先行12コードのhashは一致した。ただし当時の境界DB、Pythonプロセス、乱数状態全体のスナップショットはない。**元の完全状態を復元したとは主張しない。**

対象状態を「既知課題 `6104387_1` をseed42で新規初期化し、P80の先行12プログラムを順に実サービスで実行し、保存した要求・返答・標準出力・例外・公開スキーマ集合へ全て一致した状態」と定義する。不一致の返答を保存返答へ差し替えず、不一致後の続きへ進まない。公開履歴が一致しても、隠れた内部状態の一致までは証明しない。

## 固定条件

- P84と同じ全６入力・各３出力、全18件を元の固定順で使用する。P93で構文や終了理由を知った後の事後比較であり、独立確認とはしない。
- 各条件を別の新しい世界とPythonコンテナから開始する。先行12プログラム・28 APIの再構成費を毎条件計上する。元の課題のAPI上限80を使い、再構成後の残枠は最大52とする。
- 保存次出力を一度だけ通常の `execute_response` へ渡す。構造化ツール提出のない本文からコードを抽出・修復しない。13生成目の形式エラーも元の公開履歴へ残す。
- 全体の能動期限1,200秒、条件ごと180秒、１プログラム30秒、橋の１要求30秒。実APIは全体最大1,440件。18回の初期化、各最大13プログラム（先行12＋次１）の実行を予定するが、本文だけの６件では次プログラムを実行しない。
- 先行返答・要求・標準出力・例外・スキーマの不一致、未知の作用、利用不能なPython、後始末や会計の不整合で残りを止める。既知のAPI例外は記録どおりなら通す。続きの通常実行エラーや予算停止も結果として保持する。不足枠を補充しない。
- モデル生成０、評価器０、保留課題の読取０。既知課題のDBはサービス内の通常実行で使用するが、内容を直接照会して解答や完了判定を取り出さない。コードは既存のネットワークなし・ホストマウントなしの隔離Pythonでだけ実行する。

## 計測と判定

全条件の先行照合、次出力の構造化提出数、実行プログラム数、送信API名と要求列hash、公開実行結果hash、状態・例外、実行時間、後始末を記録する。APIの送信、サービス返却、既知例外、結果不明を分ける。生成回数と構文上の呼出し箇所数をAPIの実行回数に置き換えない。

全18枠と全15入力間組を保持する。両条件の先行照合が成功し、両方に構造化提出がある場合だけ実行された操作として比較する。本文のみでAPI０の２条件を有効な実行の一致へ加算しない。９対は３出力ずつの組合せであって独立標本ではない。全件完了を満たさない場合は予定全体の成立判定を保留し、途中結果だけで全体成立としない。

当時の実時間残量とモデルのwarm cacheは再現しない。新しい再構成状態での１応答だけの実行を、元の継続軌跡、最終課題品質、一般的な意味同値、token節約、手法の新規性へ拡張しない。P82全４採用基準未達、P88の両方式3/4成功、未見12課題の保留を維持する。
