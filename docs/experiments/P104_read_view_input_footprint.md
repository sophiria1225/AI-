# P104: 遅延読取の取得省略と入力トークンを切り分ける

## 問いと対象

明示的な遅延読取の終了済み実サービス確認では、同じ手書き６プログラムの標準出力が一致し、即時取得11 APIに対し遅延取得10 APIだった. これは未使用参照１件の取得回避であり、LLM入力や実課題総費用の削減を示していない. P104は、この全６段階を現在の会話形式へ入れた場合、次の入力のどこに差が出るかを調べる.

元記録は `public_read_views_live_v01` の２条件・12プログラム・21 APIを全て使う. 手書きの限定例で、モデルが生成した操作列ではない. 既知の課題説明を共通入力にするが、その課題を解いた記録とは扱わない. 予約評価群12課題を使わない. 現行原稿の逐次改訂はユーザー指示により保留する.

## 固定する再構成

`execute_response` に保存結果を返す専用callbackを渡し、実API記録を元順序で登録する. 元のPython文字列は実行しない. `run_python`、`span_ids=[]`、空のassistant本文、共通の明示的ReadView説明を新たに与える. これらは過去に送られた実LLM要求の復元ではなく、事後に固定する比較用の入力構成である. 同じコード、課題、説明、表示上限を両条件に適用する.

`view_program_private.json` の補正済み結果を使う. 下層の `result_private.json` にある制御RPC数を実API数へ読み替えない. 元の公開標準出力hash、成否、API数、切詰め、不明作用、完了宣言、実行時間、制御通信量と照合する. 私有ファイルのhashはP104準備時に追加固定するもので、元実験前の事前登録とは称さない. 元の終了statusと既存公開結果の結合も確認する.

各条件について、全６プログラムの直後の入力を２表示で計数する. 計24入力、12組の比較を全て保存する.

| 表示 | 内容 | 解釈 |
|---|---|---|
| harness | 通常の外側観測を維持. 実API数、API受領参照、実際の登録順のspan ID、標準出力等を含む | 現在の入力経路を通した記録の差 |
| content_attribution | 標準出力、成否、切詰め、完了、不明作用、エラーを維持. API数と受領参照を除き、外側IDをプログラム番号へ固定 | メタデータ以外の差を確認する計測用の除去条件. 実装済みの情報保持方式や品質保証ではない |

標準の `StableReferenceConversation` と既存のページ分割を共通利用する. API本文は元々ホスト側にあり、印字されないAPI値を新たにLLMへ流さない. 第６段階後も漏らさず計数するが、実際に続くモデル呼出しではない. 各境界の入力token差とprompt/token列の一致を示し、24入力を合計して「実際の全仕事token使用量」としない. 対数を独立課題数としない.

## 実行範囲と停止

- 推論サーバを作らず、固定済みP83のvocabulary-onlyバイナリ、同じモデル語彙・テンプレート・runtimeを使う. 新規decode・モデル生成・API・Python実行・評価・課題DB参照は全て０.
- auto、reasoning budget -1、seed 70、temperature 1、max output 4096、cache falseを共通の描画設定とする. 生成自体はしない.
- 元バイナリは６入力単位なので、即時/遅延×２表示の４batchを順次１回実行する. １batch120秒、標本化RSS2 GiB、全体600秒、各JSON16 MiB以内. 途中失敗、欠落、hash不一致は保持して停止し、追加入力・再試行・代替結果を作らない.
- P101の所有推論器が閉鎖した後にのみ実行する. P102の全36枠実操作確認を優先する. 停止印 `.runtime/P104.stop` とユーザー停止を尊重する.
- 同一完全SHAのpush/PR両workflowと両accounting-and-syntax job成功を確認してから一度だけ実行する. 完全な要求、API値、アカウント情報、stdoutは私有領域に保存し、公開するのは計数、hash、範囲、資源記録だけ.

## 判断

本文が同じでメタデータだけが減った場合は、その範囲に限定して記述する. 両方の入力が短くなっても、出力生成、実課題の品質、後続の再取得、制御費を測っていないため、全仕事の改善や新規性を主張しない. 大きなモデル比較を増やす前に、今回の機構に入力削減の経路があるかを具体化するための小さな確認である.
