# P38：必要項目読取の実行器への接続と、１課題の利用確認

P37で全12記録を照合した後に定める開発確認。SongのAPI対しか契約を確認していないため、対応する既知の書出課題 `P29_04_CODE` の８応答後のみを使う。選定はP37の結果を見た後であり、独立評価用の新課題や一般的な性能比較として扱わない。12未閲覧シナリオは使わない。

## 実装と通常対照

既存の隔離Python、API発見、予算、エラー、完了、記録の経路へ明示項目読取を接続する。原 `call_api` の返却は全体を維持し、新しい `read_fields` を使った場合だけ指定項目を返す。元のAPIが未発見・不正・予算外・完了後なら、キャッシュがあっても通さない。同期的な要求の応答後、次の要求を処理する前に、未知・書込操作の候補を無効化する。並列の変更や外部更新へ一般化しない。

３方式：毎回取得、同一要求キャッシュ、同一要求＋P37の別API契約。全方式で同じ全履歴、同じ説明、同じ関数を与える。キャッシュの方式名はモデルへ知らせない。２つのキャッシュ方式は原APIの全返却も再利用でき、対照を新関数だけに制限しない。モデル自身が必要項目を選ぶ。現在の返却、正解、評価器から必要項目を教えない。

## 条件と実行順

[固定設定](../../configs/P38_projected_reads_v01.json)。上の３方式を順に各１回。元と同じモデル・設定・前半、後続16生成／12万トークン／480秒、前半を含む80 API。ヘルパー導入・索引・照合の時間を後続費用に含める。復元用の操作は別枠で計測する。失敗を同じ条件で成功までやり直さない。

前半のAPI返却・保存DB・Python処理の対応と、全方式の初回入力が同じことを事前確認する。完全なプロセス状態・将来経路の一致とはしない。生成前にコード・設定・境界を固定する。独立評価は各方式が終了して選んだ最終成果へ１回ずつ行い、途中候補の採用や方式調整には使わない。

## 得たい情報と限界

まず新しい読取が利用されるか、通常キャッシュだけで足りるか、実際に別APIの過去結果を使うかを確認する。全３件の最終成否、全トークン、実送信、拒否、再利用、取得失敗、制御費用を残す。

１件の成功や11件の再利用を、一般的な品質維持・総費用削減の結論にしない。使われなければ利用されなかったと記す。単なる再利用機能や契約追加は既存研究との差にならないため、この機構確認の結果だけでレターの新規性が成立したとはしない。
