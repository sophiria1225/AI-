# P78: API失敗の通知方法を課題の最初から比較する

状態: 実装と実行前確認中。生成・課題評価はまだ行っていない。

研究の最終目標は、必要な情報と処理を保持し、最終品質を保ちながら、制御、失敗、再取得を含む仕事全体の費用を減らすことである。P76では推論履歴の保持が写真整理で局所的に効いた一方、他課題の未達と費用増加が残った。P77の公開履歴診断と型付きAPIの実環境確認を受け、比較基準の失敗処理を独立に検証する。

## 問いと位置づけ

同じAPI呼出しで発生した例外を通常の文字列として渡す場合と、Python例外として渡す場合で、回復行動、最終成否、仕事全体の費用がどう変わるか。

両条件で同一の型付きブリッジを用いる。成功時の戻り値と型は同じであり、`success: false` のような通常の戻り値を例外に読み替えない。公開APIの実際の例外だけを比較対象とする。

| 条件 | 確認済みAPI例外の渡し方 | その他 |
|---|---|---|
| error_value | 例外型とメッセージを通常の文字列値として返す | 下記共通条件 |
| error_exception | 同じ文字列を含むPython RuntimeErrorを発生させる | 下記共通条件 |

変換は共通のAPI受付と例外記録の後に行う。失敗したAPI説明要求から新しいスキーマを公開しない。未知の結果を文字列に変換しない。例外発生は副作用の取り消しを意味せず、自動再試行を行わない。両条件とも、完了通知とAPI予算を同じ場所で制御する。

これは失敗通知だけを操作する診断的比較である。error_valueは旧実装のトレースバック文字列と完全に同じではない。P29/P76の再現や因果対照とは呼ばない。型付き値、例外、状態保持、推論履歴保持そのものを新規手法とはしない。

## 固定した対象と共通条件

既に観測済みのP29の4課題を元の順序で使う。新しい課題、未開封12課題、隠された評価条件は読まない。過去の最初の公開課題記録をハッシュで固定し、新規環境の公開初期状態を毎回照合する。過去のモデルプログラムや8応答の接頭部は再実行しない。

推論履歴は最初の応答から全て保持し、永続Python、公開API名によるアクセス、公開履歴、24,000文字の既存ページング、未送信の未知パラメータに対する既存の公開契約フィードバックを共通にする。初期メッセージに条件名や結果のヒントを入れない。API例外をcatchするか、後のプログラムで回復するかはエージェント自身が決める。

モデルは既存の固定MiniMax M3 IQ4_XS、65,536文脈、同じthinking設定とsampling設定を用いる。環境seedは42、モデルは51+呼出し番号を両条件で共有する。条件ごとの最初の入力はKVキャッシュ再利用を禁止し、実測で確認する。以降は通常の再利用を許す。同じseedでも数値計算と時間の非決定性は残る。

順序は課題1 value→exception、課題2 exception→value、課題3 value→exception、課題4 exception→valueの8条件を各1回。成否を見て順序、seed、対象、試行数を変えない。

## 予算、停止、測定

1条件につき最大80モデル呼出し、450,000の論理入力+出力トークン、1,800秒。API上限は写真160、それ以外80。入力を毎回正確に数え、残予算に応じて出力を最大4,096から縮める。文脈や出力が収まらなければ停止する。実行器の通知、入力計測、失敗、回復の費用も含める。開始準備120秒、後始末180秒、独立評価180秒は別に測定し、全体時間も記録する。

8条件でモデル呼出し最大640回、予約トークン最大3,600,000。サーバーは最大21,600秒の所有者付き有限リースとし、終了経路で停止する。実行コードと計画をcommitし、その完全なHEADに対するpushとPRのCIおよび必須job成功を確認してから起動する。8初期入力を計数し、両条件の入力一致と収容可能性を検証してから全条件を有効化する。

使用量が不明なモデル応答は実行せず、その条件を終了する。API効果と後始末が既知の場合のみ、同じサーバーが60秒以内に待機状態に戻ったことを確認し、保存環境を1回評価して次の固定条件へ進む。欠測を0とみなさない。API効果不明、実行基盤の異常、初期状態不一致、後始末や評価の失敗、リース不足、ユーザー停止ではバッチ全体を止める。失敗した試行も削除・置換・再試行しない。

## 集計と採否

主指標は課題開始からの全論理入力+出力トークンと公式の最終成否。キャッシュ入力、非キャッシュ入力、出力、モデル/API回数、準備、実作業、後始末、評価、ロード、サーバー滞在時間を併記する。トークン率を金銭や時間の削減率と同一視しない。

8条件と4対を全て公開集計する。両側の使用量が既知の対のみ正確な差を算出し、欠測を含む合計は既知部分と不明回数を分ける。実際の例外回数と後続の公開要求を確認し、失敗通知が一度も使われなかった条件の差を回復の効果とはしない。公開コードやAPI記録は診断できるが、private reasoningの内容やDB内容は研究者が読まない。

開発上の採用条件は、全8条件の独立評価、監査通過、全使用量既知、少なくとも1件の実API例外、1対以上の双方成功、成功の損失なし、exception側の全仕事費用合計の減少。品質向上と費用増加はトレードオフとして報告する。4つの既知課題の1回比較で、統計的非劣性、一般化、新規性、採択可能性は確立しない。

## 新規性判断との関係

保留中の呼出し引数だけを変更して後続プログラムを保つ操作は、[ControlScope](https://arxiv.org/html/2609.34313v1)のArgに既に含まれる。P49/P50でも未送信引数修正の対象例は限定的だった。この操作だけを新提案として実装する方針は採らない。P78は比較基準を確認し、残る制御課題を根拠付きで絞るための有限の追加比較とする。
