# 完了時の回答形式を切り分ける追加確認

2026年10月21日。P25の全結果の解釈とは別に、既に終了したP22・P24の課題2だけを対象とする。P24の公開履歴診断では、承認10件のIDと明示された非認証引数が一致したが、最終成否が異なった。これだけでは、完了時の回答形式と、それ以前の調査・状態のどちらが影響したか分からない。

## 固定する比較

| 操作の前半 | 最後のcomplete_task |
|---|---|
| P22_02の記録通り | P22_02の回答引数あり |
| P22_02の記録通り | 回答引数を省略 |
| P24_02の記録通り | P22_02と同じ回答引数あり |
| P24_02の記録通り | 回答引数を省略 |

全４条件を保持する。新しい文章を生成せず、既存の回答をそのまま使う。前半は同じ公開API、初期状態、seedで最初から再実行し、各返却・ツール公開状態と、完了直前の保存DBファイルのハッシュを元記録と照合する。原状態のDB内容、正解、評価器本文は読まず、再現が一致しない条件はそこで停止する。完了APIが最後の独立した呼出しであることは記録の構造から確認済み。

再実行は新しい模擬環境に限定する。元の実行、P25、確認用12シナリオは変更しない。P25の全４件が終わるまで実API再実行を開始しない。１条件80 API・600秒を上限にする。LLM呼出しは０、４件の再実行と最後の独立評価の費用は別途残す。速度比較や、新しいエージェントの成功率として加算しない。

## 解釈と採らない案

元と同じ２条件が同じ成否になり、前半を固定して回答の有無だけで成否が変われば、この課題での完了引数の影響を限定して示せる。単なる相関より原因を絞れるが、他の課題への一般性、評価器の誤り、独自の制御方式の必要性は示さない。APIの公開仕様に沿った違いかどうかも別に確認する。

途中の動作を後から修正する案、別の回答を何度も試して合格を探す案、評価詳細から正解操作を作る案は採らない。この確認はP24の成否を置き換えるものでも、レターの新規性を保証するものでもない。追加確認が不要・不一致の場合も全件を記録し、主実験を引き延ばす反復にはしない。
