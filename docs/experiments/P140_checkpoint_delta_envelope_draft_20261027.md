# P140: explicit delta-object output envelope

This is a finite, posthoc development comparison on four already-known tasks and one fixed model seed (57). It does not reuse old outcomes as new observations, inspect the twelve reserved tasks, or establish a novel method. The closed P139 structural diagnosis found that one second-focus response decoded as a JSON array, whereas the unchanged checkpoint parser requires an object. That observation motivates clearer output wording; it does not establish that wording caused the rejection or the task failure. The original P139 records, strict prefix test, missing/unknown usage, and failed gates remain unchanged.

## Fixed comparison

The twelve cells are the four known tasks crossed with three modes:

- `threshold_recursive`: unchanged P139 threshold/recursive strong control.
- `exposure_delta`: unchanged P139 exposure/delta implementation control.
- `exposure_delta_object`: exposure/delta with an explicit object-only instruction in the second delta focus system message.

The candidate appends a clarification to the existing delta prompt: return only one object with `completed`, `usable_state`, `remaining`, and `uncertainties`; do not return an array or copy the previous checkpoint into the output. The host continues to combine its saved previous object and the returned delta. The user packet, including the prior summary as reference, is unchanged. Initial actor input, guide, tools, first summary request, exposure rule, and recursive control remain unchanged. A second opportunity after an unsuccessful first summary still uses the ordinary summary prompt, because there is no accepted prior object to extend.

All arms use the real limit of two checkpoint opportunities, at least three fresh closed turns, two retained recent turns, the same model/sampling configuration, and 4,096 output tokens per summary. The existing parser still requires a complete JSON object with the four exact fields, at most 32 string items per field, and at most 2,048 characters per item. The host's combined serialization of both fragments remains bounded by 8,192 characters and 32 combined items per field. There is no array unwrapping, JSON repair, output-cap increase, third opportunity, or retry. Structural acceptance and shorter counted input do not certify semantic accuracy.

Each cell retains 80 model calls, 450,000 logical input-plus-output tokens, and 1,800 seconds of work. The four task API limits remain 160/80/80/80. Cohort ceilings are 960 model calls, 5.4 million logical tokens, 1,200 environment API requests, twelve evaluator calls, and 24 paid summary calls. Native input counting, context admission, residual budgets, timeout handling, cleanup, and evaluation use the existing paths. The helper fixes the launch window and finite server/batch/pipeline limits; its current draft has a latest launch of 23:30 JST on October 27 and an 08:00 JST October 28 deadline. Final preparation must verify that the complete reserved lifetime fits that deadline before source freeze and launch. Ordinary user messages do not request a stop; explicit stop requests retain the existing stop path.

## Accounting and interpretation

Both paid focus calls and actor calls contribute to the whole-job ledger. The longer prompt is counted and charged through the same native input path; its extra input may change later budget notices. Unknown terminal usage stays unknown and stops continuation. A known paid actor followed by a failed additional exposure count retains its cost but withholds the action and makes mechanism accounting incomplete. Prepared prompts are reported separately from actual dispatched focus calls; installed deltas are separate from actual known/unknown actor exposure.

The two comparisons have separate gates. For each control versus the candidate, all four task pairs must be evaluated with known usage and intact contracts/accounting, with no paired success loss, lower total whole-job tokens, lower common-success tokens, and actual changed-prompt dispatch plus delta exposure on a common-success task. Candidate adoption requires both gates. All twelve planned rows, failures, unrun cells, missing counts, unknown usage, and unsuccessful comparisons remain in the report. Common-success selection does not replace the full-task cost comparison.

The following interpretation is fixed after P139 and before any P140 generation. If only the changed fourth task is repaired while the unchanged exposure/delta control still fails it, that task is outside their common-success subset. The secondary gate can therefore remain false despite observed quality recovery, and unknown control usage can leave its cost comparison unquantified. A passing strong-threshold primary gate would still be limited evidence of success preservation and lower complete whole-job cost on these four known tasks; a failing secondary gate does not negate that separate observation. The combined adoption gate remains false unless both fixed gates pass. No failed task is recategorized as a common success, and unknown costs remain null. A matched-prefix transition from rejected output to a valid installed delta and known actor exposure is a local contract-repair observation, not proof that the repair caused final success or established novelty/generalization. No P140 outcome has informed this interpretation.

Attribution against the unchanged `exposure_delta` control additionally requires the independently reconstructed second-opportunity prefix check. P140 reports both the old strict comparison and the new exact comparison modulo validated, bijective transport call/result IDs. The new normalization changes no arguments, content, reasoning text, observation, prior summary, request, cutoff, exposure/cost state, or sampling field. It does not alter P139's strict outcomes, prove hidden-state equivalence, or guarantee causal attribution for an entire job. The threshold comparison is a policy-utility comparison, not an isolated prompt effect. Posthoc selection, one known seed, four development tasks, and absence of independent replication remain explicit limitations.

## Implementation and evidence boundary

`checkpoint_delta_envelope_p140.py` derives the old checkpoint controller and replaces only the second delta focus system message. `checkpoint_delta_envelope_inference_p140.py` provides explicit new-mode construction and an offer hook because the old constructor binds its original four modes; all transport, counting, admission, resolution and accounting methods are shared. `run_whole_task_checkpoint_delta_envelope_cell_p140.py` is an explicit worker copy with the new helper, inference and `delta_envelope_control` summary. There is no global monkeypatch or old-mode/max-opportunity disguise.

The new handwritten tests compare both controls against the frozen P139 request/usage fixture, compare candidate requests through its second focus, retain the previous summary note in full actor views, reject array and over-budget responses, stop on unknown usage, and distinguish prepared, dispatched and exposed states. Their synthetic count increment is a test value rather than a tokenizer estimate. These tests do not run a model, native counter, generated task program, AppWorld API or evaluator. Live preflight, source binding, complete-cohort audit, and final decision remain separate launch/closure steps owned by the experiment runner.
