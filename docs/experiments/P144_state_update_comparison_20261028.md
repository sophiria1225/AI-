## 問いと比較

古い4フィールド要約の各項目について、保持・更新・削除を明示し、新項目を加える方法が、通常の再帰要約と単純追記の両方に対し、課題成功を失わず仕事全体の論理tokenを減らせるかを測る。

|略号|実装mode|第2要約の扱い|
|---|---|---|
|TR|`threshold_recursive`|古い要約＋新履歴から要約全体を生成し直す|
|APP|`threshold_delta_object`|明示された差分objectを古い要約に追記する|
|UPD|`threshold_delta_update`|古い全項目を明示的に保持／更新／削除し、追加を適用して単一要約を作る|

同じarchive・既存stateを入力とする場合、第1要約packetと第2要約のuser側参照packetの構築規則は3方式で共通であり、第2要約のsystem側の出力契約が異なる。独立run間で実際のpacketが同一だったかはprefix監査で別に確認する。したがって推定するのは表現方式と指示文を合わせた効果であり、parserや指示だけの独立効果ではない。前半の実入力が同じだったかは保存記録から別途検査し、同seedだけで同一経路を仮定しない。

型付き編集・host merge自体は新規ではない。Mem0、SKILL.state等との重複は[先行技術と主張範囲](../checkpoint_state_update_prior_scope_20261028.md)に記録した。候補の追加寄与・一般品質維持・学術的新規性は未確立である。

## 状態更新の契約

`completed` / `usable_state` / `remaining` / `uncertainties` の各fieldが、次の4キーだけを持つ。

```json
{"keep":[0],"update":[{"index":1,"text":"revised item"}],"delete":[2],"add":["new item"]}
```

indexはそのfield内の古いリストに対する0始まりの整数。古い各indexをkeep/update/deleteのいずれかに一度だけ指定し、未指定を削除とはみなさない。重複・範囲外・bool index・不正な型・追加キー・上限超過を拒否する。keepは文字列を変更しない。保持・更新項目は元の相対順序、addは返された順序で末尾へ置く。field間の暗黙移動はない。

提示時の旧状態とnote digestをhostに束縛し、採用前にも変わっていないことを確かめる。LLMにdigestの再出力は求めない。編集全体を原子的に適用し、不正時は現在のviewを保持する。有料の既知focus費用は拒否しても残す。修正用の再試行はしない。未知usageは未知として停止する。

UPDの採用はAPPのdelta露出に数えず、更新prompt送信、採用、操作数、正味state変更、後続actorへの実送信・既知usageを分離する。keep/addだけ、またはdelete＋同文addによる正味不変は「古い情報を変更した介入」に数えない。成功例で、古い項目変更と正味state変更の両方があり、その状態が既知usageのactorへ届くことを必要とする。

## 全条件を残す判定

主比較TR→UPD、必要な追加対照APP→UPD、記述的対照TR→APPを別々に示す。各比較の全体費用差を確定するには、その2方式×4課題の全8条件が評価済みでusage既知でなければならない。全体の開発上の候補判定には全12条件が必要。未完・不明・失敗を落とさず、未知費用を0で補わない。

両必要比較で、(1)対応する課題成功を一つも失わない、(2)全4課題の総費用が低い、(3)共通成功課題が空でなくその総費用も低い、(4)上記の実際の旧状態変更が共通成功課題でactorに届く、(5)契約・会計が完全で、起動した第2介入の正準化prefixが一致する、を満たす必要がある。成功件数が同じでも、別課題の成功喪失を隠さない。失敗課題だけの短縮や空の共通成功集合を肯定的成果に数えない。

費用はactor/focus全呼出しの実logical input＋output。既知の失敗・拒否・制御費用も含み、cached inputを引かない。API回数、壁時計時間、サーバ費用、未知件数は分ける。token削減をそのまま料金・時間削減とは呼ばない。

厳密prefixと検証済みtransport ID正準化prefixを別記する。独立trace監査はupdate parse/apply・coverage・hash・順序・サイズを再構成するが、既存JSON重複検出と通常要約parser/formatterは共有し、その依存を開示する。独立監査は記録整合の検証であって意味保存の証明ではない。途中は稼働・閉鎖件数だけを確認し、12条件閉鎖後に科学的結果を読む。

既知4課題・1seed・事後開発の局所結果である。判定を満たしても未知課題の確認、一般性能保証、採択や新規性の証明を置き換えない。原稿では確認済みの結果を示し、不成立例は適用範囲と限界に含める。
