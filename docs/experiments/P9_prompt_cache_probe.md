# P9：情報を変えず入力の並び順を変える実行基盤の校正

2026年10月21日、実行前の計画。P6第2課題の全履歴方式で入力再処理が時間を占めたため、記憶方式の研究を進める前に比較基盤の影響を調べる。新しい記憶方式や新規性を検証する実験ではない。

対象は`P6_02_FULL_V03`の最後に正常終了した隣接2入力、`call_024`と`call_025`。これらの順序・内容・スキーマ・モデルを固定し、参照ID一覧を履歴の前から後ろへ移す変更だけを比較する。選択は観察後の開発用校正であり、未経験課題での検証ではない。[計画JSON](../../configs/P9_prompt_cache_probe_v01.json)に元入力のハッシュを固定する。

## 条件と予算

| 項目 | 設定 |
|---|---|
| 比較 | 原配置、参照ID一覧を後ろに置く配置 |
| 変更しないもの | 全JSON値、要求・観測・前履歴、ツール、モデル、元入力のサンプリング設定 |
| 共通の校正用変更 | 出力上限を1トークンへ限定。環境操作しない |
| 1組 | 先行入力を`cache_prompt=false`、後続入力を`true`で実行 |
| 順序 | 原配置→後置→後置→原配置。各2組、計8呼び出し |
| 上限 | 150,000入力＋出力トークン、1,800秒、1回600秒 |
| 開始 | P8終了後、同じモデル設定で1スロットを使用 |

第1呼び出しは前の実験のキャッシュを使わない。実測でキャッシュ数0を確認できなければ比較成立とせず停止する。入力数と事前計測の不一致、使用量不明、予算不足、固定ソースの変更も記録して停止する。失敗した条件の無料再試行はしない。

## 何を測るか

主な測定は各組の後続入力の再処理トークン数・入力処理秒数。先行入力を温める費用、全呼び出しの入力・出力、生成時間、実時間も保存する。第1呼び出しを費用から除いて「安くなった」と報告しない。

これは一つの隣接入力組に対する2反復であり、一般的な速度比の推定には少ない。順序の影響を完全には除けない。モデル設定を同じにしても、キャッシュ経路により数値計算と出力が一致しない可能性がある。

生成文は環境へ送信しない。課題成功率、最終品質、圧縮によるトークン削減、再編の利益は測らない。情報をJSON値として保持したことと、LLMが同じように扱うことは別に検証する必要がある。

## 採用しなかった案

- 最初から実課題を再試行する：行動の違いと処理時間が混ざるため、まず固定入力で基盤の影響を測る。
- キャッシュを全条件で無効にする：差を消すだけで効率的な強い基準にはならない。各組の初回だけ無効にして前段の影響を抑える。
- 履歴を短くする：保持する情報も変わるため、この校正では選ばない。
- 役割ごとのKVキャッシュを複数持つ：保存容量や切り替え機構も変わる。先に単純な入力配置を確認する。
- 進行中のP8を差し替える：事前固定した条件を維持し、変更前の結果も残す。

速度差が確認できても、共通基盤への既知の最適化として扱う。独自アルゴリズムとは呼ばない。次の実課題比較では品質と全費用を改めて測る。
