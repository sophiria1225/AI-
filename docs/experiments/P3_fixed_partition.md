# P3 単一と固定分担の共通条件

2026年10月20日に仕様を作成し、実装と制御検査を経て4試行の実行前計画を固定した。P2のIQ4比較とは別の開発実験であり、この計画固定時点では実モデルのP3実行は0件。P2の2課題を成功するまで反復する計画ではなく、同じ条件で構成を比較する開発観察である。

Q3のP2では、2件とも入力枠ではなく全体予算の事前検査で終了した。残予算はそれぞれ17,181、29,245トークン。動作中のモデルには初期上限だけを渡していた。最終成果物を凍結した後の公開テスト結果も、その実行には戻していない。この条件のまま分担だけを追加すると、基準方式の予算管理と分担の効果が混ざる。

P3では単一・固定分担の双方に、各呼び出し前の残り総トークン・呼び出し枠・時間を示す。公開情報から選んだテストコマンドも最初に渡す。予算通知自体の入力費用を含め、途中で自動圧縮や追加の無料制御呼び出しを行わない。P2との差は、量子化差や分担差と呼ばない。

| 項目 | 単一 | 固定分担 |
|---|---|---|
| モデル・基本ツール・作業ツリー | 共通 | 共通 |
| 論理担当 | 1 | 実装担当・検証担当の2つ |
| 実行 | 逐次 | 交互に逐次、物理的には1呼び出し |
| 作業範囲 | 全要求 | 実装と検証を主な役割とするが、双方に全体の読取・変更・検査を許可 |
| 履歴 | 自身の履歴 | 担当ごとの履歴。相手の操作・可視結果・作業版を共有 |
| 予算 | 全体で1枠 | 全担当合算で同じ1枠 |
| 最終提出 | 現在の成果物へ完了宣言 | 同じ成果物の版に対して双方が完了宣言 |

固定分担に強制的なファイル分割を置かない。要求から正解の変更対象を先に教えることや、相手の領域を読めない設定で失敗を作ることを避ける。これは工程による固定分担であり、モジュール別の排他的な更新責任を再編する実験ではない。

相手への共有には、生成された思考文を含めず、可視回答・ツール要求・同じ表示上限の実行結果を用いる。共有内容が長くなった費用もそのまま計上する。形式エラー・失敗した操作・検証・提出に必要な生成を無料にしない。未取得の使用量は不明として停止する。

完了宣言は成果物の版に結びつける。担当の一巡の区切りで変更を観測した場合、古い宣言を無効化する。異なる版に対する2つの宣言を、同じ完成物への合意と扱わない。操作の終了が確認できないときも継続しない。状態移管機能や自動再編はこの段階に加えない。途中の差分は観測用であり、プロセスや一時ファイルを含む完全な環境復元用チェックポイントではない。

まず、模擬応答で共有予算・古い完了宣言の失効・不完全な応答の拒否を検査する。これは配線の検証で、モデル性能の測定ではない。実課題のモデル・試行数はIQ4の容量と品質結果を踏まえて実行前に固定し、設定、コード版、原記録、最終成果物を残す。

他の候補の扱い：全員の全履歴を毎回結合する方式は別の記憶方式となるため今回は使わない。調整役を追加する方式は制御費用も増えるため後の対照に残す。残予算に合わせた出力上限の自動縮小は未完のツール要求を増やす可能性があり、初版ではP2と同じ保守的な上限判定を維持する。品質の不足を単なるトークン削減として報告しない。

## 観測記録から最初に調べること

`summarize_p3.py`は担当別の入力・出力、実行回数、検査等の非ゼロ終了、成果物変更、完了宣言の失効を集計する。原使用量と全体予算の一致は`audit_p3.py`で別に確認する。モデルに追加の理由説明を生成させず、既存の操作・成果物・API記録を用いる。

同じコマンドの反復回数も保存するが、必要な再検査を含むため、そのまま「無駄な作業」と呼ばない。ファイルが変わったことや担当が交互に操作したことだけでは、相互依存や相手の変更に起因する修正を確認できない。該当する可視履歴・差分・検査結果を示し、情報不足、実装誤り、検査失敗、予算不足、相互調整の候補を分ける。構成の効果を確かめる介入は、対象となる現象を観測した後に設計する。

既存の模擬5応答・実コンテナ記録に対して、担当別の合計600という人工トークン値、成果物変更2回、完了宣言の失効1件を照合した。[集計の検査](../../reports/P3_observation_control.json)。模擬値は実モデルの費用へ合算しない。計画固定時点の実測は0件で、その後の[実行記録](../P3_progress.md)と[実測集計](../../reports/P3_measurements.json)を順次更新する。

## 最初の4試行の固定条件

[計画ファイル](../../configs/P3_development_plan_v01.json)と[開始前の検査](../../reports/P3_plan_controls.json)を保存した。モデルはMiniMax M3 IQ4_XS、KVはq8_0、入力枠は65,536。P2で使用した温度・seed・出力上限・基本ツール・公開検査を維持し、P3の役割・共有・完了規則を適用する。

| 順序 | 課題 | 方式 | 課題設定 |
|---|---|---|---|
| P3-01 | 15380 | 単一 | [共通設定](../../configs/P3_minimax_iq4kv8_15380.json) |
| P3-02 | 15380 | 固定2担当 | 上と同じファイル |
| P3-03 | 15957 | 固定2担当 | [共通設定](../../configs/P3_minimax_iq4kv8_15957.json) |
| P3-04 | 15957 | 単一 | 上と同じファイル |

課題ごとに先行方式を逆にし、P3の結果を見る前に順序を固定する。各試行は全担当合計30呼び出し・総入力出力300,000トークン・実行ループ3,600秒を上限とする。4試行のモデル呼び出し上限は120回、トークン上限は1,200,000。独立評価や終了処理の時間は別途記録する。モデルサーバーの監視上限は6時間にし、P2で経過した稼働時間が後の試行を短くしないよう新しく起動する。入力枠・KV形式・同時処理枠は変えない。

`run_planned_p3.py`は12ソースと2設定のSHAを照合し、試行開始を排他的に記録する。同じ試行の再実行は、失敗した開始も含めて拒否する。先行試行の実行・監査・独立評価が完了してから次へ進み、課題の不合格を再試行の理由にしない。基盤や費用計測の異常があれば残りの計画を止め、記録を残した別計画として変更を検討する。

この4件は既に開発に用いた2課題であり、未調整の最終評価、品質の非劣性、一般的な削減率の推定には使わない。15380のような局所修正を、相互依存の強い大規模作業の成功例として数えない。
