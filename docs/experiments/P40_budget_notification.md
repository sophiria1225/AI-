# P40：残予算の通知を備えた比較対象

2026年10月22日。目的は、不要な情報取得・ツール実行を減らして最終品質を保つ研究に、予算を明示した比較対象を置くこと。新方式の提案とは扱わない。

P33/P38の全15条件・102呼出しを受動的に点検した。実行器は上限と使用量を管理するが、入力のsystemは固定、userは公開課題と形式エラー等の観測だけで、残りのAPI・呼出し・トークン・時間の通知はない。ツール結果には処理内のAPI回数があるが、上限と残量の通知とは異なる。これは失敗原因の証明ではない。[監査](../../reports/P40_budget_visibility.json)。初回の解析では通常の形式エラー通知のJSON形状を未登録として停止したため、実際のNativeConversationの生成形状を確認して受け入れた。モデル・APIの追加実行はない。

予算を毎回知らせるBudget Tracker、予算に応じた計画・検証のBATSは既出である。[本文 §3.1, §4](https://arxiv.org/html/2511.17006v2)。同研究は検索だけでなく会話・コード課題への適用も記載するため、「実行課題へ移した」だけを差分にしない。本実装はAppWorldの既存ハーネスへ通知を追加した対照であり、原論文の完全再現ではない。[関連研究の区別](../budget_control_overlap_20261022.md)。

## 変更する条件と固定する条件

全４既知開発課題の既存８応答後から２分岐する。前半の会話、API返却、DB、Python状態を復元する。通知なしと、残予算を各呼出し直前に通知する方式を比較する。全履歴を維持し、P38の項目読取ヘルパーやキャッシュは使わない。原ツールとPython状態は同じ。追加された通知を除く初回入力は一致し、そのハッシュを保存する。

通知のAPI回数は前半を含む。総トークンは入力と出力の合計で、KV再利用分も含む。時間は通知作成時点の残り秒数で、生成中も経過することを説明する。現在の出力上限と次の入力を予約する従来の停止判定は維持する。通知の文字数・token数・処理時間を無料にしない。履歴には通知を蓄積せず、各呼出しで最新の１件を加える。

各条件の最初の呼出しは`cache_prompt=false`、２回目以降はtrueとする。初回cache_n=0を実測確認し、前条件からの接頭辞再利用を除く。ビット単位の完全決定性を保証しない。P39の校正が終了し、計測が一致した後に開始する。

上限は１条件16生成・120,000論理token・480秒、APIは元課題の160または80回で前半を含む。全８条件最大128生成・960,000token。共通前半の復元を別記する。課題1,3は通知なしを先、2,4は通知ありを先にする。各１回の探索的比較であり、一般化や非劣性は検証しない。

## 実行前確認と停止

共通前半の実API返却・DB・Python再現は、P33で全４課題の照合を済ませた同じ原記録を使う。P40ではその境界ハッシュ・元アダプター・公開スキーマを再確認し、２方式の追加通知だけが変わる入力を数える。各本実行でも前半を復元して照合し、一致しなければ生成しない。

不明使用量・効果不明・初回キャッシュ状態不一致・復元不一致・評価器失敗・停止指示ではバッチを停止し、置換しない。通常のタスク失敗や既知の予算停止はそのまま残す。最終評価は各条件の終了後に別プロセスで行い、次の生成には結果を渡さない。未閲覧12シナリオは使わない。

## なぜ別の案を先に行わないか

- キャッシュ契約の拡大：P38では再利用０であり、拡大の効果を示す根拠がない。
- API上限だけを緩和：完了しやすくなっても、同一予算での制御の改善を検証できない。
- 失敗１課題だけの通知調整：成功済みの課題を壊す影響を見逃すため、全４課題を固定する。
- 予算予測器・学習器の追加：まず実測残量の単純通知を比較対象に置く。予測・停止にも先行研究があり、追加価値を別に検証する必要がある。

結果は全件の成否、総費用、通知量、API・モデル・tokenの残量、停止理由として示す。単に失敗を早く打ち切った費用減を、品質維持として数えない。良い結果が得られても、それ自体をレターの新規性に置き換えない。
