# 既観測16課題のページ取得状況を調べる

2026年10月21日。これは開発用の事後分析であり、新しい確認実験ではない。P22の最終１課題で「全件数と同じだけ返った最初のページ」を最後に探索を終えたことが、分析の動機になった。その事例だけを選ばず、P10・P11・P18・P22の標準全履歴16課題を対象にする。P24の途中内容と確認用12件は含めない。

## 実装・全件集計の前に固定する規則

1. 対象は[固定リスト](../../configs/collection_frontier_audit_v01.json)の全16試行。入力は保存済みの公開要求結果、公開API定義、既存の成功・費用の集計に限る。新しいモデル生成・API要求は行わず、DB・デモ・解答・評価器本文を読まない。
2. `GET`で、公開定義に`page_index`と`page_limit`があるAPIを対象とする。省略された引数は公開の既定値で補い、ページ番号以外の全引数が同じ要求をまとめる。上限・検索条件・認証範囲が異なる要求は混ぜない。引数値は公開しない。
3. 同じアプリへ変更を伴う操作が送られたら、以後は別の区間とする。未知の操作も同じアプリの区間を区切る。GETと書かれていることだけで一般に無副作用とは保証しない。アプリをまたぐ影響、外部変更、検索順の安定性はこの分析では証明しない。
4. 返却がリストの場合に行数を数える。エラー・非リスト・不正引数は「未分類」で保持する。空ページ、上限未満のページ、上限と同じページを分ける。空または短いページがあるだけでは、飛ばしたページのない列挙とはしない。
5. 区間内の同一要求について、0から連続するページの後に空・短い返却が観察されたかを数える。ただしAPIが常に残りを詰めて返すか、順序が安定するかは別の条件である。「終了らしい返却の観察」と呼び、網羅証明にはしない。後に矛盾するページ・異なる再返却があれば不整合として分ける。
6. 全て上限どおりで終端らしい返却がない要求を記録する。これは未取得対象の実在、課題への必要性、最終誤答を意味しない。「未完のページ取得があれば失敗」という規則が成功例にも反応するかを集計する。
7. 成功・失敗、宣言完了・予算停止を分けて全件報告する。16件は既に見た開発事例で、効果の推定・新規性・別課題への一般化には使わない。未分類や解析失敗も削除しない。

公開するのはAPI名、匿名の要求グループID、ページ番号・件数、区間番号、状態の分類、原記録のハッシュ、集計値のみ。検索語、対象ID、返却内容、認証情報を出力へ含めない。

## なぜこの分析か

P22の最大値回答は取得済み35曲の範囲では正しく、単純な数値計算の追加が原因候補と直結しなかった。一方、最初の５プレイリストだけで十分かは確認できていない。この差を他の成功例も含めて調べる。

全ページを機械的に取り直す制御を直ちに実装する案は、探索用の検索や変更済み集合にも介入する可能性があるため先に採らない。結果を見て対象課題を差し替える、DBで未取得対象を確定して生成へ渡す、継続中のP24へ介入する案も採らない。

解析器の検査は、引数の既定値、異なる条件の分離、ページ飛ばし、変更後の区間分離、矛盾・再返却、出力への認証情報混入を中心にする。単純な実装と同じ出力を期待するだけの検査にしない。
