# P43：入力費用とAPI返却の表示対応を調べる

2026年10月22日、アカウント変更後のユーザー指示で研究を再開した。P42の生成見送りは維持する。次の方式を選ぶ前に、同じP29全４課題・８応答後の入力を分解する。これは方式の実験ではなく、保存入力の計測である。

## 対象と計測を固定する

- P42に保存した全履歴入力４件を再構成し、入力ハッシュ・元の32応答・境界・P42の23省略候補を照合する。課題の選別や未閲覧12シナリオの利用はしない。
- 全標準出力を、対応する要求群が仕様APIのみ／仕様と他APIの混合／他APIのみ／不確定の４群へ分ける。これは要求の分類で、標準出力の全文が仕様であるという判定ではない。異常・切断・未送信・要求なしは不確定へ残す。対応が壊れている場合は停止する。
- 仕様APIの返却全体の既定の直列化が、標準出力のどの位置と完全一致するかを測る。複数位置・重複区間は曖昧として除外する。文字列一致はデータフローの証明ではなく、残りを全て作業情報や不要なラベルと断定しない。表示や原記録は変更しない。
- 内容・コード・API引数・認証情報は公開しない。公開するのは件数、位置、長さ、ハッシュ、照合理由のみ。文字数・UTF-8バイト数・token数を混ぜない。

## 入力tokenの内訳

チャットの役割、呼出しID、道具名を残した空の枠を起点とし、①基本ツールの定義、②システム指示、③課題、④AIの説明、⑤AIの操作引数、⑥標準出力以外の実行記録、⑦仕様APIのみの要求群のstdout、⑧混合群、⑨他API群、⑩不確定群を順に戻す。各段階の入力をサーバーの同じチャット形式・tokenizerで計数する。全４課題×11入力、最大44計数、各30秒、全体600秒。生成・アプリAPI・環境再生・評価器は０。

隣接する計数の差をこの順序での寄与とする。合計は保存済みP42全履歴の8,517／10,995／15,474／13,499 tokenへ一致しなければ停止。差は順序や境界のtoken結合に依存し、負値も丸めない。部品ごとの独立な因果効果、実際に省ける費用、継続総費用の上限ではない。計数用の空欄入力をAIの行動生成へ使わない。

## 実行と採否

軽量検査、公開コードのCI、固定コミットの確認後に計数する。モデルを起動する段階で、前の停止記録を保存した再開記録、モデル版、１スロットのアイドル、新しい有限の稼働期限を確認する。使用する計数のcache_promptはfalse。失敗した実行を上書き・自動再試行しない。P42の閾値を変更しない。

この計測から追加生成を自動承認しない。次の制御は、減らす費用、必要な品質、既存対照との差、採否基準を別途固定してから実装・実験する。部分一致へ緩めただけのAPI仕様省略を新規性としない。
