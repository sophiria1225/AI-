# P27：取得・計算・API操作をつなぐ通常のコード実行型との比較

2026年10月22日、実モデルの生成前に準備する。これは独自提案ではない。[CodeAct（ICML 2024）](https://proceedings.mlr.press/v235/wang24h.html)が扱う実行可能なPythonによる行動の統合を、現在の公開API・費用制約へ接続する比較相手である。原モデル・原エージェントの完全再現とはしない。

準備済みP23は取得済み値の計算だけができ、次のAPI引数への転記はモデルが行う。P27ではPythonが公開APIを取得し、値をそのままループ・集合・CSV等で処理し、次のAPIへ渡す。この差を確かめずに「通常のコードでも解消しない」と結論する案は採らない。

`run_python(code, span_ids)`をモデルへ提供する。コード内では`call_api(app, api, **args)`を使い、公開済みのAPIだけを呼べる。資料の取得後には同一コード内でそのAPIを使える。正確な公開スキーマは`api_schemas`へ更新する。取得・加工した値はPython変数で受け渡し、モデルに長いCSVやID一覧を再出力させる必要はない。

プログラムごとに変数は新しくなる。既存の公開観測は指定したspanから取得でき、全API返却は外部記録へ残る。次のモデル入力には、モデルがprintした内容、実行の状態、各API記録のIDを返す。原返却は`read_span`で読み直せる。外部の評価器・正解・私的ファイル・他シナリオへアクセスする機能はない。

Pythonは固定した3.12.15のコンテナ、ネットワークなし、ホスト共有なし、読取専用ルート、非root、256MiB、1CPU、最大90秒。公開APIはホスト側の仲介で実行し、１件ごとに資料公開状態・残予算・終了状態を確認する。途中のエラー以前に実行済みの操作を巻き戻したことにせず、送信後の応答不明では後続操作を止める。タイムアウトを「送信しなかった」と扱わない。

全APIを個別に計上する。１回のコードから40 APIを呼べても、１ APIとは数えない。計算・コンテナ起動・記録を実時間へ含める。LLMの入力・出力も全呼出しを計上し、プログラム内部のデータ量は別に記録する。

対象は既知のP18/P25の全４件を維持する予定。写真整理はP26と同じ160 API、他３件はP25と同じ80 APIを上限にする。モデル・seed42・80生成・45万トークン・30分・4,096出力は固定する。P26の終了・監査を確認するまで起動判断は作らない。失敗だけで対象を増減せず、確認用12シナリオは未閲覧のままとする。

比較にはPythonの制御フロー、スキーマの読み方、返却の提示、コード間の変数保存の有無という実装差がある。トークン減少を、コード言語だけや特定の内部機構だけの因果効果とは呼ばない。コードが書いた手順の正しさ・列挙の完全性を、実行できたことから保証しない。

全４件終了後に最終成功・使用量不明・全費用・取得と書込みの件数を報告する。今回のコード型で十分なら、それを新提案へ名前を変えずに認める。追加技術の主張には、この比較相手で残る問題と新しい機構の対照が別途必要である。
