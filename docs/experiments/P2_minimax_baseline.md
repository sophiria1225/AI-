# P2 MiniMax M3の実行適合と単一基準の校正

2026年10月20日開始。目的は、大型の非Flash候補を研究基盤へ接続し、モデル能力不足とハーネス構成の問題を区別できる基準を作ること。モデル変更による改善を再編方式の効果とは呼ばない。

## 固定する選択と理由

- MiniMax M3、第三者変換Q3_K_L、合計204,971,152,128バイト。Hubコミットと6ファイルのSHA-256を`configs/models/`へ保存する。
- Q3_K_Lから始める理由は、実測256GiBメモリで入力キャッシュ・検査環境・OSの余地を残すため。IQ4_XS約214GiB、Q4_K_M約243GiBは後続の上限検証候補。容量適合と品質を別々に測る。
- 実行基盤は公式llama.cpp b11669、コミット620d2225cc436ab0b001e3200e590e3b286ef9ab。v0.7.0が指すビルドを固定し、macOS ARM64バイナリのSHA-256を照合する。既存SDK不一致を避け、独自パッチを最初の条件へ重ねない。
- 画像・動画はコード実験で使わず、投影器も取得しない。マルチモーダル能力を評価したとは主張しない。
- Hy3 Q4_K_Mは比較候補。既存Flashモデルと27Bは再現・接続確認用に保持する。容量が足りている段階で削除して過去条件を失う必要はない。

## 順序と通過条件

1. 全ファイルのサイズ・SHA-256、実行基盤の版、Metalへのロードを確認する。
2. 通常回答、JSON、ツール要求、ツール結果利用を確認する。使用量が欠けた試行は費用不明として停止する。
3. 小さいコンテキストから16K、32K、64Kへ増やす。設定値だけでなく実入力長・正答・RSS・swap・時間を記録する。
4. 検査の終了コードを明示的に保持し、後続コマンドが失敗を隠さないことを確認する。
5. 使用済み開発課題django__django-15380と15957を測定する。未調整の最終評価には数えない。最終成果物を凍結後に独立評価する。
6. 同一モデルで単一と固定分担を比較し、対象現象が観測できる場合に同一状態の分岐比較へ進む。

取得・ロード・API・ツール・タスク失敗を区別する。ダウンロード待ちや互換性不足から量子化品質を判定しない。

## 予算と計測

最初のコード試行は総300,000トークンを候補にする。推論モード・生成上限・入力長・制限時間は接続試験から決め、実問題開始前に設定へ固定する。調整・失敗試行も記録する。

推論トークンを出力費用から除外しない。キャッシュされた入力を論理的な総入力から差し引かず、実計算量と別に報告する。モデル間にはトークナイザー差があるため、モデル間トークン数だけでハーネス効率を結論しない。

最終評価で途中候補を選び直さない。公開検査と独立評価が異なる場合は両方を残す。2課題だけで統計的なモデル順位や研究手法の優越性を主張しない。
