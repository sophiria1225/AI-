# Ansible候補で何を観察するか

2026年10月20日、P4_PRO_01の実行中に整理した分析方針。最終結果を見た後の分類ではないが、試行開始前の事前登録とも呼ばない。公開要求と基点コードの確認は[選定記録](../main_task_feasibility.md)、原資料の版は[公開コード確認](../../reports/pro_public_base_sources_v01.json)を参照する。

この候補には、YAMLフィルター、読み込み・書き出し、信頼情報と由来情報、vault、テンプレート値の取り扱いが登場する。研究上知りたいのは、それぞれの名称が登場する数ではなく、ある判断を別の処理と整合させる作業が発生するかである。要求が依存先を明示している部分を「実行中に初めて発見した」と数えない。

| 観察するもの | 記録から言える範囲 | 言えないこと |
|---|---|---|
| 複数箇所の変更と検査 | 変更したファイル、更新した時点、検査の成否 | ファイル数だけによる依存の強さ |
| 別の機能への再訪 | 公開ツールの呼び出しと再読込 | 再訪が無駄だったという断定 |
| 修正後の検査不合格 | どの変更の後に何が観測されたか | 対照実験なしでの原因特定 |
| 変更が生成されない状態 | 予算、取得した公開情報、終了理由 | 複数担当や集約で解決するという保証 |
| 最終成果物と要件の整合 | 独立評価の結果と公開成果物 | 内部の判断がすべて正しいという保証 |

単一方式が成果物を作れても、分担や集約の追加価値があるとは限らない。一方、不合格であっても、局所的な実装ミス、知識不足、調査の継続、状態不整合を区別する必要がある。単一方式の失敗をそのまま担当間の受け渡し失敗へ読み替えない。

次の構成比較では、元の問題文・要件・インターフェース、全リポジトリ、モデル、ツール、全入力＋出力予算を揃える。工程役割を交互に呼ぶ比較と、作業範囲・更新責任を実際に変える比較は別の操作である。前者の成功だけで後者の必要性を主張しない。

初期分担を設ける場合も、正解パッチの分布や今回のモデルの変更箇所から担当境界を作らない。公開要求の機能関係から決め、他担当の原資料を読めないようにして弱い対照を作らない。分担境界が不自然だった場合は、その不適合も結果として残す。

ここでの優先は、観察可能な調整負担があるかを確認することである。自動再編の判断器、自由な担当生成、別モデルへの変更を一度に加える案は、効果の出所が分からなくなるため後順位に置く。
