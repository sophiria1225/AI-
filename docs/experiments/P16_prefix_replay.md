# P16後の修復比較に向けた前半再生の確認

2026年10月21日。記憶表示の24生成は固定条件のまま継続中。新しいモデル比較を増やす前に、
同じ４課題で、対象操作の直前まで公開API履歴を再生できるかを確認する。
P16の生成内容・最終評価を見て対象を選び直さない。

初期化のseed、公開APIの版、接続コードを元のP11にそろえ、対象応答の前までの要求だけを新しい模擬環境へ順に送る。
各返却内容と送信状態を完全一致で確認し、元の保存境界のDBファイルとバイトハッシュを比較する。
一つでも一致しないケースはそこで止め、一致しなかった内容の種類を残す。許容差を後付けして成功扱いにしない。
全４ケースを記録し、不一致のあるケースを別の課題に入れ替えない。

一致した場合だけ、P16と同じ未知引数による送信前拒否を実行器へ渡す。
API送信０、拒否結果の一致、保存DBファイル不変を確認する。新しい推論と独立評価は行わない。
原タスク・応答・DB内容はローカルに置き、公開するのは件数、ハッシュ、照合結果、費用だけ。

これは保存したプロセスの復元ではなく、初期状態からの前半再実行である。
DBファイルと既知の観測が一致しても、任意の後続操作で完全に同じ動作になる保証ではない。
実環境での修復比較に進むなら、枝ごとに同じ前半を再生し、その費用と後続処理の費用を分けて記録する。

理由：会話だけをコピーして環境まで同一とする比較を避けるため。
採らない案：元の正常操作が既に終わった最終DBへ拒否文だけを追加して、未実行状態からの修復と呼ぶこと。
P16と並行するため、この再生の実時間から方式の速度差は主張しない。

実測：コミットfb82e94を保存してから、４課題をこの順で再生した。
API要求は５・11・14・４件、合計34件。各観測が元記録と一致し、操作直前の保存DBファイルは各13個、全52個のハッシュが一致した。
続けて未知引数による拒否を渡し、４件ともAPI送信０、拒否結果一致、保存DB不変を確認した。
所要時間は合計約14.1秒。モデル呼び出し０、正解情報ロードfalse、独立評価０。
[結果](../../reports/P16_prefix_replay_v01.json)。

この結果で、少なくとも今回の４つの既知履歴を同じ公開観測・保存DBへ戻す手段を確認できた。
修復方式の優劣と最終成功はまだ測定していない。P16の意味監査で候補の追加価値が残る場合に限って修復比較へ進む。
