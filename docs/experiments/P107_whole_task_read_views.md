# P107: 同じ参照インタフェースで既知のCSV課題を最後まで比較する

P106の手書き列では、通常の完全応答キャッシュを両側へ与えるとAPI数は12対12になった. これを受けて、次はモデル自身が参照を使うか、必要な項目だけを読むか、最終成果と全費用がどうなるかを確認する. 手書き列の微小な差を新規性へ転記する実験ではない.

## 事後に選んだ既知１課題の開発確認

既知のSpotify CSV課題`6104387_1`を対象に、`eager_cached`、`coalesced_cached`の順で新しい環境を各１回作る. この課題は既にP29、P88、P99等の成否を見ている. Spotifyの公開項目契約だけが現在接続されていることと、CSV課題の取得経路を既に調べていることから選んだ. 独立な未見評価、４課題の再評価、過去の欠測補充ではない. 未閲覧12課題は開かない.

同じシステム説明で`read_view("spotify", "show_song", song_id=...)`を案内する. 両方式とも同じMappingを返し、未知項目と`dict(view)`は完全値を要求し、通常の`call_api`は完全応答を返す. 状態変更前の取得、同一範囲・状態版の通常キャッシュ、参照保持、型、例外、失効、API予算を共有する. 方式名や以前の結果はモデルへ教えない. 元の生成コードを射影・書換え・補完せず実行する.

入力で具体的な対象ID、必要曲数、正解CSV、後続コード、課題評価の内容を教えない. モデルが参照を使わない、全値を表示して即座に取得する、APIを再取得する、提出に失敗する、といった経路も残す. 既知の出力を見て指示・seed・対象・上限を変更して再実行しない.

## 共通の実行条件

両側ともP99と同じtyped API、タスク内で持続するPython、公開API名、返された全推論、構造上の参照正規化、非表示の残時間、`tool_choice=auto`、reasoning -1を使う. world seed42、model seed57＋呼出し番号. 最初の要求はcoldで実測cache０を必須とし、以後は通常のprefix cacheを許す. 初期の完全要求が両側で一致することを生成前に照合する. 同じseedで同じ軌跡になる保証はない.

参照用経路はP99の外側のschema-feedback decoratorとそのまま合成できないため、そのdecoratorを黙って被せない. 両側とも共通の参照プロトコルで引数を検証し、公開仕様を取得可能にし、型付きAPI例外を例外として返す. P99との差を遅延取得だけへ帰属させない. 今回の比較対象は同じ新しいインタフェースの２方式である.

モデルへ出すAPI残数では、実送信済み、未取得参照の予約、追加送信に使える残数を分ける. 通知そのもの、API仕様、失敗と回復、参照操作もモデル入力になった分を含め、初回からの全入出力tokenを数える. API仕様を取得した同じPythonプログラム内で`api_schemas`が更新されるよう、成功して公開された仕様だけを追加送信なしで転送する. これは接続上の修正であり、新規手法ではない.

## 有限予算と閉鎖

各方式80生成、450,000論理token、80 API、仕事時間1,800秒. 合計は最大160生成・900,000 token・160 APIで、これらは予約上限であって実消費ではない. 各出力4,096、context65,536、各生成待ちは600秒と残時間の小さい方. 各方式の設定120秒、終了180秒、idle確認60秒、独立評価180秒. 所有モデルサーバーの稼働上限9,000秒. 再試行０、停止印`.runtime/P107.stop`とユーザー停止を優先する.

使用量不明の要求を０とせず、その応答を実行しない. 元の有限実行器と同じく、作用と終了が既知ならidle確認後に１回評価し、固定した次条件へ進む. API作用不明、契約不一致、設定・終了・評価の失敗では全体を止める. 終了のためだけに未取得参照を取得せず、停止時の予約と参照残数を保存する. 全２条件の閉鎖まで成否を読んで条件を変えない.

## 判定

主に最終課題成功、初回からの全論理token、実API数を測る. 使用量が全件既知で照合に通り、両方式が独立評価で成功した場合だけ、成功した同一課題の費用差として読む. 両方失敗や安い失敗を品質維持の削減としない. tokenとAPIは別指標とし、APIだけが減った結果をtoken削減と書かない.

全生成、API、Python、参照作成・完全取得・通常キャッシュ・解放、予約、制御通信、起動・終了・評価を残す. 参照の利用回数は性能指標の代わりではない. １既知課題×１回では一般化、非劣性、新規性、採録見込みは確定できない. 原稿の逐次更新は保留する. 最終ソース、監査と集計を固定し、同じ完全headのpush/PR両workflowと両job成功後に一度実行する.
