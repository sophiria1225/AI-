# E1：担当変更の効果を切り分ける仕様 v0.1

2026年10月20日。設計段階。四条件のLLM実行、実コンテナの完全保存・復元、利益予測器は未実装。今回追加するのは保存物・復元物の不足や不一致を検出する契約と、その制御検査まで。

## 何を測るか

[研究のアプローチ](../research_contribution.md)に従い、情報の整理・共同方針の効果と、判断から実行までを同じ担当に置く効果を区別する。P5の空パッチと履歴だけを後から完全なチェックポイントに変換しない。一時ファイルが失われていれば元の状態は復元できない。

## 同じ開始状態の条件

安全なツール境界で、実行中操作0、保留中のモデル呼び出し0を確認する。保存対象は次の六つ。

| 保存物 | 最低限必要な内容 |
|---|---|
| 会話 | 担当ごとのモデル入力・ツール応答。公開しない完全履歴はローカルに保持 |
| 作業管理 | 未完了作業、担当、根拠参照、成果物の版、更新責任 |
| 予算 | 全担当の使用済み費用、残トークン・呼び出し・時間、費用不明の有無 |
| 完了状態 | 現在の成果物に対する確認・完了票、版番号 |
| ファイル状態 | リポジトリの追跡・未追跡・削除・権限・リンク、一時ファイル、作業で書いた全領域 |
| ツール状態 | 固定イメージ、作業ディレクトリ、環境設定、外部入力、乱数・推論設定 |

書き込み可能な領域をアダプターが列挙し、全領域が保存対象に含まれることを要求する。単に `/app` のGit差分を保存して `/tmp` を省く方式を拒否する。コンテナの全差分やマウントの扱いは次の実装で検証する。今回の契約は列挙漏れを自動発見する仕組みではなく、**申告された範囲と実ファイルの整合性検査**である。

対象ファイルのSHA-256、モデル・ツール環境の識別子、残予算を保持し、介入前の復元物と照合する。生存プロセスやネットワーク外部状態は今回の契約では復元しない。再開に必要なら対象外として停止する。モデルの推論キャッシュは各分岐で共通にクリアする方針とし、実装時に実際にリセットできたことを確認する。トークンと実時間の評価を区別する。

## 四条件の変更範囲

| 条件 | 文脈 | 方針 | 作業・更新責任 |
|---|---|---|---|
| A 継続 | 元の担当履歴 | 現行規則 | 維持 |
| B 情報整理 | 共通の取得済み状態文書で更新 | 現行規則 | 維持 |
| C 中央調整 | Bと同じ更新・原資料アクセス | 共通の計画生成手順 | 元の担当が実行 |
| D 担当変更 | B/Cと同じ更新・原資料アクセス | Cと同じ計画生成手順 | 関連する未完了部分を一担当へ移し、共同判断と更新を継続 |

状態文書は課題、未解決事項、現在の成果物、取得済み根拠と版、公開検査から作る。未来の正解や独立評価の追加テストを含めない。C/Dの計画生成手順は共通化し、同じ固定計画を渡す補助比較を行う場合は、計画作成費用を各分岐へ帰属させる。共通前半と分岐後の費用を別々に残し、共通処理を無料扱いしない。

Dだけ新しいモデル、より長い文脈、特別なツールを使わない。全体の許可範囲は同じで、変わるのはその内部の仕事・文脈・更新責任の割り当て。Cで共同方針が失敗した場合も実行結果として残す。CとDの差はこの処置一式の差であり、単独の心理的・ニューラルな原因を証明するものではない。

## 強い対照と一般化

四条件に加えて、中央役が必要時に直接仕事を引き取れる方式、Flow/Puppeteer等を共通環境へ合わせた方式を比較候補とする。中央役を不自然に弱くしてDを有利にしない。機能がDと同一になる場合は等価な比較対象として扱う。

状態の抽出時点・対象課題・条件別分類は結果を見る前に決め、順調な状態も含める。同じ課題から複数状態を採っても独立課題数は増えない。学習・調整・確認を課題群単位で分ける。過去のP3/P4/P5は開発用のままにする。

## 着手条件と止める条件

1. 実コンテナの保存・復元が一致することを、追加・削除・未追跡・一時ファイルを含めて確認する。
2. 強い基準方式が要求に関する修正・判断へ進み、介入を比較できる状態を観察する。全方式が進まない原因を担当間依存と決めつけない。
3. 基本四条件を少数の開発状態で比較し、情報整理や中央調整を超える追加価値がなければ、自動移管の学習へ進まない。
4. 条件ごとの利益が残った場合に、費用・品質の予測を用いた選択を検証する。

今回の契約検査が通っても1の実コンテナ検証を済ませたことにはならない。ライブ状態を捕捉するアダプターとの接続と、復元後の同一公開操作の結果確認が必要である。
