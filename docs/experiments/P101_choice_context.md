# P101：保存入力の表現と通常tool choice設定の局所比較

2026-10-24、準備. P99の途中成否を開かずに、この追加確認の範囲を固定する. P99の全８条件が終了・監査され、所有推論器停止を確認した後にのみ最終実行計画を作る. 現在は未実行. 最終計画の実行headについてpush/PR両workflowとaccounting-and-syntax jobの成功を要求する.

## 確認すること

P84では、参照を統一した保存入力の出力が一致してもツール提出を伴わなかった. P99は通常auto/requiredを課題全体で比較する. P101は、同じ保存文脈で入力表現と提出設定を組み合わせ、次の出力の一致と静的な提出形式の対応を確認する. P99の成功条件を選び直す実験でも、P87の未実行枠の補充でもない.

入力はP83が既に保存した全６件を使う. A/Bは２つの元入力、C/Dは表示前に参照を統一した入力、NはAの構造上の参照だけを変更した対照、Xは診断文を加えた内容変更対照. 既知のCSV１文脈を事後に選んだ診断であり、６つの独立課題ではない. 未見12課題は使わない.

P84と同じcold要求を元に、`tool_choice`だけをautoまたはrequiredとする. messages、tools、返却推論、seed70、温度1、出力上限4096を含め他の保存要求欄を保持する. 両設定ともcache_prompt=false. P99の要求や過去のwarm状態を再現したという主張はしない. requiredが正しいPython、既知span参照、実行成功を保証すると仮定しない.

## 入力と生成制約を測る

固定済みの語彙専用描画器を再利用し、各設定で全６入力を一度ずつ描画する. GPU推論contextは作らず、decodeは０. 描画器・共有ライブラリ・実サーバruntimeを照合し、実サーバの起動引数と同じモデルでprompt、token列、生成制約、その他の要求設定をhash化する. 私有の文章・推論内容・token列は公開しない.

全12要求についてサーバ入力計数を各１回行い、描画器の計数と照合する. autoは元のP83計数にも一致を要求する. requiredはそれぞれの実計数を使い、autoとの入力同一性や同一費用を仮定しない. C/Dは設定内で要求JSONが完全一致する. A/Nのtoken同一性をrequiredにも決めつけず、描画結果の全66組で入力と生成制約を別々に報告する.

全６入力×２設定×３反復、36枠. 課題入力の順序はP84の３順序を保持し、各入力で設定順を交互にする. 完全な順序は計画JSONへ保存する. seedや上限を結果で変えず、打ち切り・空出力・不明使用量・未実行を除かない.

## 固定する解析

全36枠を監査し、元の要求、原応答、使用量、cache、提出形式のhashを照合する. 全12入力条件それぞれの３反復と、全66条件組×９対応を保存する. 対数や反復を独立標本数とせず、有意差を付けない. １条件でも不明なら、全件既知とは記載しない.

公開出力の一致、JSON引数、インタフェースの形、位置情報だけを外したPython ASTを分ける. 本文のみの一致、空API相当の出力、途中切れを有効操作の一致に数えない. 静的な提出形式の整合は実行済みの証明ではない. spanの存在、Pythonの意味、外部作用、CSV完成、最終課題品質、全仕事費用削減はこの診断では測らない.

設定内のA/B、C/D、A/Nと設定間の同一入力を、全件表の該当部分として読む. 入力token列や生成制約が違う場合は、その差を残したまま説明する. 本文一致と形式整合が両立する、しない、出力が揺れる、生成が途中で止まる、いずれも結果として保存する. 一般的な正規化や文法制約を新手法とせず、局所データで原稿の主張を限定する.

実装はP84の有限実行・監査を別ファイルへ派生し、元のソース・出力を変更しない. P99の設定・順序・予算にも変更を加えない. [既存ID修正の範囲](../external_identifier_prior_fixes_20261024.md)、[元の局所確認](../P84_findings.md)、[現在の主原稿](../../papers/202610_letter/README.md)と区別する.
