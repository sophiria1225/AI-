# P70：持続PythonにおけるAPI返却の直接利用範囲

P69終了後に定めた読取点検。P35〜P38の項目読取を再実装せず、必要項目をコードから自動取得する入口が既存記録にあるかを調べる。[選定理由と原典](../field_demand_review_20261023.md)。独自手法の性能実験ではない。

## 固定範囲と予算

P35で通常・計測付きの対応を確認したP33全４既知課題×３条件を使う。共通前半96プログラム、後続81、状態一覧の制御４、計181の出現を全て残す。同じ前半の重複を独立したプログラムや課題数へ転記しない。元のP35集計に保存された入力ファイルのハッシュから読取リストを作り、解析前に固定する。

上限120秒、181入力、各４MiB・コード20,000字・構文木5,000ノード。読むのは固定した `input_private.json` のコードとprogram_indexだけ。ファイルには公開観測由来の引数等も含まれるが、コード・値・資格情報を出力へ保存しない。結果・API応答・評価器・DB内容を追加に読まない。モデル生成・環境API・評価・記録コードの実行・コンテナ起動・保留群の読取は０。

## 判定

構文上の `call_api` 呼出し箇所を列挙し、直接の文字列キーによる添字、直接get、名前への束縛、全体引渡し、その他を分ける。文字列API名が静的でない場合も不明として残す。関数・lambda・生成器内、bridge名の置換や動的実行は適用可否を不明にする。項目数や呼出し箇所数をAPI回数・token削減へ換算しない。

現在のコード内で根の返却を変数へ束縛しただけで、その変数の将来利用項目が確定するわけではない。将来の入力プログラムを現在の判定へ利用しない。直接の添字候補でも、P37の対象API・公開項目・引数形に合うかは別記し、状態・鮮度・成功した返却・キャッシュ充足を確かめたことにはしない。明示的な `read_fields` は既存の別インターフェースとして数え、元APIの自動射影候補へ加えない。

## 検査と採否

未来の変数参照、別名、全体印字、動的キー、getの既定値、遅延実行、bridgeの再束縛、構文・サイズ上限を合成検査する。合成検査は実タスク性能の代わりにしない。

全12記録と不明を報告する。P37の既存対象に対する直接添字候補が０なら、単純な自動射影をランタイムへ接続しない。候補があっても、通常の静的な項目選択との差、状態と例外の保存、追加制御費用を固定するまで新しいモデル比較へ進めない。P38やP69の元の成否は変更しない。
