# P37：必要項目を指定する読取と、限定した再利用契約

2026年10月22日。P36の構造照合は返却全体を代替できなかった。次は、原APIと区別した `read_fields(api, arguments, fields)` という部品を実装する。原APIの呼出しを黙って部分辞書に変換しない。LLMへの新しい指示や未閲覧課題の実行は、この部品の検証には含めない。

## 範囲を固定する

最初の契約は公開AppWorld実装のSpotify `show_song_library → show_song` のみ。対象はSongのID、項目は `song_id, title, album_id, duration, artists`。両APIの実装と `Song._to_humanized_dict`、`UserLibrarySong._to_humanized_dict` を確認した。ライブラリ固有の `added_at`、Songの集計・計算項目、PlaylistやAlbumの似たIDは契約外にする。

ソースファイルは次のSHA-256へ固定する。実行環境に読み込む際は照合が必要で、文字列の版名だけで一致を保証しない。

- `apps/spotify/apis.py`: `eaa23bb250094ee3ff50330d3b75bdac86999394611a15b0b44934c90464b3f1`
- `apps/spotify/models.py`: `e35f8c4cd5fcd090d8e6d187bce0ee4c2e1e2f3202ec719186d0e663a13430a6`

公開の詳細APIには認証がなく、共通項目を同じSongから返すことを、この組だけの根拠とする。認証付き一覧の全項目を公開情報へ変換する規則ではない。保持は同じ実行・閲覧範囲に限定し、他の実行や利用者へ配布しない。

## 実行条件

ホストが実行範囲・状態版・契約版を渡す。状態版が不明、変化、別実行、契約不一致なら過去値を使わない。原APIを含む書込・不明な操作の送信前には無効化する。外部更新のない隔離環境、または信頼できる版管理が前提であり、一般の外部サービスの鮮度保証ではない。

最初の記録照合前に、同じ公開ファイルの `show_song`、`show_song_library`、`show_album`、`show_album_library`、`show_playlist`、`show_playlist_library` の本体と対応する通常・短縮変換も確認した。この６読取だけは状態版を維持し、それ以外の送信はGETでも全候補を無効化する。これは情報再利用の契約をAlbum・Playlistへ拡張する指定ではない。対象の２ファイルのハッシュだけで共通ライブラリや外部環境の不変まで保証するものではない。

必要項目を明示し、すべてを満たすときだけ再利用する。衝突した値を「最新が正しい」と選ばず取得へ戻す。未対応項目、引数、型、部分一致、APIエラー、未知の状態では通常取得して同じ射影を返す。通常取得のエラーはそのまま扱い、成功したことにはしない。

比較は、(A) 毎回取得して同じ項目選択、(B) 同一要求のキャッシュ後に同じ項目選択、(C) Bに上記の別API契約を加える、の３通り。同一要求キャッシュが持つ全返却から別の項目集合を返せるようにし、Bを弱くしない。型や項目名が似ているだけの未検証なキャッシュは比較方式に入れない。

## この段階で測るもの

まず合成の正負例で、返却一致・古い値・異なる範囲・衝突・欠落・エラー・改変耐性を検査する。次に全12の閉じた記録を使い、`show_song` に固定した `title, artists` を要求する補助プロトコルで３方式の値と再利用候補を照合する。その他のAPIを無視して鮮度を延長せず、契約外の操作で無効化する。過去の実際のプログラムがこの２項目だけを必要としたと仮定しない。

これで得るのは、明示項目読取の部品の挙動と、固定した補助要求列での候補件数。元のLLMが同じコードを出す、元の仕事を完了する、トークンや実時間が減るという結果ではない。実返却は各時点のキャッシュ判断後に照合し、その前には渡さない。不一致や対象０件も全件記録する。

## 採否

一般的な部分キャッシュ・意味に基づく問い合わせ再利用・状態付きツールキャッシュは先行研究がある。契約を追加したことは論文の新規性にしない。この狭い契約の適用範囲が乏しい場合、モデル実験を重ねず候補を保留する。実タスク比較へ進める場合も、同じ項目選択を使うA・Bと、モデルが項目を選ぶ費用、失敗、検査を含める。
