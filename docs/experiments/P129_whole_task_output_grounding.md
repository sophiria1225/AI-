This comparison is fixed from the closed P127 failure diagnosis while P128 is
running. No P128 task result, partial outcome or private model content selects
these conditions. P127 fetched the observed source metadata but wrote CSV
content contradicting it. The purpose here is to distinguish ordinary pre-write
feedback from deterministic payload repair. This is a single known-template
calibration, not a new verification method or general quality claim.

The [closed-source diagnosis](../../reports/P129_closed_source_diagnosis_20261026.json)
accepts the final writes in four prior successful runs and identifies source
contradictions in both P127 runs. An earlier invalid-credential write remains
unknown. These data-only checks dispatch no repair and establish neither live
counterfactual quality nor token savings.

## The only intervention is before a target CSV write

A pure monitor consumes prior trusted typed public API records. It checks the
single exact public instruction template and target path, successful logins
bound to the public supervisor identity, complete unfiltered source pagination,
song membership and observed title/artist metadata. Pagination and response
semantics are bound to the installed public implementation. Token rotation for
the same principal is allowed; failed reads are not successful source evidence.
Conflicting or incomplete evidence stays unknown. Artist order is not required
by the task: compare artist multisets within a cell rather than imposing a new
alphabetic or API-return order requirement.

Only a create/update operation on the exact requested CSV is eligible. All
normal catalog, resource and stop checks run before dispatch. Off sends the
original payload. Feedback blocks a proven inconsistent write before any API
request, retains a genuine unsent local record and returns a diagnostic so the
model can repair its own code. Repair changes only content when prior complete
evidence proves inconsistency and supplies an unambiguous CSV; it then makes
one ordinary paid request. Unknown/outside-scope operations pass unchanged.
There is no new API call, hidden database lookup, evaluator access or free model
inference to create the replacement.

Preserve original program/control packets. Record original, proposed and
effective argument hashes, prior evidence hashes, dispatch/typed nonce/outcome,
and an explicit intervention notice separate from API return/stdout. The inner
API record describes the effective action actually sent. Feedback must never
invent a sent request, nonce or successful receipt. The independent auditor
reconstructs each decision from the prior prefix, not from a claimed guard bit.
Monitor failures retain costs and stop rather than silently authorizing writes.

Account deletion is never blocked, repaired, reordered or performed by this
monitor. Missing backup evidence is not silently upgraded into a new deletion
admission rule. Subsequent deletion and final success remain ordinary behavior
and independent evaluation. A write/readback receipt alone is not correct CSV
evidence; a typed returned repair is counted as successful only when the monitor
also confirms that the actual saved backup matches the complete source.

## Primary decision and complete accounting

The primary comparison is repair versus feedback. Off is an auxiliary quality
control, not a weaker replacement baseline. Retain all six slots and every
failed, incomplete or unknown-cost attempt. Count all actor/focus input and
output, guard notices, expansion, recovery, unsuccessful repair attempts and
summaries. Cached input is still logical input. Host validation, interpreter,
setup, cleanup, evaluation and server time are separately measured; overlapping
durations and receipt bytes are not token savings.

The development gate requires all six independent evaluations and known usage,
no audit errors, intact runtime/grounding contracts and complete grounding
accounting. In each seed, repair must not lose a success achieved by feedback
or off. Aggregate two-seed whole-job tokens and a nonempty common-success
subset must both decrease versus feedback. At least one actual successful
repair must occur on a primary common-success condition. Merely proposed,
unsent or raised repairs do not meet that requirement.

Report every seed and mode, success losses/gains, all-task/common-success/
both-failed costs, sent versus successful repairs, feedback blocks and unknown
evidence. A quality gain over cheap failure is reported as quality improvement,
not as quality-preserving token savings. Aggregate success does not establish
noninferiority, unseen-task transfer or novelty. P128 and all older runs are
excluded from these primary totals. Raw task values, generated code, prompts,
credentials and reasoning remain private. The user writes the manuscript.
