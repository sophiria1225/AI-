# 追加開発課題：公開要求を見る前に選択規則を固定する

2026年10月21日。現在の2課題は接続確認に繰り返し使っているため、未調整の性能確認には使えない。次の開発観察では別のシナリオへ広げ、既存の全履歴・圧縮・台帳で何が起きるかを調べる。[選択規則](../../configs/P11_public_task_selection_v01.json)を、新しい要求本文を読む前に保存する。

学習集合のIDだけを読み、以前に公開要求を閲覧した4シナリオを除く。残るシナリオをID順に並べ、先頭4シナリオの`_1`を選ぶ。課題の本文、初期DB、難度メタデータ、解法、評価器、モデル結果を選択に使わない。簡単そう・難しそうという判断で入れ替えない。選定後に公開要求の性質を分類し、期待する集合処理が含まれない場合も記録する。

一つのシナリオの派生課題を独立な大量事例として数えない。今回読む4件とその派生は、今後の未閲覧確認用の集合から外す。既に見た最初の12件は4シナリオに属するため、12独立シナリオとは扱わない。

元の環境、利用可能な公開API、原データは維持する。必要な対象だけを人が抽出してモデルへ渡したり、正解に関係するAPIだけを与えたりしない。一方、この4件だけで大規模性や多領域の一般性を保証しない。実際に観測した対象数・依存関係・情報量を後で測る。

他案との比較：本文から提案が有利になりそうな課題を選ぶ案は、結果の解釈が狭くなるため初回の追加には使わない。原論文の失敗シナリオは機構確認の別候補として残すが、学習集合に存在せず、未閲覧の試験集合まで広げる選定とは分離する。全30シナリオを一度に実行する案は、基準と保存する観測が未確定のため保留する。ID順の4件も無作為標本ではなく、ベンチマーク全体の代表性は主張しない。

この規則で行うのは公開入力の選定だけで、モデル生成・API操作・評価は0回。P8/P9/P10の条件は変更しない。P10で接続と評価が成立した後に、使う基準、予算、対照、途中状態の記録方法を別計画へ固定する。
