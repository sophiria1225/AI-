# P64：公開名アクセスの通常基準を課題開始から比較する

## 問いと固定対象

P63で、従来のPython接続は説明未取得の公開API名も拒否すると確認した。標準AppWorldの公開名束縛に近い通常基準を用意し、この追加制約が課題の成否・時刻取得・仕事全体費用へどう関係するかを測る。新提案手法の実験ではない。

対象はP29で新たに引数検査を通る時刻要求があった写真 `34d9492_1` と電気代精算 `3c13f5a_1` の２既知課題。P63を見た後の開発選択であり、独立評価や全課題への一般化には使わない。各条件を課題開始から１回だけ実行し、結果に応じた追加seed・再試行・予算変更は行わない。

順序は写真documented、写真named、精算named、精算documented。２条件の順序を課題間で反転するが、反復による分散推定や時系列影響の除去はできない。

## 同じものと変えるもの

両条件は同じ持続Python、公開API集合、認証、引数検査、標準的な使い方の案内、文書表示、原課題、履歴表現、モデル・生成設定・予算を使う。開始時の公開課題と13個の保存DBのハッシュを元P29の初期記録へ照合してから生成する。DB内容は生成側へ渡さない。過去の生成、未来の公開応答、解答プログラム、公式評価を与えない。

documentedは従来のNativeCatalogで、説明取得済みの公開名のみを受け付ける。namedはP63のPublicNameCatalogで、正確な登録済み公開名なら説明取得前でも受け付ける。api_schemasへ表示する定義は、どちらも明示的な説明取得でだけ増える。未登録・非公開名や未知引数を自動修復せず、説明取得も追加しない。

モデルには各条件で実際に使える能力を正しく説明する。namedのsystem promptとrun_pythonの短い説明は、説明取得前でも名前で呼べることを示す。その入力長差も課金する。したがって、受付条件とその正確な説明をまとめたインターフェース比較であり、受付コードだけの因果効果とはしない。履歴や説明の省略方式も追加しない。

## 有限の予算

固定JSON：[P64_public_name_comparison_v01.json](../../configs/P64_public_name_comparison_v01.json)。

| 項目 | 固定値 |
|---|---|
| モデル／推論器 | 既存固定MiniMax M3 IQ4_XS／llama.cpp b11669-620d2225c |
| 入力枠／出力上限 | 65,536／4,096 token |
| seed／temperature／top_p | 各条件42から呼出しごと+1／1.0／0.95 |
| 各条件の生成上限 | 80回・論理入力+出力450,000 token |
| 各条件の実行時間枠 | 1,800秒。新規処理の受付と生成deadlineで制御 |
| 各条件API上限 | 写真160、精算80。完了通知も含める |
| 初期化／評価／idle待機 | 各120／180／60秒まで |
| worker／所有推論器の寿命 | 9,600／10,080秒。起動待ちは300秒まで |
| 合計の最大配分 | 320生成・1,800,000 token・480 API・４評価 |

各条件の最初はcache_prompt=falseで、実測cached input=0を検査。後続はtrueで、キャッシュ分を含む全入力+全出力を主費用とする。残り時間の動的な通知は与えず、固定の予算案内を共通に与える。入力計数の後に4,096出力を予約できる場合だけ要求する。SSE終端使用量のない要求をゼロ扱いしない。途中の生成内容は実行しない。

Pythonは既存の制限付きコンテナ。各プログラム最大90秒、各内部APIを別々に数える。実行時間枠の末尾に既に受け付けた処理や片付けが残る場合があるため、実測全経過時間も別に残す。所有プロセスの有限寿命を最外側の停止境界とする。

## 失敗・停止・集計

予算終了、使用量不明または使えない生成応答では、その条件を終了する。環境の作用が既知なら凍結状態を１回評価し、次の固定条件へ進む。不明使用量は欠測のまま集計し、総費用の優位を断定しない。実行の置換はしない。

API作用不明、開始状態不一致、実行・片付け・評価の異常、モデルやソースの変更、ユーザー停止、所有プロセスの期限では残条件も停止する。未実行を失敗や費用０の観測へ置換しない。停止ファイルは `.runtime/P64.stop`。評価の内容はモデルへ返さず、公開するのは公式集計だけとする。

全４条件の成否、全入力・出力・cached input・不明数、生成回数、API回数、公開時計の返却、未送信の時計要求、実行・初期化・全経過時間、推論器のロード・RSS・swap・終了を報告する。SSE、要求、応答、イベント、集計を後から照合し、成功条件だけ選ばない。P29/P55の公式結果は変更せず、異なる計測条件の過去実行との差を効果量としない。

この２課題の結果で新規性や一般的な品質維持を確立したとは扱わない。予備的４ページ原稿の接続条件・適用範囲を補強する材料とし、主たる研究目的は必要な情報と最終品質を保った仕事全体費用の削減である。保留12課題は閲覧しない。

## 実行前条件

実装・計画・合成接続検査を同じcommitへ固定し、pushとPRのCIでworkflowと個別jobの成功を照合する。そのcommitの別作業木から、所有する有限の推論器でのみ開始する。準備時点では生成・環境API・評価を実行していない。
