# P29：課題内で変数を保持する通常コード方式の比較条件

2026年10月22日。これはP28の全件監査を待つ比較仕様であり、実行判断は`reports/P29_activation_v01.json`で別途固定する。その記録がない場合、バッチ実行器は開始を拒否する。

比較対象はP28と同じ４既知課題、同じ順序。写真整理160 API、他３件80 API、80生成・45万トークン・30分・4,096出力、同じモデル・温度・seedを維持する。P28の全結果から、変数の状態を分ける比較に意味があると判断した場合にのみ実行する。特定の失敗だけを選ぶことはせず、確認用12シナリオは使わない。

変更するのは、Pythonの変数・関数・importを同じ課題内で保持する能力と、その事実を知らせる指示。P28の提供済み関数の説明、基本ツール、API公開範囲、費用制約、観測記録の再読は維持する。プログラムの状態を毎回初期化するP28との差と、通常API基準との差を個別に示す。CodeActやCaveAgentを完全再現した条件とは呼ばない。

最終成功と全費用を主に報告し、変数未定義、同一引数のAPI再取得、元観測の再読、初回API到達、コードの出力上限、移管・終了の不具合を補助集計する。同じ引数で呼んだというだけで、環境変化を無視して全て無駄と分類しない。プログラム間の状態保持は既存機能であり、改善しても独自方式の性能としない。

コンテナの全寿命と処理時間を記録し、終了時の削除も確認する。１プログラム最大90秒。タイムアウトで実行状態が失われた場合には再生成・再試行をせず、その課題を未完了として残す。API応答不明時も追加操作を止める。Pythonエラー前のAPI変更や変数代入は巻き戻さない。

公開APIの環境状態、履歴、予算の境界保存は継続するが、Pythonのヒープ、乱数、スレッド等を復元する機能はない。因果的に同じ途中状態へ完全復帰できるとは主張しない。実時間差はコンテナ寿命・キャッシュ・処理経路の差を含み、変数保持だけの速度効果と断定しない。

全４件が独立評価を終えてから、保存したソース、実際のモデル入力、内側API、費用、コンテナの寿命をまとめて監査する。単発の開発比較なので、有意な一般優位は主張しない。この通常比較を閉じた後、残る現象と近接研究の具体的な差に研究の中心を絞る。
