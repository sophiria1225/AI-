# P18：未使用の開発シナリオで必要な機構を確かめる

2026年10月21日、P17生成中。先に[選定規則](../../configs/P18_public_task_selection_v01.json)を記録し、課題ID一覧から４シナリオを選ぶ。その後に公開の要求文だけを読む。生成条件は別に固定し、P17と同時に大型モデルを動かさない。

## この順番にする理由

P11の４課題は、検索と原観測の再読を備える全履歴基準で全件成功した。P13/P14を加えた結果だけでは追加の記憶機構の必要性を示せず、P14の出典契約には自作側の不整合もあった。P16で元入力の誤完了も確認できなかった。そこで、同じ４課題に改良を合わせ続ける前に、未使用の開発課題で、観測・保持・実行にどんな問題が残るかを調べる。

これは新しい方式の本評価ではない。失敗があれば、実行基盤の不具合、対象探索、情報保持、操作、完了判定を分ける。成功も全て残し、失敗した課題だけを全件の結果として示さない。追加機構が不要な結果も許容する。

## 選ぶ方法と採らない方法

既閲覧の８シナリオを除いたtrainのIDを辞書順に並べ、先頭４件のvariant 1を選ぶ。全体の環境・データ・APIを保ち、正解に必要な対象だけへ縮小しない。選定後に実際の対象数や難度を推測で補わない。

- 正解コード、隠し評価、難度ラベルから失敗しそうな４件を選ぶ案は採らない。確認用の正解を設計側へ漏らすため。
- 要求文を読んでから都合のよい課題へ差し替える案は採らない。対象の選定と方式の結果を混ぜるため。
- 全30シナリオの一括実行は現時点では採らない。今週の期限内に、原記録の原因確認まで完了できる単位に区切る。
- 前の４課題の派生variantだけを使う案も採らない。既に見たシナリオに偏るため。

今回追加するのは新しいシナリオであり、以前の結果に追加して方式を調整した後「未調整の確認データ」とは呼ばない。最初の全履歴観察が終了してから、残る機構に対応する比較を決める。

## 事前の制約

最初はP11と同じ強い全履歴基準。MiniMax M3 IQ4_XS、64K、公開APIの発見と標準ツール呼出し、原観測のページ読取、同じ初期seedと予算を使う。全履歴が入力上限に達した場合も結果に残す。現在の時点で、これらが長期課題・難課題であるとは決めない。

モデル生成の前に、選定記録、実行ソース、各試行の総予算、モデル版、サーバーの稼働期限、独立評価の分離を固定する。元のデータ・記録や既存の実行作業木を上書きしない。

## 選定後に固定した実行仕様

選定規則をコミット`438e391`で保存してから、34d9492_1、3c13f5a_1、60d0b5b_1、6104387_1をこの順に選んだ。要求文の分類は[公開情報だけの記録](../../reports/P18_public_requirement_characterization.json)。日付・対象の分割、複数アプリを横断する計算、時間関係の照合、複数集合の統合と出力後の処理を含む。難度や対象数を確認した結果ではない。

１課題につき80モデル呼出し、80公開API要求、総入力＋出力450,000トークン、1,800秒、１生成4,096。４課題のモデル上限は320呼出し・180万トークン。各課題の終了後に独立評価を行い、その情報は次のモデル入力へ渡さない。seed 42からの実行役の呼出し順、温度1、公開APIの発見規則、24,000文字の原観測ページ、64Kモデル上限はP11と同じ。

P18は全履歴だけを使い、記憶役の追加やP17の修正版台帳はまだ入れない。２つを同時に変えて未知課題の失敗を解釈しにくくすることを避ける。最初の比較から独自手法の改善率を出す計画ではない。

P17_01が正常終了するまで実行器を待機させる。現在のサーバー期限は2026年10月21日13:00:13 UTCで、開始時に監督プロセスの実際の期限も確認する。４課題の最大実行時間と評価の余裕を含む8,100秒が残っていなければ開始しない。状態保存はP11と同じDB／ハーネスの差分記録で、１課題512MiB以内、１境界128MiB以内。全原環境を毎回複製しない。
