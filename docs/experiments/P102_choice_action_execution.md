# P102：P101の全予定出力を通常実行口で確認する事前設計

2026-10-24. P99の全件結果をまだ開かず、P101の描画・計数・生成も始まる前に範囲を固定する. P101は出力の静的な形式を測るため、実行できたことは証明しない. P102では、その全36予定枠を対象に、既存P94と同じ先行操作照合の後、保存出力を通常実行口へ渡す. この時点では設計のみで、実装・最終計画・実行は未完了.

## 全枠を残す

P101の６入力×auto/required×３反復、順序も全36枠もそのまま使う. P101の終端使用量が既知で原応答まで監査された出力を各１回確認する. 本文のみ、形式不整合、途中切れも除外せず、元の実行口の判定を記録する. 本文からコードを救済したり、引数やspan参照を修正したりしない. P101の不明・未実行枠は理由付きで残し、出力を生成し直さず、実行可能な出力として補完しない. 既知出力の一部だけを成功例として選ばない.

各実行で既知のCSV課題 `6104387_1` をseed42の新規環境に初期化する. P94と同じP80保存記録に対し、先行12コード・28 APIの要求、返答、例外、公開標準出力、公開schemaを照合する. 保存返答をサービス応答の代わりに使わない. 照合不一致または不明な作用が発生した場合は、その出力と後続条件を停止して残し、別の反復で置き換えない.

先行操作の一致はPython変数、DB全体、元のwarmモデル状態の完全な復元を意味しない. 全件が同じ１保存文脈に由来する. 36枠や全66条件組を独立した課題数へ数えない.

## 有限予算と開始条件

各条件のAPI上限80は先行28 APIを含み、全36条件で最大2,880 API. 能動処理は全体1,800秒、各条件180秒、各Pythonプログラム30秒、bridge通信30秒を上限とする. 終了処理は別途記録し、所有bridgeとPython環境の停止を確認する. モデル生成、評価器、未見課題の閲覧は０. ユーザー停止を優先し、自動再試行は０.

P101の所有推論器停止、全36枠の監査、閉じた原応答のhash、P101最終計画、保存prefixのhashを最終P102計画へ結びつける. P101が途中停止した場合も、監査が成立した既知出力だけを元の枠で実行し、不明・未実行を保持する. 監査の不一致がある状態では開始しない. P102実装と最終計画を固定した同一headのpush/PR両workflowおよびaccounting-and-syntax jobの成功後にのみ実行する.

## 比較と原稿への使い方

全36枠の出所、提出数、実行プログラム数、送信API列、公開実行結果、通常の形式拒否と実行時例外、未知作用、停止理由、再構成費用を記録する. 全12条件内の反復比較と全66条件組×９対応を残し、提出も実行もない空API列どうしを有効操作の一致へ数えない.

設定内のA/B、C/D、A/Nと、同じ入力のauto/requiredの差を全件表から読む. P101で測る入力token列・生成制約の差も残し、tool_choiceの差を文法だけの単一原因へ読み替えない. 通常設定で形式拒否が解消する場合、解消しない場合、入力が一致しても実行が揺れる場合のいずれも保持する.

これは新しい制御方式でも、CSV完成・最終品質・全仕事削減の測定でもない. 結果を見てから新しい採用閾値を設定しない. 局所の提出形式、実際の操作、最終成果を分けるための追確認とする. [P101の固定設計](P101_choice_context.md)／[P94の保存出力実行](P94_saved_action_execution.md).
