# P5：Ansibleの単一／固定2担当を共通条件で観察する

2026年10月20日。P4と中間資料の完了後に準備した開発比較。開始前に2試行を固定する。P4の結果を既に見ているため、未調整の確認評価とは呼ばない。

## 目的と条件

同じ公開要求を工程で分担すると、調査・再現から機能修正へ進むか、具体的な確認・変更のやり取りが生じるかを観察する。P3と同じ実装役・検証役を交互に呼び、双方へリポジトリ全体の読取・変更・検査を認める。役割境界と排他的な更新責任は別であり、作業移管や自動再編は行わない。

| 条件 | 両方式で共通 |
|---|---|
| 課題・公開要求 | P4のAnsible基点、問題文・要件・インターフェースの全3項目 |
| モデル | MiniMax M3 IQ4_XS / KV q8_0 / 64K / 1物理スロット |
| 生成設定・ツール | P4と同一 |
| 各試行の上限 | 60呼び出し・600,000入力＋出力・7,200秒 |
| 公開検査 | 同じ131既存テストを含む設定 |
| 実行順序 | 固定2担当を1回、単一を1回 |
| 最終評価 | 各停止時の成果物を凍結し、別の環境で一度だけ評価 |

## なぜP4との直接比較から、2試行の共通条件へ変えたか

最初はP4と同じ3,600秒で2担当を追加する案を考えた。開始前にP3の時間を点検すると、固定2担当は275,008トークンで2,274.54秒、275,531トークンで2,324.12秒だった。単純比例で600,000トークンへ換算すると約4,962秒／5,061秒となり、60分が先に制限する可能性がある。これは異なる課題からの粗い参考値で、実際のP5所要時間の予測精度を保証しない。

トークン費用の観察を実行時間上限だけで打ち切る影響を弱めるため、**両方式とも7,200秒**へ広げ、新しく各1回実行する。単一も時間残量通知の入力が変わるため、P4をそのまま同条件の対照にしない。トークンと呼び出しの上限は増やさない。P4の条件・結果・資料は上書きしない。

時間上限だけを2担当へ追加する案は同条件ではなく、P4を成功まで延長する案とも違う。片方の結果で他方の予算・指示・順序を変えない。実行途中の新しい修正指示、P4の再現スクリプトや失敗分析、独立評価の内容はモデルへ渡さない。内部推論の内容を研究者向けに表示しない。

一つの物理スロットなので、担当切替時のキャッシュ再利用や実時間は構成とともに変わる。実時間の一般的な優位や物理並列化の性能は主張しない。原記録へキャッシュ対象入力とサーバーの実行条件を保存する。前のサーバー監視期限が両試行の途中で効かないよう、試行前に同じ推論設定で監視プロセスを更新する。

## 実装と事前検証

共通実行器の担当数を1または2へ一般化し、P3と同じ交互実行・相手の公開操作の共有・版に結びつく完了宣言を使う。1台帳に全呼び出しを計上する。P4に対する設定差は、段階のメタデータと3,600→7,200秒だけを許可し、両方式の設定ファイルは完全に同一にする。

最初の1担当の完了宣言で全体を終えないこと、他担当の変更で古い宣言が失効すること、2担当へ予算を倍付けしないこと、公開入力・モデル・費用上限の改変を開始前に拒否することを模擬操作で確認する。模擬応答の数字をモデル性能には加算しない。基点の実ツール校正は変更していないコードと固定記録を照合して再利用する。

## 開始前に決める観察項目

1. 最終成否、全入力＋出力、呼び出し数、実時間、メモリ、停止理由。
2. 原コードへの変更・再現テスト・公開検査の時点と担当。
3. 一方が提示した具体的な公開観測への他方の対応。単に同じファイルを読むことと区別する。
4. 同じ事項についての修正依頼や変更の往復。ただし回数だけで無駄や因果依存としない。
5. 公開検査の合格と要求完了の相違、移管が必要だと判断できる材料の有無。

片方が成功しても1課題・各1回なので、品質同等や一般的な費用削減は確定しない。両方で機能変更に至らなければ、作業移管の比較へ直ちに進む根拠にはしない。結果に合わせて「依存が強い」等の分類を作り直さない。基盤故障・費用不明は試行を残して停止し、成功までの自動再試行はしない。
