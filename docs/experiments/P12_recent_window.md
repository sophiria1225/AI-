# P12：同じ4課題で直近履歴と原文再読を比較する

P11の全履歴に対し、まず通常の直近履歴保持で十分かを調べる。複雑な生成型圧縮を加える前の強い単純対照とする。これは独自アルゴリズムではない。P11の途中で方式を差し替えず、全4試行の終了後に、同じ初期環境から各課題を1回ずつ実行する。

## 固定するもの

P11と同じ4シナリオ・同じ順序、MiniMax M3 IQ4_XS、種42からの呼び出し順、公開API仕様と発見規則、指示、24,000文字の原観測ページを使う。上限は各80モデル呼び出し・80 API要求・450,000入力＋出力・1,800秒・生成4,096。共通の途中保存と独立評価も使う。新しい評価結果を生成側へ返さない。

4課題は本文を読む前のID順で選定済み。P12計画時点でP11の第1、第2課題は成功、第3は進行中、第4は未開始だった。これは既に見た開発課題の比較で、未閲覧の確認実験とは呼ばない。P11の成否を理由に課題を交換しない。

## 変えるもの：作業履歴の選択

1. systemと元のtaskを除いた標準会話のメッセージをJSON化し、同じモデルのトークナイザーで長さを測る。API仕様はこの作業履歴の指標に含めないが、実際のモデル入力費用には全て含める。
2. 4,096トークン以内なら全履歴と完全に同じ入力を渡す。
3. 超えたら直近の応答から、要求と全ての実結果をひとまとまりで残す。古い応答を一つずつ加え、最初に4,096を超えた候補の直前までを使う。長さの大域的最適化を保証する規則ではない。
4. 最新の1応答だけで超える場合は、その1応答を保持して超過を記録する。要求だけを残して結果を落としたり、結果を別要求へ付け替えたりしない。モデル全体の64Kと生成予約の検査は引き続き適用する。
5. 原履歴は削除しない。部分保持の入力には利用可能な元span IDと記憶の範囲を付け、共通のread_spanで原文を読み直せる。再読はAPI操作を再実行しない。追加したID一覧・説明も費用に含める。

4,096は既存の導入設定と対応させた事前値であり、この4課題の結果で最適化した閾値ではない。JSON化した履歴の指標と、テンプレートを通ったモデル全体の入力長を混同しない。

選択のためのLLM呼び出しは0回。トークン計数の要求回数、失敗、実時間は記録する。計数に失敗した場合も既に終わったAPI操作は再実行せず停止する。失敗した計数まで全時間へ含める。部分保持の注記も変わるため、純粋な情報削除だけの効果とは主張しない。

## なぜこの比較を先にするか

P6の圧縮条件は古いAPI接続だったため、新しい全履歴にその成績を直接並べても記憶だけの比較にならない。また、生成型の圧縮には追加の入力・出力と状態維持が必要になる。まず同じ接続の安価な既存対策を比較し、それで十分なら追加の独自機構を先行させない。

固定件数だけを残す案は、応答ごとの大きさが異なるため今回は選ばない。要求・結果を個別に削る案は対応を壊すため選ばない。大きな最新応答を切り捨てて強制的に4Kにする案、正解の対象一覧を与える案、見える成功だけで方式を調整する案も採用しない。

FOCUSの再実装と対象台帳は次の比較候補として残す。公開仕様が履歴外のtools欄にもあること、複数操作を1応答に含むこと、更新費用をどう数えるかを明示してから接続する。原稿の成績の完全再現とは呼ばない。

## 検証と成果の読み方

全保持は保存済みP10入力とペイロード・ハッシュが一致した。部分保持、複数操作の一部選択、履歴なし＋空台帳の4形式は現モデルの入力計数が成功した。生成・環境実行は0回。[入力検査](../../reports/P12_memory_view_controls_v01.json)。これは短くした入力で正常に仕事ができるという結果ではない。

操作・観測の対応、不正で未実行の要求の保持、保存値の破損検出、原入力一致、計数失敗後の非再実行を検査してから実行する。実行時の全ての選択について、計数文字列のハッシュと結果を残し、終了後にモデルを呼ばず選択を再計算して実入力と照合する。

最終成功と総トークンを同じ課題で並べる。再取得、余計な操作、途中保存、キャッシュ再処理と実時間も別に示す。4課題×各1回の探索的結果から品質同等性・一般的な削減率・新規性を確定しない。必要な原文が落ちても再読して正しく完了すれば、忘却による失敗とは扱わない。
