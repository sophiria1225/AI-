# P30：APIを再送せず、Pythonの実行前半を再生できるか

2026年10月22日、P29実行中に仕様を固定する。P29全４件の実行・独立評価・監査が終わるまで、実課題を読んで再生しない。成功した課題だけを選ばず、同じ４件を全て対象にする。これは新手法の性能実験ではなく、引き継ぎ・分岐比較を正しく作るための前提確認である。

状態付きエージェントでは、会話と環境のDBを復元しても、Pythonの変数・関数・importは元に戻らない。今回は保存したプログラムを同じ隔離Pythonで順に実行し、API要求に対して元の公開応答だけを返す。要求の名前・引数・型・順序が一つでも変われば停止する。元の書込み操作も、記録済みの応答を返すだけで実際には送信しない。ホスト上で生成コードを実行しない。

プログラムごとに、API列、印字内容、Python例外、出力の切り詰め、完了宣言、応答不明を別々に照合する。どれかが異なれば、それ以降のプログラムへ進まず、相違と費用を残す。モデル呼出し０、実AppWorld操作０、評価器実行０で行う。実コンテナ５合成プログラム・２セッションで、保持と例外後の続行、変更された書込引数の拒否、隔離条件、削除を確認した。

全て一致しても、Pythonの全メモリが一致した証明にはならない。印字されない値、オブジェクト同一性、乱数、時刻、スレッドなどは保証しない。将来の任意の動作の同一性も未確認。環境DBそのものの復元は別の検査である。元の成功率を置き換えず、再生の一致率をタスク成功率と呼ばない。

全プロセスのコピー、pickleだけの保存、元APIの再送は選ばない。対応外の状態まで完全復元と誤認したり、操作を重複させたりするためである。通常のrecord/replayを新規技術として発表せず、次の研究比較で本当に同じ実行前半を条件にできるかを判断する。
