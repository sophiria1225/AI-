# P42：API仕様だけの出力を区別する費用点検

2026年10月22日。P33の全出力省略は入力を短くしたが、最終品質を保つ総費用削減にはならなかった。次に、仕様説明の出力とタスク中の観測を区別できるかを、モデル実験の前に点検する。

## 固定する対象と方法

以前から使っているP29全４課題・８応答後の境界を全て使う。未閲覧12シナリオは対象外。各課題について、共通の省略説明を持つ全履歴、以前の全stdout省略、仕様だけのstdout省略の３入力を構成し、計12入力を同じモデルの入力計数器で測る。生成・アプリのAPI・環境再生・評価器は呼ばない。

対象は以前の全stdout省略が扱えた、最新ターン以外の正常・非空出力に限定する。その中でも次を全て満たす出力だけを仕様候補とする。

- 元のAPI要求が全て既知の`api_docs`読取で、成功した実送信の記録と対応する。
- 元のstdout全体が、その返却を既定のJSONまたはPython表示で直列化した文字列と完全一致する。
- エラー、途中で切れた出力、未知効果、完了宣言を含まない。
- 返却がJSONの辞書・配列として読める。トップレベルにerror/detailを持つエラー候補や、解釈できない文字列は残す。

文字列の一部分だけを削除しない。仕様以外の要求や追加説明を含む出力は残す。仕様と似たフィールド名を持つ作業データも残す。全体一致がないものをLLMや曖昧照合で補わない。

省略する場合も、元の命令、状態、参照IDを保持し、全文へ戻る同じ省略標識を使う。元の原記録・Python状態・基本ツールは変更しない。完全一致は出力内容を分類する根拠であり、将来不要という証明ではない。

## 次に進む基準

まず各課題の正確な入力token、適用出力数、適用できなかった理由を示す。少なくとも２課題で１入力あたり1,000 token以上の削減が得られる場合だけ、品質・再取得・継続全費用を測る追加生成の設計を検討する。この閾値は追加計算を配分する開発上の基準であり、統計的有意性や実用価値の保証ではない。

初回入力の削減を、全体費用や最終品質の改善に換算しない。今回の結果だけでAIが同じ行動を取るとも主張しない。API仕様圧縮や外部参照は既存方式で、新規性は別に確認する。一律省略を再び実行する、仕様だけなら無条件に安全とする、適用しやすい課題だけ残す案は採らない。
