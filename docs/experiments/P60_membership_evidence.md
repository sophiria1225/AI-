# P60：必要な所属判定だけを再利用する通常対照

P59で確認した既知の支払依頼に対して、肯定・否定・不明を分ける部品を実装する。一般的な集合照合と問い合わせ再利用の通常対照であり、新アルゴリズムとしての採用ではない。LLMへの接続や原APIの置換は行わない。

必要な返却は「指定したメールが、roommateまたはcoworkerの連絡先に含まれるか」。要求解釈・関係名・キーは分析者が与える。原APIの全文を求める検索とは別の補助要求で、元の６検索を自動削除したことにはしない。

規則は次のとおり。

1. 同じ情報源・利用主体・状態版・契約版の有効なページに対象の証拠があれば肯定する。
2. 対象がなく、両方の関係について先頭から連続した全ページと終端が確認できれば否定する。
3. 部分取得・状態変更・別主体・契約変更・不足や矛盾は不明にする。未知を否定へ補完しない。
4. 終端・状態版は信頼する接続側が与え、モデル自身には宣言させない。実装単体は外部更新を検知しない。

公開AppWorld 0.1.3.post1のphone.search_contacts、Model.retrieve_records、paginateを確認した。query空では利用主体と関係で絞り、並べてからページを切る。固定版の保存観測を使う補助試験では、上限未満の先頭ページを終端として扱う。任意のAPIへこの条件を一般化しない。

保存済みの受信依頼26件から26個の補助所属要求を作り、(a)観測なし、(b)一方の関係だけ、(c)両関係の終端あり、(d)同じ行だが終端証拠なし、(e)状態版変更、(f)利用主体変更の全６条件を実行する。(c)は同じ行の通常の集合結合と比較する。全156個は同一既知課題の制御確認で、156課題でもモデルの実際の要求でもない。正解タスク評価・成功率・節約額に使わない。

追加のモデル生成・入力計数・環境API・評価器・DB・保留群閲覧を０、実行60秒、部品の行上限4,096・ページ上限128に固定する。契約・ソース・仕様を保存してから１回実行し、全条件と不明を残す。失敗した場合、入力・条件を都合よく変えず不具合を記録する。タスク品質・総token削減・独自性は別途未検証。
