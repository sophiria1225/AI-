# 要約後の入力短縮が作成費用を回収したかを調べる

P120の中間成否を読まずに範囲を固定する. P118とP119の結果は既知である. 対象はP118、P119、P120の４課題×２方式、全24条件. 成功や要約の採用の有無で条件を選別しない. 全８枠ずつと各所有serverの閉鎖、監査、session点検がそろってから、保存記録の指紋を固定し、一度だけ計数する.

## 調べる量

実際の行動列、応答、API返却、予算通知、要求の非messageパラメータを固定する. 各実モデル要求について、次の２入力を作る.

1. 実際に送信した入力. 既知の入力token数は、元の実測値と一致することを確認する.
2. 実際に履歴を置換した後だけ、古い履歴を復元した入力. 要約が未採用なら実際の入力と同一とする.

同時出力で要約metadataを再入力しない処理は、両入力へ同じように適用する. 必須または任意欄の提示、追加指示、schema、現在のコードと返却、未来の保存ターンは変えない. 別呼出し要約の要求も両側で同一とし、費用を残す. 元のarchiveは変更しない.

入力差 `D_j = 復元した入力token − 実際の入力token` を各要求で求め、全保存要求にわたる `D = Σ D_j` を出す. 一度の短縮量を後続呼出し数へ機械的に掛けず、後続の各入力を実際に数える. 別要約の実測入力と出力を `C` とし、各時点の累積入力差と `C` の差も示す. 同時出力の要約本文だけの生成tokenは分離計測していないので、その費用を推定して差し引かない.

## 解釈の範囲

`D − C` は同じ応答列と残予算通知を固定した算術上の回収額である. 要約をしなければ行動、出力、残予算通知、再調査、成功が変わり得るため、別方式の実測費用や因果的な節約とは呼ばない. 元の全仕事比較、失敗、未知、採用基準の判断は変更しない.

不明なモデル使用量は、入力だけ数えられても不明のままにする. 保存要求が欠けていれば仮想要求を作らず２枠を欠測として残す. 送信されなかった最後の入力候補を実モデル費用へ加えない. 仮想の復元入力に実際の出力予約を足してcontext上限を超える場合、既知総費用へDを足して仕事token予算を超える場合を明示する. 上限内でも、その仮想経路を実行できる保証にはしない.

## 有限な手順

最大24条件、各80要求、各２入力、合計3,840入力とする. 全体900秒、１条件のrendererは120秒と2GiBのRSSまで. １私有入力16MiB、私有入力合計1GiBまで. P110で固定した語彙計数専用binaryとライブラリ、同じモデルrevision、llama.cppのcommit、chat templateを確認する. 推論contextは作成せず、decode、モデル生成、保存Pythonの実行、API、評価、課題databaseの読出しは０. 自動再試行はしない.

準備ソースを同一headのpushとpull_request両workflow・両検査jobで確認する. 全元条件の閉鎖後に記録を一度だけ束縛し、その計画を含むheadの両workflow・両job成功後に計数する. 未知、欠測、途中失敗を保持し、ユーザー停止を優先する. この診断自体を新提案手法や新規性の証拠にせず、原稿と未見12課題は保留する.
