# P135: observed entity-field obligations after accepted checkpoints

P135 is a separate recovery namespace for the **unstarted, unchanged P134 six-condition comparison**, not an IDs-only ablation. The original P133 report-builder failure and original P134 failed queue remain immutable. No P133 scientific outcome changes conditions, seeds, mechanisms or budgets.

P135 is a finite development comparison on one already known CSV task. It tests whether automatically showing bounded, unfilled entity-field obligations after an accepted summary improves quality-conditioned whole-job cost over a counts-only policy with the same evidence and query capability. The original P123 rolling interface is a separate strong anchor. This protocol does not claim a novel general method, unseen-task performance, or guaranteed completion.

Design evidence comes from closed P123/P127/P132 records and public API implementations. P133 outcomes are not consulted to select conditions, seeds or limits. P133 is a separate ordinary checkpoint-payback comparison; its forecast controller is disabled in P135. No hidden evaluator content or reserved scenario is used.

## Controls and intervention

`raw_anchor` retains the original P123 initial prompt, tool schemas, full receipts, ordinary rolling controller and budget notification behavior. It runs the same trusted observer and checkpoint capture as the other modes, but receives no new guide, query tool or progress notice. Thus its operational observer/capture costs are still recorded.

`counts_only` and `entity_fields` have identical initial messages, common guide, `read_obligations` schema, evidence, source capture, ordinary environment capability and limits. Both receive the current collection status, counts and a query handle after accepted checkpoints. Only `entity_fields` automatically expands up to 16 song IDs with their unfilled `title`/`artists` obligations. Selection is by ascending numeric ID, fixed before the cohort. The count policy can explicitly obtain the same rows through the common tool.

The JSON notice has a shared 2,048 UTF-8 byte cap; the common introductory text is additionally charged. Actual sizes are not padded to equality. The native input count and sent request must use the same final messages. A notice is transient on the next actual actor dispatch after an accepted revision, never inserted into the raw archive or focus input. Rejected summaries do not trigger capture. Unsent admission failures have exposure zero. A dispatched request with unknown usage still consumes the notice and follows the existing stop rule.

The host captures once per accepted revision in every mode. `prepare_packet` validates the captured packet hash and execution/requirement/contract identity without duplicating capture. The live adapter binds that packet to the original observation prefix and program boundary before count/send. Hash validation alone is not source reauthentication; the independent auditor rebuilds the store from saved trusted observations.

## Public source contract and uncertainty

The pure monitor accepts only the existing public export-request template and pinned public API/serializer implementations. It does not infer the task from evaluator tests or inspect database state. The target set is the observed complete union of song library, album-library song IDs and playlist-library song IDs.

The new ordinary partition extension handles a specific previously unsupported case: separate `is_public=False` and `True` playlist queries. Public code filters the same user's playlist collection on a non-nullable boolean and then paginates. Each partition must have every page through an observed short terminal page, consistent page limits/contents, matching returned flags and no duplicate playlist IDs across partitions. Same-principal typed receipt checks are inherited. An unfiltered/filtered mixture, contradictory pages, unknown effect or unsupported source mutation produces a permanent taint. The extension has a distinct contract binding the pinned public files, old monitor dependencies and new module bytes. Unobserved external mutations remain outside the immutable-source assumption.

Enumeration is `open`, `closed` or `unknown`. A complete-partition flag never overrides taint. In open/unknown scope, totals are null and there is no purported complete obligation list. A known-empty closed scope is represented separately. A returned full-schema response missing required metadata is contract uncertainty, not a legitimate partial record. Album/playlist partial song serializers may legitimately expose title and artist IDs without artist names; names remain unfilled until successful typed public evidence supplies them. Observations outside the target union do not expand that union.

Each required field retires only when supported by the current trusted evidence. The ledger is not reconstructed from a summary, model assertion or requested API arguments. Raised/unsent/unknown responses do not supply values. Known side-effect-free read failures can leave earlier evidence intact. Observed account deletion makes the current acquisition source unknown without intercepting or blocking deletion. Field acquisition completion is not proof that CSV content, backup, deletion order or official task success is correct.

The common explicit tool is `read_obligations(op, handle, cursor, limit)`. All four arguments are required. `snapshot` uses null handle and cursor 0 and returns current metadata with zero rows. `page` requires a 64-hex handle, nonnegative cursor and limit 1–32. It returns bounded observed IDs, missing field labels and already-observed artist-ID dependencies lacking names. Its JSON response is at most 8,192 bytes, with explicit total/continuation information. A stale handle returns fresh metadata and no old rows; the model must explicitly query the new handle. The tool issues no environment API call, writes no value and generates no API action. Model-visible query responses and their transport/time costs are included.

Caller query errors are ordinary `ObligationQueryError` feedback. Internal source/hash/representation violations stop the runtime; they cannot be mislabeled as recoverable input errors. Unknown evidence is an ordinary uncertainty packet, not an internal exception. Ordinary API dispatches are not rejected merely because coverage is unknown.

## Outcomes and gates

Primary comparison is `entity_fields` versus `counts_only`; `raw_anchor` is secondary. Report every paired official quality transition—common success, quality gain, quality loss, both failed and not both evaluated—with all known token subtotals and unknown counts. No byte-to-token conversion or free query/capture allowance is used. Actor, focus, failed requests and all model-visible control costs count from task start.

The development gate requires all six officially evaluated with known usage, no paired success lost to either control, fewer aggregate and common-success whole-job tokens than counts, fewer aggregate tokens than raw, at least one primary common-success pair, actual entity-row exposure on primary common success, no audit error and complete intact mechanism accounting. A capture or notice prepared but never sent is not exposure. Cheap failure, a favorable seed alone, a subset-only reduction, unknown usage, or evidence coverage without official success cannot satisfy the gate. Raw common-success costs are reported even though the additional fixed raw cost gate uses its all-job total.

The six-cell design tests this finite policy difference on a known task. Same-capability reproducibility of the policy is not a novelty refutation, and passing synthetic correctness cases is not empirical task success. Overlap with ordinary checklists, typed provenance/query systems, runtime inventory and FOCUS's entity-omission observation remains acknowledged. Any broader novelty or quality-preservation claim requires separate evidence and is not established by this protocol.
