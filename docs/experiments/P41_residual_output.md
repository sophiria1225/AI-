# P41：停止入力に対する残量出力枠の限定検証

2026年10月22日。P40終了後の計数で、固定4,096出力の予約が停止理由となった３入力のうち２件には、2,471／3,878 tokenの出力枠が残った。まず通常の基準実装として、この枠を実際の生成上限へ渡せるか、モデルが完結した道具の指示を返すか確認する。

## 範囲と選定

P40の使用量が確定したtoken予約停止を全て使用する。写真整理・通知なし、分担請求・通知なし、分担請求・通知ありの順。未実行のP40_04_PLAIN_KEEPや使用量不明のP40_04_BUDGET_KEEPを補完しない。確認用12シナリオも使わない。

各保存入力を再構成し、元のハッシュと一致させる。入力、モデル、次のseed、サンプリングは維持する。出力枠は `min(4096, 残token − 次の全入力token)`。０以下なら生成しない。３件目の残tokenは6,590、入力は16,123なので、短い出力枠でも生成不可という負の対照になる。

## 費用と停止

最大２生成、既知入力と最大出力の合計上限39,949 token。失敗・上限到達も含めて記録する。各入力は再計数し、初回キャッシュ再利用なしを実測確認する。

元のP40は途中のキャッシュを持っていたが、今回の入力は新しく処理する。そのため診断には別枠で各最大360秒、全体900秒を設定する。**元の残時間内に仕事が完了するかを測る実験ではない。** 時間・入力処理を含む診断費用は別に記録し、P40の費用・成否を書き換えない。上限延長でP40を再試行することとも区別する。

使用量不明、入力計数・モデル・キャッシュ状態の不一致、時間上限、明示停止でバッチを止める。試行の差し替えはしない。出力上限に達して指示を返せなかった場合は、その結果を残して次の固定入力へ進む。

## 判定すること／しないこと

生成結果は実行しない。道具名とJSON引数、参照先の存在、Python 3.12の構文だけを機械確認する。完結した指示がない、途中で切れた、構文に適合する、という状態を区別する。構文適合は、処理内容の正しさ・必要性・最終成功を保証しない。

短い出力枠で指示が出るなら、次段階の実行を含む比較に進む余地がある。指示が出なければ、枠を増やして成功するまで反復する案は採らない。元の残時間、必要な道具処理、次の入力費用も含めて、より早い段階の予算配分を検討する。

残量通知・出力枠の調整は通常の制御であり、新規性にはしない。ここで確認するのは、提案方式と比較する基準が不必要に早く停止していないかという一点。新しい省費用方式の有効性は別の比較で示す必要がある。
