# 公開APIの返却と例外を区別する通常部品

2026年10月23日、P77で確認した全３例外を公開記録と実装から読み取った。精算２件は認証失敗の文字列を辞書として参照した二次エラー、書出し１件は読取専用ファイルシステムへの書込み失敗だった。失敗の原因を区別するため、API呼出し元で返却・例外を包む任意利用の部品を追加した。**新手法の中核ではなく、タスク成功・費用改善は未測定。現行の実験用workerへの接続もまだ行っていない。**

## 確認した範囲

[全３件の読取記録](../reports/P77_public_failure_contract_review.json)は0.003844秒、追加生成・API・評価・保存コード実行・DB内容読取・保留課題読取０。P77と同じ公開spansとコードのhashを照合し、元の報告を上書きしていない。表の３件は全件であり、独立した３課題ではない。

| 元条件 | プログラム例外 | 公開APIの返却 | 解釈 |
|---|---|---|---|
| P76 精算・公開のみ | TypeError | phone.loginの返却１件がJSONではないstr、Tracebackを含む | 失敗文字列の辞書参照が元の認証失敗を隠す |
| P76 精算・推論保持 | TypeError | 同じ型・同じ公開観測hash | 同じ経路の失敗。推論保持だけでは解決しなかった |
| P76 書出し・公開のみ | OSError、Errno 30 | show_songの60返却は全てJSONのdict | コード43行のopen(..., 'w')で読取専用環境へ書込み。APIのJSON解析失敗ではない |

別の手動読取では、精算２件の公開観測にHTTP 401があり、標準文書とfunction calling文書のphone.loginは共にusername/passwordを指定していた。引数名のスキーマ不一致とは判定しない。この手動確認は上記の機械集計へ事後に混入させず、資格情報・引数値・エラー本文は公開しない。誤った資格情報の作成理由や、正しい資格情報へ置き換えた場合の最終成功は未確認。

P25では同じ既知書出し課題に75 APIで成功した履歴があるが、P76と同時・同条件の対照ではない。「80 APIでは不可能」も「この例外だけ直せば成功」も導かない。

## 実装の契約

現行の`ApiChannel`は、bridgeの返却をJSON解析できない場合に文字列として保つ。AppWorldの`execute`は、実行時例外の説明を文字列として返す。したがって、文字列の内容だけから正常な文字列と実行失敗を一意に区別することはできない。旧実装の実験結果を誤りとして差し替えない。

[public_api_envelope.py](../scripts/public_api_envelope.py)は、公開文書にあるAPIを１回呼び、その位置でのPython例外を捕捉する。JSON引数はリテラルとして埋め、呼出しごとに新しい128 bit nonceを使うことを呼出し側の契約とする。

| 状態 | 意味 | 呼出し側が言える範囲 |
|---|---|---|
| returned | APIが値を返した | 値は保持する。業務上の成功・タスク完了とは限らない |
| raised | 呼出し中のExceptionを元の位置で捕捉した | 型とメッセージを区別できる。先行作用や呼出し途中の作用が取り消されたとは言えない |
| 不正・欠落した返却 | 完全な対応付きJSONを確認できない | 結果・作用は不明。追加送信と自動再試行を止める |

エラーに見える正常文字列を例外へ変換しない。`success: false`を含む通常の返却辞書も、Python例外へ付け替えない。複数JSON、余分なstdout、重複key、別nonce、非有限数、過大な応答は受理しない。返却の直列化で失敗した場合も、APIが未実行だったとは言わない。nonceは対応照合であり、悪意ある実行系の真正性を証明するものではない。JSON以外のPython戻り値の完全な型保存を提供する部品ではない。

Pythonの例外は失敗した文からそのまま実行を再開する仕組みではない。名前空間を保持しても、ループ位置、部分更新、外部操作の再実行可否は別に扱う必要がある。メッセージ本文も安定した制御用APIとはされていないため、今回の文字列markerを一般の復旧規則にしない。[Python 3.12実行モデル](https://docs.python.org/3.12/reference/executionmodel.html)。

## 検証と次の判断

14件の部品検査を含む全1,008検査が1.760秒で合格し、scripts/testsのcompileallも成功した。[実際のSafetyGuard下の４合成ケース](../reports/public_api_envelope_guard_20261023.json)では、JSON、エラーに見える文字列、作用後の例外、業務失敗を含む辞書を0.038695秒で確認した。各fixture呼出しは１回で補助関数は除去。AppWorldインスタンス・タスク・API・評価器は使っていない。

次の実験に使う場合は、両対照に同じ返却契約を与え、追加の制御自体の差を測る必要がある。返却型を直すこと、状態保持を説明すること、通常の部分再実行だけを提案手法にはしない。今回の実装だけを理由にモデルを再起動せず、制御規則・比較相手・有限予算・反証条件を先に定める。既に終了したP76/P77と原稿の成否・費用・使用量不明は変更していない。
