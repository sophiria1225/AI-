# 技術的中核の再検討：2026年10月21日

**現時点では、独自アルゴリズムは確定していない。** 前案の四条件比較は機構を調べる実験設計として残すが、それ自体を新しい制御技術とは呼ばない。集約を前提に実装と大規模実験を進める方針から、近接方式の具体的な制約を確かめて技術を選び直す方針へ変更した。[Issue #28](https://github.com/sophiria1225/AI-/issues/28)で管理する。

## 1. 何を目指すか

大規模で相互依存する仕事について、同じモデルで品質条件を満たしながら、仕事全体の入力・出力トークンを減らす。そのために、ハーネスが情報・作業状態・実行を扱う機構を研究する。人数や担当を変えることは手段の候補であり、必須の結論ではない。

必要なのは「既存機構AとBを接続した」という説明から一段進んだ、次の対応関係である。

> 既存方式が依存する仮定 → その仮定が成立しない観測可能な状態 → 具体的な表現・更新規則の変更 → 同じ情報・予算での反証可能な比較

既存技術を使うこと自体が問題なのではない。接続によって何が初めて可能になるかを定義・検証できていないことが、現在の不足である。新しい略称や構成図だけでは補えない。

## 2. 今回確認した重複と、採用を見送る理由

以下は候補の**一般構想を独自技術として採用しない**という判断であり、各方式が無用・低性能という判断ではない。原稿の本文を確認した範囲と要旨だけの確認を分けた。今回の新しい文献は著者公開原稿として扱い、正式な査読採録は未確認。公開実装の性能再現は行っていない。保存した12原典のURL・版表示・SHA-256・確認範囲は[出典記録](../reports/R18_literature_sources.json)に置く。

| 候補の一般構想 | 確認した近接方式 | 今回の判断 |
|---|---|---|
| 将来の判断に必要な履歴を予測して残す | [FOCUS](https://arxiv.org/html/2609.37590v1)：将来計画で参照される履歴を選択し、防御的な再確認も行う | 将来の有用性を考慮するだけでは差にならない |
| 同じ内容でも受け手が使えない原因を分け、共有方法を選ぶ | [Bayes-Sufficient Compression Is Not Enough](https://arxiv.org/html/2610.03769)：情報の外部化、受け取り、行動への反映を分解し、通信方式を選択する | 「情報が届いたか」と「使えたか」の分離や費用付き通信選択だけでは差にならない |
| 失敗した質問を反例にして共有記憶を修正する | [WiCER](https://arxiv.org/html/2605.07068v1)：診断用QAと失敗分析から保持制約を加えて再構成する | 反例による記憶の更新という一般構想は見送る |
| 状態変更の影響を受ける担当だけに通知・再修正させる | [CoAgent](https://arxiv.org/html/2606.15376)：登録ツールの操作範囲、通知、順序付け、修復を扱う | 通知と部分修復だけでは差にならない。成立条件を読まずに保証を一般化しない |
| 意図・証跡・版をまとめて変更を確定する | [Cordon](https://arxiv.org/html/2606.17573)：意味的トランザクションと変更の検証。今回の確認は要旨・導入中心 | トランザクションという名称だけでは採用しない。本文の詳細照合は残る |
| 通信を遮断する介入から必要な経路を選ぶ | [E2-Explainer](https://arxiv.org/html/2608.12921v2)：経路の介入評価と予算付き構成選択 | 通信グラフを介入で求める一般構想は見送る |
| 誤りの依存を介入で確かめ、関連箇所を直す | [EDGE](https://arxiv.org/html/2609.01360v1)：誤りへの介入と依存の検証 | 依存グラフや反実仮想修正だけでは差にならない。ツール結果を固定する評価範囲を全環境の効果と混同しない |
| 意味が変わらない結果を再利用し、影響箇所だけ再計算する | [Incremental Consistency Execution](https://arxiv.org/html/2609.24090)：契約、依存、結果の不変領域を使う。今回の確認は要旨・導入 | 単なる差分実行や意味的な再利用は候補から外す。具体的アルゴリズムの比較は未了 |
| 証拠の範囲と必要項目を検査してから完了させる | [Evidence-Carrying Termination](https://arxiv.org/html/2608.23623v1)：信頼された要求契約と記録に対する決定的な検査 | 証拠台帳・完了ゲートを作るだけでは差にならない |
| 「見つからない」と「存在しない」を観測範囲で区別する | [CROWN-QA](https://arxiv.org/html/2608.04591v1)：完全性と質問範囲を変える評価、構造化した範囲判定 | 未観測と不在の区別自体を発見とはしない |
| 一件ずつでは分からない記憶同士の相互作用を測る | [MeClear](https://arxiv.org/html/2609.09115v1)：集合を変えた反実仮想評価と協力ゲームによる寄与評価 | 集合で評価するだけでは差にならない。単独削除が無効でも相互作用がないとはしない |

[iML](https://arxiv.org/html/2602.13937)も契約とモジュール分担の関連候補として保存したが、検索結果と取得HTMLで題名の版が異なった。詳細比較の根拠にはまだ使わない。検索で見つかっただけの文献を、本文・コードまで検証済みの比較対象へ昇格させない。

以前のFlow、Puppeteer、MaAS、TDAG、APO等との重複は[10月20日の比較表](related_work_matrix.md)に残す。今回の調査で「研究余地がない」と証明したわけでも、全関連研究を網羅したわけでもない。

## 3. 既存のP5記録を再点検した結果

元の2試行は変更せず、公開操作の記録だけを読む[監査スクリプト](../scripts/audit_p5_evidence.py)を追加した。推論本文、正解パッチ、独立評価用の追加テストは分析入力にしない。追加のモデル呼び出し・記録内コマンドの再実行は0回。[集計と出典ハッシュ](../reports/R18_P5_evidence_audit.json)。

| 観測 | 固定2担当 | 単一 |
|---|---:|---:|
| モデル呼び出し／公開ツール操作 | 36／36 | 38／38 |
| 記録された成果物変更境界 | 0 | 0 |
| 受理された完了宣言 | 0 | 0 |
| `head` / `tail`を含む操作文字列 | 19 | 17 |
| 出力が空・終了1・`grep`を含む操作文字列 | 2 | 4 |

操作文字列の検出は意味解析ではない。部分表示があるから必要情報が欠けた、検索の終了1だからリポジトリ内に対象がない、調査が長いから無駄だった、とは判断しない。一時領域への書き込みと、提出する成果物への変更も区別する。

表示処理の違いを最初は交絡の候補として点検した。上流のツールが前後各5,000文字と切り詰め表示を返し、本人用の表示器も前後各5,000文字に整形する。観測した長い出力は**単一試行の1回だけ**で、後段が削ったのは20文字の切り詰め表示だった。追加の原文欠落ではなく、単一試行には他担当もいない。2担当の36操作では後段の切り詰め自体が起きていなかった。この経路をP5の担当間情報差や失敗原因とする仮説は支持されなかった。

成果物変更のない2試行から、修正の往復や更新責任の競合は示せない。P5を集約判断器の教師データにしても、集約の利益ラベルは得られない。環境を完全に保存していなかったため、会話だけを取り出した再実行を「同一状態からの分岐」ともしない。

監査用の8制御検査は、切り詰め表示だけの削除／本当の原文欠落、境界長、文字数とバイト数、短い部分表示、不明な取得量、公開してはいけない本文の混入を点検する。これらの合格は新方式の性能実験ではない。

## 4. 次に確かめる制約の優先順位

次の表は**新規手法の採用表ではない**。既存方式を正しく動かした上で、追加の技術が必要かを調べる入口を選んだ。

| 優先 | 具体的な制約・出発点 | 最初の比較と、採用しない場合 |
|---|---|---|
| 1 | FOCUS付録A.10の、集合に対する抽象的な計画が個々の対象の情報を過小評価する事例 | 防御的検証を含む方式、対象IDを保持する単純な台帳、元の履歴保持を比べる。既存の台帳や防御的検証で足りれば、それ以上の独自機構を作る理由にしない |
| 2 | CoAgentの、登録された操作範囲・担当単独での成功等の前提 | まず共同更新が実際に起きる状態が必要。現在のP5にはその観測がない。前提外の例を作っただけで原方式を反証したとは呼ばない |
| 3 | EDGEでツール結果を固定した介入と、環境ごと再実行する介入の対象効果の違い | 測定妥当性の課題。研究の目的である実行品質・費用改善へつながる機構がない限り、主題にしない |

最初の項目を優先する理由は、原著者が具体的な失敗条件を明記していて、比較すべき修復処理もあるため。新規性が確定したからではない。ハーネスの情報保持と仕事の完了を結びつけられる一方、単なるチェックリストへ戻る危険もある。

### 最初の項目で、モデルを回す前に固定するもの

1. 原稿の防御的検証、閾値、圧縮時点、プロンプト、対象版と、実装の取得可否を確認する。論文の弱い変種だけを比較対象にしない。
2. 公開の実行タスクで、要求から対象集合を定める手続き、対象の列挙元、未処理対象、既処理対象を追える少数事例を選ぶ。FOCUSの説明例をそのまま自分たちの発見とはしない。
3. 課題入力・ツール出力から分かる情報だけを全方式へ渡す。最終正解の対象一覧を提案側だけに渡さない。
4. 対象ID台帳にも同じ抽出条件・保存・再読費用を課す。「完全な台帳を人が与える場合」は分析用上限へ分離する。
5. 個々の対象の脱落、余計な操作、最終完了、全呼び出しの費用を測る。情報が文脈から消えても、外部から再取得して正常完了すれば最終失敗とはしない。
6. 原方式も単純台帳も失敗する局面が残った場合に限り、その原因に対応した表現・更新規則を一つ定義する。実行単位の集約は自動的に追加しない。

これは局所的な機構検証であり、それだけで大規模・複数領域への有効性を主張しない。原資料や実行環境を小さな玩具問題へ置き換えて主実験を済ませる方針ではない。

### 原方式の再現準備で確認できたこと

FOCUSの[原稿PDF](https://arxiv.org/pdf/2609.37590v1)を追加確認した。付録A.9には既定の草案3回とAppWorldの圧縮開始4,096トークン、図4には保持閾値0.3が記載されている。この組合せでは、救済処理前の保持集合は「3草案のどれか1回以上で参照した履歴」の和集合になる。これは原方式の規則を具体化した算術であり、自分たちの新アルゴリズムではない。

付録A.10の失敗シナリオIDは`ff58e36`。個別の派生課題・乱数・その失敗軌跡は取得できていない。論文内のリンクと題名による検索では著者実装を特定できなかったが、公開実装が存在しないとは断定しない。本文から実装する場合は、仕様の補完箇所を明記した再実装として扱い、論文の成績の完全再現とは呼ばない。[arXiv要旨ページ](https://arxiv.org/abs/2609.37590v1)では著者が査読中のプレプリントと記載している。

AppWorldの[公式説明](https://github.com/StonyBrookNLP/appworld/blob/main/README.md)には、課題状態の保存・復元と、最終状態の検査への入口がある。ただし復元可能なのは記載された状態範囲であり、推論履歴・予算まで自動的に同一になるとはしない。データには解答・評価情報も付属するため、導入する場合は既存研究と同様に生成側から隔離する。元データをGitHubへ載せず、まず開発用の少数課題で動作を校正する。今回、データの導入・モデル実行・失敗の再現はまだ行っていない。

続いて[公式配布パッケージ0.1.3.post1](https://pypi.org/project/appworld/0.1.3.post1/)を625,317バイト取得し、配布元のSHA-256と照合して公開部分のソースだけを点検した。インストール、データ取得、課題・解答の閲覧は行っていない。[導入前の確認記録](../reports/R18_appworld_preflight.json)。

- 既存の実験用環境はPydantic 2.14.1、AppWorldの要求は2未満。既存環境へ上書き導入しない。
- 点検した保存関数はDB保存へ委譲し、復元はDB読込と前処理を行う。これらの関数にはユーザーが作ったPython変数の保存・復元が見当たらない。実行時の完全復元を確認したという意味ではなく、別途検査すべき範囲が分かった段階。
- データ取得処理は既存の保存先`data`を削除する実装だった。研究リポジトリ直下を取得先にせず、新しい専用ルートへ限定する。

## 5. 実装を拡大する条件

次の五点がそろうまで、自動再編判断器と大規模な構成比較へ進まない。

- 比較する具体的な既存方式と、実際に確認した制約がある。
- 提案の入力、状態表現、更新規則、出力を手順として書ける。
- 同じ情報の共有、単純台帳、再取得などで説明できる改善を除ける。
- 追加の制御・推論・保存・復元の費用を全て計上できる。
- 何が出ればその候補を取り下げるかを実行前に書ける。

独立した技術的中核は、この五点を満たしてから候補として提示する。今回は近接研究の重複確認と既存観測の監査を終えた段階であり、新手法の完成・新規性・性能改善を達成したとは報告しない。
