# 完了検査の自動作成を次の中核へ進める条件

2026-10-24。P81の固定反復を継続しながら、P66で局所的な削減が出た終了制御の未解決部分を確認した。P66は既知の写真課題に人が書いた要求解釈を使っており、自然言語要求から検査を自動で作った結果ではない。P68の書出し未達も保持する。今回、新しい契約生成モデル実験やオンライン完了操作は配分していない。

## 原典から確認した範囲

[Lahiri, Intent Formalization v1](https://arxiv.org/html/2603.17150v1)の要旨、§2、§2.1、§3.1–3.3を読んだ。検査できる仕様を生成することと、その仕様が元の意図に合うことを区別する。候補仕様をテストや変異した出力で検査する方法も扱うが、有限のテストが十分な意図検証になるとはしない。これは研究課題を整理する論考であり、今回のタスクへの性能再現ではない。

[Mendozaほか, ARTEMISのICSE 2026公式発表](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/287/Automating-Requirements-Formalization-Using-LLMs-and-Low-Complexity-Distinguishing-T)では、構造化自然言語を中間表現にし、候補を区別する短い実行例を人が受理・拒否して絞る手順を確認した。確認範囲は公式要旨と著者公開PDFの検索可能な冒頭・貢献記述である。PDF全文の取得は失敗したため、アルゴリズム節を読了したとはしない。原典の性能値を本実装の見込みへ転用しない。

既存の[ECT、Contract2Tool等との照合](termination_control_overlap_20261023.md)も維持する。自然言語から契約を生成する、契約を実行記録へ照合する、反例で契約を直すという一般形だけでは新しい規則にならない。

## 生成した検査を完了許可へ使う際の区別

| 自動作成案で確認できること | それだけでは確認できないこと |
|---|---|
| 出力が決めたJSONや検査言語の構文に合う | 元の要求を漏れなく正しく表したこと |
| 各検査に要求文の引用範囲がある | 否定、全称、対象範囲、時点、順序の意味が保存されたこと |
| 候補検査が保存した成功例を受理する | 別の誤った状態を受理しないこと |
| 有限の変異例や反例探索を通った | 未探索の入力・作用にも完全な判定となること |
| ２回のモデル判定が一致する | 両方が同じ要求を取り違えていないこと |

不明時に通常エージェントへ戻す仕組みは必要だが、誤った契約を正しいと誤認した場合の完了許可は防げない。未観測情報だけを「不明」にする規則と、要求解釈の正しさを同一視しない。これは自動作成一般の不可能性ではなく、現在の案に残る評価対象である。

## 比較へ進めるために固定するもの

次に候補を実装するなら、要求文と公開API記述のどこから、どの限定した義務を作るかを手順として示す。引用範囲の列挙に加え、対象集合、全称・存在、時点、操作順序、不明な外部作用をどう判定するかが必要になる。作成時点で使っていない将来の正解や評価器の判定を、契約の作成根拠へ戻さない。

比較は、人が正しく指定した既存の通常検査、単純な一回のモデル判定、候補の自動作成と実行時検査を分ける。契約生成、追加文書取得、検査、修復、不明時の通常継続を初回から計上する。後続生成が減っても構築費を含む全費用が増える場合は改善としない。複数仕事での償却を主張する場合は、その仕事数と再利用条件も先に固定する。

現時点では、これらを満たし通常対照を上回る具体的規則は未確立である。単に判定生成器を増設して新手法ができたとはしない。P81の全件結果を原稿へ反映する作業と、独自の制御規則を作る課題を分け、未閲覧12課題は保留する。
