# 保持結果が確定した後の草案生成を省けるか

P6で観測した費用を、既存の保持規則に沿って点検する補助分析。新方式の実課題比較ではなく、保存された出力を読む解析である。元の試行・プロンプト・予算は変更していない。

FOCUS再実装の設定は、3つの草案、参照率の閾値0.3、救済対象の和集合である。3草案なら必要な参照回数は`ceil(3 × 0.3) = 1`。一度保持が確定した履歴は、残りの草案で削除されない。

途中までの草案で、**全ての利用可能な履歴の保持が確定した**なら、残りの草案がどの有効な出力を返しても、保持集合は変わらない。後続の不正出力に対する既存の処理も「元の履歴を維持する」なので、この場合の保持集合は同じになる。任意の一部集合について途中終了できるという主張ではない。

| 第1課題の更新 | 全保持が確定した時点 | その後に記録された草案 | その草案の既知トークン |
|---|---|---:|---:|
| 1 | 最初の草案 | 2 | 15,773 |
| 2 | 不正参照が先にあり、認定しない | 0 | 0 |
| 3 | 不正出力が先にあり、認定しない | 0 | 0 |
| 4 | 2番目の草案 | 1 | 8,100 |
| 5 | 使用量不明の中断で、認定しない | 0 | 0 |

2つの更新で後続3呼び出し、既知23,873トークン、記録上283.544秒が省略候補となった。**実際に省略した実行結果ではなく、研究全体の削減実績でもない。** 不正な参照を後から削って認定を増やしていない。表の0は「省略候補に数えなかった」ことであり、元の失敗や費用が0という意味ではない。

3つの履歴について、残り2草案の参照・救済の全4,096組を列挙し、この条件で保持集合が変わらないことを検査した。閾値を変えた場合と、不正なIDを含む場合も確認した。実データの計測は[集計](../reports/P6_task1_shortcircuit_analysis.json)、処理は[解析スクリプト](../scripts/analyze_focus_shortcircuit.py)へ保存した。

第2課題の終了後、同じ解析を3更新へ適用した。全て認定前に不正草案があり、認定できた更新0、後続の省略候補0だった。[第2課題の集計](../reports/P6_task2_shortcircuit_analysis.json)にも失敗分類と入力・出力のハッシュを保存した。この早期終了だけでFOCUSの費用問題全体を解消できるとは言えない。

## この結果から行わない主張

保持集合が同じでも、未実行の後続処理、キャッシュの数値差、残予算、次回の乱数スケジュールは変わり得る。最終成功や全体の削減率は、実際の比較なしには分からない。原論文のあらゆる設定で同じ省略ができるとも言わない。

これは単調な集合演算に対する通常の早期終了であり、独自アルゴリズムの新規性にはしない。固定3草案を弱い比較相手として残す前に検討すべき改善候補である。P8・P9の校正結果を見て、必要なら制御費用を抑えた強い保持方式を比較対象へ追加する。
